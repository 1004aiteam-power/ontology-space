CIM을 파이썬 클래스로 설계하기Designing CIM as Python classes · pycim

IEC CIM의 UML 모델을 파이썬 클래스로 그대로 옮겨, 전력망 데이터를 코드로 만들고, 분석하고, 온톨로지(RDF)로 내보내고, pandapower · OpenDSS로 계산합니다. 지금은 Core · Topology · Wires 패키지의 핵심 클래스를 구현한 프로토타입 단계입니다.

pycim mirrors the IEC CIM UML model as Python classes: build grid data in code, analyse it, export it as an ontology (RDF), and solve it with pandapower · OpenDSS. It is a prototype covering the core classes of the Core · Topology · Wires packages.

Issued as UUID v4/v5; dependent objects derive from their parent. Duplicates and non-UUIDs are rejected.

💡 쉽게 말하면In plain words

전력 설비 공용 사전(CIM)을 파이썬 코드의 블록으로 그대로 옮긴 것입니다. 레고 설명서처럼 "차단기 블록", "선로 블록"을 만들고 단자로 끼워 맞추면 전력망이 조립됩니다. 조립한 결과는 온톨로지 문장(RDF)으로 저장하거나 계산 프로그램에 넘길 수 있습니다.

The shared power-equipment dictionary (CIM) turned into Python building blocks. Like LEGO instructions, you create "breaker blocks" and "line blocks", snap them together via terminals, and a grid is assembled — then saved as ontology sentences (RDF) or handed to a calculator.

사용 예Usage

from pycim import *

m = Model()
n1, n2 = m.add(ConnectivityNode(name="N1")), m.add(ConnectivityNode(name="N2"))
src = m.add(ExternalNetworkInjection(name="grid")).connect(n1)
cb  = m.add(Breaker(name="CB")).connect(n1, n2)        # creates Terminal 1, 2
ld  = m.add(EnergyConsumer(name="load", p=8.5)).connect(n2)

cb.open = True
topology.deenergized_loads(m, [src])   # → [EnergyConsumer('load')]
print(to_turtle(m))                    # export as CIM RDF (Turtle)

mRID 발급 (pycim/ids.py)Issuing mRIDs (pycim/ids.py)

CIM의 mRID는 한 번 발급하면 바뀌면 안 됩니다. pycim은 세 가지 방식을 제공합니다.

An mRID must never change once issued. pycim offers three ways to issue one.

함수FunctionUUID용도Use
new_mrid()v4기본값. 새 설비 등록Default. New equipment

from pycim import Breaker, ConnectivityNode, Model, stable_mrid

# 기존 SCADA 설비코드 → 항상 같은 mRID (UUID v5)
cb = Breaker(mrid=stable_mrid("SCADA", "A변전소", "CB-154-01"), name="154kV 선로 CB")
cb.connect(ConnectivityNode(), ConnectivityNode())   # Terminal mRID도 cb에서 파생

m = Model()
m.add(cb)
m.add(Breaker(mrid="CB-154-01"))   # ValueError: mRID는 UUID여야 합니다
m.add(Breaker(mrid=cb.mrid))       # ValueError: 중복 mRID

RDF로 내보낼 때는 to_turtle(m, iri_style="urn")으로 urn:uuid:… 형식의 IRI를 쓸 수 있습니다 (기본값은 CGMES 2.4.15식 _uuid). 예제 계통(samples.py)은 모든 mRID를 v5로 발급해 몇 번을 만들어도 같은 ID가 나옵니다.

For RDF, to_turtle(m, iri_style="urn") emits urn:uuid:… IRIs (default: CGMES 2.4.15-style _uuid). The sample grid (samples.py) issues all mRIDs as v5, so it is identical on every build.

💡 쉽게 말하면In plain words

설비 번호를 만드는 번호표 발급기 세 가지입니다. 새 설비는 제비뽑기(new_mrid), 기존 시스템에서 옮겨 오는 설비는 옛 코드로 찍는 도장(stable_mrid, 몇 번을 옮겨도 같은 번호), 단자 같은 부속품은 본체 번호에서 이어 붙이기(child_mrid)입니다. 형식이 틀렸거나 이미 있는 번호는 받아 주지 않습니다.

Three ticket machines for equipment numbers: a lottery draw for new equipment (new_mrid), a stamp made from the old code for migrated equipment (stable_mrid, same number every time), and numbers derived from the parent for parts like terminals (child_mrid). Badly formed or duplicate numbers are refused.

UUID 자세히: v4, v5, 그리고 시간으로 만드는 IDUUIDs in depth: v4, v5 and time-based IDs

mRID에 쓰는 UUID가 어떻게 생겼고, 버전마다 무엇이 다른지 정리했습니다. 아래 상자에서 브라우저로 직접 만들어 볼 수 있습니다.

What the UUIDs behind mRIDs look like and how the versions differ. Try generating them in your browser below.

생김새Anatomy

UUID는 128비트 숫자를 16진수 32글자로 적고, 하이픈으로 8-4-4-4-12로 나눈 것입니다. 13번째 글자가 버전, 17번째 글자가 variant(RFC 표준 UUID면 8·9·a·b 중 하나)입니다.

A UUID is a 128-bit number written as 32 hex digits split 8-4-4-4-12. The 13th digit is the version; the 17th is the variant (8, 9, a or b for RFC UUIDs).

현재 시각을 나노초로: 쓸 수 있지만 ID로는 부족합니다Current time in nanoseconds: useful, but not enough for an ID

네, 있습니다. Python의 time.time_ns()는 1970-01-01 UTC부터 지난 시간을 나노초 정수로 돌려줍니다. 예를 들어 이 페이지를 만들 때의 값은 1793748581701337119였습니다(19자리, 2026-11-03).

Yes. Python's time.time_ns() returns nanoseconds since 1970-01-01 UTC as an integer, e.g. 1793748581701337119 (19 digits) when this page was written (2026-11-03).

함수Function무엇을 재나Measures쓰임Use

ID로 쓰기에 부족한 이유는 세 가지입니다.

  • 단위와 정밀도는 다릅니다. ns 단위로 찍혀도 실제 시계 해상도는 운영체제·하드웨어에 따라 더 거칠 수 있습니다.
  • 같은 순간이 겹칩니다. 여러 서버나 스레드가 같은 값을 받을 수 있습니다.
  • 시계는 뒤로 가기도 합니다. 시각 보정이 일어나면 같은 값이 다시 나올 수 있습니다.

Why it is not enough as an ID:

  • Unit is not precision. Real clock resolution may be coarser than the ns unit, depending on OS and hardware.
  • Instants collide. Several servers or threads can read the same value.
  • Clocks go backwards. After a correction, a value can repeat.

그래서 시간 기반 ID는 시각에 무작위 비트나 순번을 붙입니다.

  • UUID v1: 1582년부터 센 100ns 단위 시각에 MAC 주소를 붙입니다. 장비 주소가 드러나 요즘은 피합니다.
  • UUID v7(RFC 9562, 2024): 유닉스 밀리초에 난수를 붙입니다. Python은 3.14부터 uuid.uuid7()을 지원합니다.
  • ULID: v7과 비슷한 구조를 26글자로 짧게 적습니다.
  • Snowflake: 밀리초에 장비 번호와 순번을 붙인 64비트 정수입니다.

So time-based IDs add random bits or a counter:

  • UUID v1: 100 ns ticks since 1582 plus the MAC address; avoided now because it leaks the device address.
  • UUID v7 (RFC 9562, 2024): Unix ms plus random bits; Python has uuid.uuid7() from 3.14.
  • ULID: a v7-like layout written in 26 characters.
  • Snowflake: a 64-bit integer of ms, machine number and sequence.
💡 mRID에는 무엇을?Which one for mRIDs?

새로 생긴 설비는 v4로 발급합니다. 기존 시스템 코드가 있으면 v5로 그 코드에서 만들어, 다시 만들어도 같은 ID가 나오게 합니다. mRID는 "언제 만들었나"를 담을 필요가 없고 바뀌지 않는 것이 가장 중요하므로, 시각을 드러내는 v7이나 나노초 시각은 쓰지 않았습니다. 다만 DB 정렬이 중요한 기록(측정값, 이벤트 로그)에는 v7이 잘 맞습니다.

New equipment gets a v4; equipment with a legacy code gets a v5 derived from it, so rebuilds keep the ID. An mRID needs no creation time and must never change, so v7 and raw ns timestamps are not used. For time-ordered records (measurements, event logs) v7 fits well.

하나의 CIM 모델, 두 개의 해석 도구One CIM model, two solvers

pycim 모델을 pandapower 네트워크와 OpenDSS 스크립트로 자동 변환해, 같은 계통을 두 도구로 계산합니다.

A pycim model is converted automatically to a pandapower network and an OpenDSS script, so the same grid is solved by both tools.

             ┌──▶ export_pandapower ──▶ pandapower net ──▶ runpp()
CIM model ───┤
 (pycim)     └──▶ export_opendss    ──▶ .dss script    ──▶ Solve
💡 쉽게 말하면In plain words

같은 설계도를 두 가지 계산기의 언어로 번역하는 것입니다. pandapower는 표(엑셀 같은)로, OpenDSS는 명령문으로 전력망을 받아들이기 때문에, 하나의 CIM 모델에서 두 형식을 자동으로 만들어 넘겨줍니다. 두 계산기의 답이 같으면 번역이 제대로 됐다는 증거입니다.

Translating one blueprint into two calculators' languages. pandapower takes the grid as tables, OpenDSS as text commands, so one CIM model is automatically turned into both. Matching answers from both prove the translation is right.

Like a contact card that lists a person's national ID (mRID) alongside their employee, student and membership numbers. Attach the SCADA, asset and GIS numbers to one device, and any of them leads to the same equipment.

CGMES 파일 읽기: CIGRE MV 배전망Reading CGMES: the CIGRE MV network

실제 CGMES 2.4.15 파일(CIGRE 중압 배전 벤치마크, NEPLAN에서 내보냄)을 pycim.cgmes.read_cgmes()로 읽어 pycim 객체로 만들고, 조류계산 결과를 파일에 들어 있는 NEPLAN의 결과와 비교했습니다.

Real CGMES 2.4.15 files (CIGRE medium-voltage benchmark exported from NEPLAN) are read into pycim objects with pycim.cgmes.read_cgmes(), and our power flow is compared with NEPLAN's results stored in the file.

💡 쉽게 말하면In plain words

다른 회사 양식의 서류를 우리 양식으로 옮겨 적는 일입니다. 우리가 모르는 칸(도면 좌표 등)은 건너뛰고, 번호 체계가 다르면 우리 규칙대로 새 번호를 주되 원래 번호는 메모(Name)로 남깁니다. 다 옮긴 뒤 계산해 보니 원래 회사(NEPLAN)의 답과 거의 같아서, 제대로 옮겨졌다는 것을 확인했습니다.

Copying another company's forms into our own format. Unknown fields (drawing coordinates etc.) are skipped; if numbering differs, new numbers are issued our way while the originals are kept as notes (Names). Recalculating afterwards gives almost the same answers as the original tool (NEPLAN), confirming a faithful copy.

읽을 때 처리하는 것What the reader handles

  • 네임스페이스: CIM16(2012·2013)과 CIM100을 모두 인식
  • 모르는 클래스(Diagram, OperationalLimit 등)는 건너뛰고 개수를 보고
  • UUID가 아닌 ID(Load7-I, N12) → UUID v5 mRID를 새로 발급하고, 원본 ID는 Name(NameType "rdf:ID")으로 보존
  • 버스-브랜치 모델: ConnectivityNode 없이 TopologicalNode만 있으면 노드마다 ConnectivityNode 생성
  • SSH 없음: 부하의 P, Q를 SV의 SvPowerFlow에서 가져옴
  • Namespaces: CIM16 (2012, 2013) and CIM100
  • Unknown classes (Diagram, OperationalLimit…) are skipped and counted
  • Non-UUID IDs (Load7-I, N12) → new UUID v5 mRIDs; the original ID is kept as a Name (NameType "rdf:ID")
  • Bus-branch models: if only TopologicalNodes exist, one ConnectivityNode is created per node
  • No SSH: load P, Q are taken from the SV SvPowerFlow

계산 결과를 CIM SV 프로파일로Writing results back as the CIM SV profile

조류계산 결과를 다시 CIM 객체(SvVoltage, SvPowerFlow)로 만들어 RDF로 저장합니다. CIM에서 해석하고 다시 CIM으로 돌아오는 흐름이 완성됩니다.

Power flow results become CIM objects (SvVoltage, SvPowerFlow) and are saved as RDF, closing the loop from CIM to analysis and back to CIM.

   │ topology.process()      닫힌 개폐기로 이어진 ConnectivityNode → TopologicalNode   (TP)

TopologicalNode와 SV 객체의 mRID도 부모에서 파생(UUID v5)하므로, 같은 계통을 다시 계산하면 같은 ID에 새 값이 들어갑니다. 결과 파일: sample_grid_full.ttl · cigre_mv_SV_pycim.ttl · 실습 페이지에서 "SV 전압" 질의로 확인할 수 있습니다.

TopologicalNode and SV mRIDs are derived from their parents (UUID v5), so re-running the same grid updates values under the same IDs. Output: sample_grid_full.ttl · cigre_mv_SV_pycim.ttl · try the "SV voltages" query on the Lab page.

💡 쉽게 말하면In plain words

계산 결과를 원래 장부에 다시 기록하는 것입니다. 전압과 전력 흐름이 설비 정보와 같은 형식(온톨로지 문장)으로 저장되므로, "전압이 0.95 미만인 곳은?" 같은 질문을 바로 할 수 있고, 같은 규칙으로 검사하고, 다른 시스템과 그대로 주고받을 수 있습니다.

Writing the results back into the same ledger. Voltages and flows are stored in the same form (ontology sentences) as the equipment, so you can immediately ask "where is voltage below 0.95?", check them with the same rules, and exchange them as-is.
