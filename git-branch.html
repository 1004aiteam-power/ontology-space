Git 사용법 · 브랜치와 병합GIT USAGE · BRANCHES AND MERGING

🌳 갈라지고 합치기:
브랜치 · 병합 · 충돌Forking and joining:
branches, merging and conflicts

Git 의 힘은 가볍게 갈라지고 안전하게 합치는 것에서 나옵니다. 브랜치가 정말 이름표일 뿐임을 그래프로 확인하고, 합치기(fast-forward · 병합 커밋 · rebase)가 이력을 어떻게 다르게 남기는지, 충돌이 나면 어떻게 푸는지를 터미널에서 직접 해 봅니다.

Git's strength comes from forking lightly and joining safely. See in the graph that a branch really is just a label, how joining (fast-forward, merge commit, rebase) leaves history differently, and how to resolve a conflict, all in the terminal.

터미널은 페이지 안의 시뮬레이터입니다. 병합 · 충돌 · rebase 의 동작은 tests/git.test.mjs로 확인합니다.

The terminal is a simulator inside this page. tests/git.test.mjs checks merging, conflicts and rebase.

LAB 1

브랜치는 이름표, 병합은 이름표 옮기기A branch is a label; merging moves labels

main 에 커밋 3개가 있는 저장소입니다. 아래 ▶ 를 순서대로 눌러 브랜치를 만들고, 커밋하고, 합쳐 보세요. 오른쪽 그래프에서 이름표(초록)가 어떻게 움직이는지가 핵심입니다. 첫 병합은 fast-forward, 두 번째는 갈라진 뒤라 병합 커밋이 만들어집니다.

A repo with three commits on main. Press the ▶ buttons in order to create a branch, commit and merge. Watch how the labels (green) move in the graph on the right. The first merge is a fast-forward; the second, after the history forked, makes a merge commit.

커밋 그래프Commit graph

세 영역Three areas

  1. 지금 main 에 커밋 3개. 그래프의 main 이름표와 HEAD 가 가장 최근 커밋에 있습니다.main has three commits. The main label and HEAD sit on the newest commit in the graph.
  2. 브랜치를 만든다 = 이름표 하나 더 붙이기. 커밋은 하나도 복사되지 않습니다.Making a branch = putting one more label. No commit is copied.
  3. HEAD 가 feature 로 이동. 파일은 그대로(같은 커밋이니까).HEAD moves to feature. Files stay (same commit).
  4. feature 에서 커밋. feature 이름표만 앞으로 가고 main 은 제자리입니다.Commit on feature. Only the feature label moves forward; main stays.
  5. main 으로 돌아오면 f.txt 가 사라집니다(그 커밋이 main 에는 없으니까). ls 로 확인하세요.Back on main, f.txt disappears (main lacks that commit). Check with ls.
  6. main 이 feature 의 조상이라 fast-forward: 새 커밋 없이 이름표만 앞으로 옮깁니다.main is an ancestor of feature, so fast-forward: no new commit, the label just moves ahead.
  7. 새 브랜치를 만들며 이동 (branch + switch 한 번에).Create and move to a new branch (branch + switch in one).
  8. login 에서 커밋.Commit on login.
  10. main 에서도 커밋 — 이제 두 갈래로 갈라졌습니다 (그래프 확인).Commit on main too: the history has now forked in two (see the graph).
  11. 갈라진 두 줄은 fast-forward 가 안 되어 병합 커밋(부모 둘)이 생깁니다. 파일이 겹치지 않아 자동으로 합쳐졌습니다.Forked lines cannot fast-forward, so a merge commit (two parents) is created. The files do not overlap, so it merged automatically.
  12. 병합 커밋이 맨 위에 있습니다.The merge commit is on top.
  13. 합친 브랜치는 이름표만 지우면 됩니다 (커밋은 그대로 이력에 남음).A merged branch is deleted by removing just the label (commits stay in history).
  14. 아직 커밋하기 이른 작업이 생겼다고 합시다.Suppose some work is too early to commit.
  15. 작업 폴더를 깨끗이 치우고 임시 보관함에 넣습니다. 급한 일이 생겼을 때 쓰는 명령.Tucks it into a temporary shelf and cleans the working tree. For when something urgent comes up.
  16. 다시 꺼내서 이어서 작업합니다.Take it back out and carry on.
LAB 2

충돌을 일부러 만들어 풀어 보기Make a conflict on purpose and resolve it

충돌은 사고가 아니라 "사람이 정해 줘야 할 곳"을 Git 이 알려 주는 것입니다. 같은 줄을 두 브랜치에서 다르게 고쳐 병합하고, 표시를 지워 해결해 봅니다. 중간에 포기하려면 git merge --abort.

A conflict is not an accident but Git showing where a human must decide. Change the same line differently on two branches, merge, and resolve by removing the markers. To give up midway: git merge --abort.

커밋 그래프Commit graph

세 영역 (⚔ = 충돌 중)Three areas (⚔ = in conflict)

  1. app.txt 한 줄을 두 브랜치에서 다르게 고쳐 볼 겁니다.You will change one line of app.txt differently on two branches.
  2. feature 에서 둘째 줄을 blue 로.On feature, line 2 becomes blue.
  4. main 에서 같은 줄을 green 으로.On main, the same line becomes green.
  5. CONFLICT! 같은 줄을 서로 다르게 바꿔 Git 이 정할 수 없습니다. 표 끝의 ⚔ 표시 확인.CONFLICT! The same line was changed differently so Git cannot decide. Note the ⚔ mark in the table.
  6. "Unmerged paths: both modified: app.txt". 병합이 도중에 멈춘 상태이고 프롬프트에 MERGING 이 보입니다."Unmerged paths: both modified: app.txt". The merge is paused midway and the prompt shows MERGING.
  7. 충돌 표시: <<<<<<< HEAD 아래가 내 쪽(main), ======= 아래가 상대(feature).Conflict markers: below <<<<<<< HEAD is yours (main), below ======= is theirs (feature).
  8. 해결 전에는 커밋이 거절됩니다.Committing is refused before resolving.
  9. 파일을 원하는 모양으로 고쳐 씁니다 (표시도 모두 지움). 실제로는 편집기로 합니다.Rewrite the file the way you want (removing all markers). In reality you do this in an editor.
  10. "해결했다"고 표시. ⚔ 가 사라집니다.Mark it "resolved". The ⚔ disappears.
  11. 병합 커밋 완성 (부모 둘).The merge commit is complete (two parents).
  12. 결과 확인.Check the result.
LAB 3

merge 와 rebase: 같은 결과, 다른 이력merge and rebase: the same result, different history

시작은 같습니다: main 에 커밋 B, feature 에 커밋 C 가 따로 있습니다. 왼쪽은 git merge feature, 오른쪽은 git rebase main(feature 에서) 뒤 main 에서 merge 한 결과입니다. 파일 내용은 같지만 그래프의 모양이 다릅니다.

Same start: commit B on main and commit C on feature. Left is git merge feature; right is git rebase main (on feature) followed by a merge on main. The file contents are the same but the shape of the graph differs.

rebase

  

  
rebase 는 C 를 복사해서 B 위에 다시 쌓습니다. 그래서 C 의 해시가 바뀌고(두 그림의 C 해시가 서로 다릅니다), 이력이 한 줄로 깔끔해집니다. 대신 이미 push 해서 남이 쓰는 커밋에는 쓰면 안 됩니다.rebase copies C and stacks it again on top of B. So C's hash changes (C has a different hash in the two pictures) and history becomes one tidy line. In exchange, never use it on commits you already pushed and others use.

알아 둘 원리Principles worth knowing

  

    
① 브랜치가 가볍다는 말의 뜻① What "branches are cheap" means

      
브랜치는 커밋 하나의 해시를 담은 작은 파일입니다. 만드는 데 파일도 커밋도 복사하지 않으니 실험마다 브랜치를 만드는 것이 Git 의 기본 작법입니다. 합칠 때만 비용이 들고, 쓸모없어진 브랜치는 이름표만 지우면 됩니다.

      
A branch is a tiny file holding one commit hash. Creating one copies no files or commits, so a branch per experiment is Git's default practice. Only merging costs something, and an obsolete branch is removed by deleting just the label.

    
② fast-forward 와 세 갈래 병합② Fast-forward vs three-way merge

      
한쪽이 다른 쪽의 후손이면 이름표만 앞으로 옮기는 fast-forward입니다. 두 쪽이 갈라졌으면 공통 조상(merge base)과 양쪽을 비교해 합치고 부모 둘인 병합 커밋을 만듭니다. 이력에 합친 흔적을 남기고 싶으면 --no-ff.

      
If one side descends from the other it is a fast-forward: only the label moves. If they forked, Git compares both sides against their common ancestor (merge base), merges and makes a two-parent merge commit. To keep a visible trace of the merge, use --no-ff.

    
③ 충돌의 정체와 푸는 순서③ What a conflict is and how to resolve it

      
공통 조상 대비 같은 곳을 다르게 바꾼 경우만 충돌입니다(다른 줄이면 자동으로 합쳐짐). 순서: git status로 충돌 파일 확인 → 파일을 열어 표시를 지우고 원하는 내용으로 → git add → git commit. 한쪽만 택하려면 git checkout --ours/--theirs 파일. 에디터나 IDE 의 3-way 병합 도구가 편합니다.

      
Only changes to the same spot, differently relative to the common ancestor conflict (different lines merge automatically). Steps: find the file via git status → edit away the markers and write what you want → git add → git commit. To take one side: git checkout --ours/--theirs file. An editor or IDE 3-way merge tool helps.

    
④ rebase: 복사해서 다시 쌓기④ rebase: copy and restack

      
rebase 는 내 커밋들을 잠시 떼어 두고 대상 브랜치 끝으로 간 뒤 하나씩 다시 적용합니다(위 LAB 3). 각 단계에서 충돌이 나면 멈추고, 풀고 git add → git rebase --continue, 포기는 --abort. 결과 이력이 직선이라 읽기 좋지만, 커밋 해시가 바뀝니다.

      
rebase sets my commits aside, goes to the target branch's tip and reapplies them one by one (Lab 3). A conflict stops it at that step; resolve, git add, git rebase --continue, or --abort to give up. The history is a straight line, easier to read, but commit hashes change.

    
⑤ 황금률: 공유한 커밋은 다시 쓰지 않는다⑤ Golden rule: never rewrite shared commits

      
rebase · amend · reset 은 해시를 바꿉니다. 이미 push 해서 남이 받은 커밋을 이렇게 바꾸면 남의 이력과 어긋나 큰 혼란이 생깁니다. 내 로컬(또는 나만 쓰는 feature 브랜치)에서만 다듬고, 공유한 것은 merge/revert로 앞으로만 나아가세요.

      
rebase, amend and reset change hashes. Altering commits already pushed and pulled by others diverges from their history and causes great confusion. Tidy only locally (or on a feature branch only you use) and move forward on shared work with merge/revert.

    
⑥ cherry-pick: 커밋 하나만⑥ cherry-pick: just one commit

      
git cherry-pick 해시는 다른 브랜치의 커밋 하나의 변경만 복사해 현재 브랜치에 새 커밋으로 만듭니다(해시는 다름). 릴리스 브랜치에 급한 수정 하나만 가져갈 때 씁니다. 같은 변경을 양쪽에 다른 커밋으로 두게 되므로 남발하면 이력이 헷갈립니다.

      
git cherry-pick hash copies only the change of one commit from another branch into a new commit on the current branch (different hash). Use it to take one urgent fix to a release branch. It leaves the same change as two different commits, so overuse muddles history.

    
⑦ 브랜치 전략: 팀의 약속⑦ Branching strategy: a team agreement

      
GitHub Flow: main 은 항상 배포 가능, 모든 작업은 짧은 feature 브랜치 + Pull Request → 머지(작은 팀에 적합). Trunk-based: 아주 짧은 브랜치로 main 에 자주 합침(CI 와 기능 플래그 필수). Git Flow: develop · release · hotfix 브랜치(릴리스 주기가 긴 제품). 정답은 없고 팀이 같은 규칙을 쓰는 것이 중요합니다. 이름은 feature/… fix/…처럼 접두사로 통일하세요.

      
GitHub Flow: main is always deployable; all work goes on short feature branches + Pull Request → merge (suits small teams). Trunk-based: very short branches merged to main often (needs CI and feature flags). Git Flow: develop, release and hotfix branches (for products with long release cycles). There is no right answer; what matters is the team using the same rule. Unify names with prefixes like feature/…, fix/….

    
⑧ 이 시뮬레이터가 생략한 것⑧ What this simulator leaves out

      
rebase -i(커밋 합치기 · 순서 바꾸기), 병합 전략 옵션, 서브모듈, git bisect, blame은 넣지 않았습니다. 그래프는 최근 커밋 16개까지만 그립니다. 충돌 병합은 줄 단위 LCS 로 만든 단순 구현이라 진짜 Git 의 ort 병합과 다르게 판정하는 경우가 있습니다.

      
Left out: rebase -i (squashing and reordering), merge-strategy options, submodules, git bisect and blame. The graph draws only the latest 16 commits. Conflict merging is a simple line-level LCS implementation and may judge some cases differently from real Git's ort merge.
