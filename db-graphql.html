🕸️ 모양은 클라이언트가 정한다:
GraphQL과 데이터 APIThe client decides the shape:
GraphQL and data APIs

REST는 서버가 응답의 모양을 정하고, GraphQL은 클라이언트가 질의로 정합니다. 화면이 필요한 필드만 한 번에 받고, 관계를 점에서 점으로 따라갈 수 있습니다. 대신 서버 안에서는 그 질의를 DB 질의로 풀어내는 일이 따로 필요하고, 거기서 N+1이 다시 나타납니다.

With REST the server decides the response shape; with GraphQL the client decides it in the query. A screen receives just the fields it needs in one call and can follow relationships from node to node. In exchange, the server must unpack that query into DB queries, and N+1 reappears there.

질의 해석과 실행은 이 페이지 안의 작은 구현이 하고, DB 질의는 같은 페이지의 SQL 엔진이 실제로 실행합니다. 결과 · 질의 수 · 오류는 tests/db.test.mjs로 확인합니다. 지원하는 문법은 중첩 필드와 인자뿐입니다.

Query parsing and execution is a small implementation in this page, and the DB queries are really run by the page's SQL engine. tests/db.test.mjs checks results, query counts and errors. Only nested fields and arguments are supported.

알아 둘 원리Principles worth knowing

  

    
① 왜 나왔나: 엔드포인트 폭발① Why it arose: the endpoint explosion

      
REST는 화면이 바뀔 때마다 새 엔드포인트가 필요하거나, 한 엔드포인트가 모든 화면에 필요한 필드를 다 담아 과하게(over-fetching) 보냅니다. 반대로 한 화면이 여러 자원을 모으려고 호출을 여러 번(under-fetching) 합니다. GraphQL(2015년 공개, 페이스북 출신)은 클라이언트가 모양을 정하는 질의 하나로 이 둘을 해결하려는 방식입니다. 위 비교 막대가 그 차이입니다.

      
REST needs a new endpoint whenever a screen changes, or one endpoint carries every field every screen might want and over-fetches. Conversely a screen collecting several resources makes several calls (under-fetching). GraphQL (open-sourced in 2015, from Facebook) tackles both with one query whose shape the client decides. The comparison bars above show the difference.

    
② 스키마가 계약이다② The schema is the contract

      
서버는 타입 있는 스키마(위)를 공개하고, 질의는 그 스키마에 맞아야 실행됩니다. 없는 필드를 묻거나 오브젝트 필드에 하위 선택을 빠뜨리면 실행 전에 오류입니다(위 예시 "잘못된 질의"). 같은 스키마가 문서이자 자동 완성이자 자기 설명(인트로스펙션)이어서 도구와 AI가 읽기 쉽습니다.

      
The server publishes a typed schema (above), and a query must fit it to run. Asking for a missing field, or leaving the sub-selection off an object field, is an error before execution (the "Invalid query" example above). The same schema serves as documentation, autocomplete and self-description (introspection), easy for tools and AI to read.

    
③ 리졸버와 N+1③ Resolvers and N+1

      
서버는 필드마다 리졸버(값을 가져오는 함수)를 갖고, 질의의 중첩을 따라 호출합니다. 변전소 3개에 각각 assets를 물으면 리졸버가 3번 불려 DB 질의가 3번 나가는데, 이것이 ORM의 N+1과 똑같은 문제입니다. 해법은 DataLoader: 같은 순간에 요청된 키를 모아 IN (…) 한 번으로 묻고 나눠 줍니다. 위의 체크박스로 질의 수가 줄어드는 것을 확인하세요.

      
The server has a resolver (a value-fetching function) per field and calls them along the query's nesting. Asking 3 substations for their assets calls the resolver 3 times, sending 3 DB queries, the same problem as the ORM's N+1. The fix is a DataLoader: gather the keys requested at the same moment, ask once with IN (…) and hand them out. Tick the checkbox above to watch the query count drop.

    
④ 질의가 자유로운 만큼 위험도 있다④ Freedom to query brings risk

      
클라이언트가 질의를 정하므로 substations { assets { substation { assets { … } } } }처럼 깊고 넓은 질의로 서버를 괴롭힐 수 있습니다. 대응은 깊이 제한 · 질의 비용 계산 · 시간 제한 · 승인된 질의만 허용(persisted queries)입니다. REST는 서버가 모양을 정하니 비용이 예측되지만, GraphQL은 이 방어를 직접 해 주어야 합니다.

      
The client chooses the query, so it can punish the server with a deep, wide query like substations { assets { substation { assets { … } } } }. Defences are depth limits, query cost estimation, timeouts and allowing only approved queries (persisted queries). With REST the server fixes the shape so cost is predictable; with GraphQL you must build these defences yourself.

    
⑤ 캐시와 권한이 어려워진다⑤ Caching and authorization get harder

      
REST는 주소마다 응답이 정해져 있어 HTTP 캐시가 잘 맞지만, GraphQL은 보통 한 주소(POST /graphql)에 질의가 다 실려 와 캐시 키가 질의 글자가 됩니다. 클라이언트 라이브러리가 객체 id 기준의 캐시를 따로 둡니다. 권한도 엔드포인트 단위가 아니라 필드 · 객체 단위로 리졸버 안에서 확인해야 합니다.

      
REST answers are fixed per address so HTTP caching fits well, but GraphQL usually carries every query to one address (POST /graphql), making the query text the cache key. Client libraries keep a separate cache by object id. Authorization must also be checked inside resolvers per field and object, not per endpoint.

    
⑥ 그래프 DB 질의와 닮았지만 다르다⑥ Like a graph-DB query, but not the same

      
GraphQL은 DB 질의 언어가 아니라 API 질의 언어입니다. 뒤에 무엇이 있든(표 · 문서 · 다른 API) 리졸버가 연결합니다. 반면 Cypher나 SPARQL은 DB가 직접 실행하는 질의입니다. 같은 질문 "Sub-A의 설비 이름과 건전도"를 세 말로: GraphQL { substation(id:"S1"){ assets{ name health } } } · Cypher MATCH (:Substation {id:'S1'})-[:HAS_ASSET]->(a) RETURN a.name, a.health · SQL SELECT name, health FROM assets WHERE substation_id = 'S1'. 그래프 DB 위에 GraphQL을 올리는 것도 흔합니다.

      
GraphQL is an API query language, not a DB query language. Whatever lies behind (tables, documents, other APIs), resolvers connect it. Cypher and SPARQL, by contrast, are queries the DB runs itself. The same question, "names and health of Sub-A's assets", in three languages: GraphQL { substation(id:"S1"){ assets{ name health } } } · Cypher MATCH (:Substation {id:'S1'})-[:HAS_ASSET]->(a) RETURN a.name, a.health · SQL SELECT name, health FROM assets WHERE substation_id = 'S1'. Layering GraphQL over a graph DB is also common.

    
⑦ 변경과 구독⑦ Mutations and subscriptions

      
읽기는 query, 쓰기는 mutation, 서버가 알려 주는 실시간 변경은 subscription(보통 WebSocket)입니다. 쓰기도 REST처럼 검증 · 권한 · 트랜잭션을 서버가 책임집니다. 이 페이지는 읽기만 만들었습니다. 여러 팀의 스키마를 하나로 묶는 페더레이션도 큰 조직에서 쓰입니다.

      
Reads are queries, writes are mutations, and real-time changes pushed by the server are subscriptions (usually over WebSocket). For writes too the server owns validation, authorization and transactions, as in REST. This page builds reads only. Federation, joining several teams' schemas into one, is also used in large organisations.

    
⑧ 이 모형이 생략한 것⑧ What this model leaves out

      
질의 언어의 일부(별칭 · 변수 · 프래그먼트 · 지시자 · mutation)와 타입 검사 · 널 규칙은 구현하지 않았습니다. REST 비교는 "객체마다 전체 필드를 돌려주는 자원 주소"라는 가정 아래 호출 수와 글자 수를 센 근사이며, 실제로는 필드 선택 옵션이나 묶음 엔드포인트로 줄일 수 있습니다.

      
Parts of the query language (aliases, variables, fragments, directives, mutations) and type checking and null rules are not implemented. The REST comparison counts calls and characters under the assumption of "resource addresses returning every field of each object"; in practice field-selection options or bundled endpoints can shrink it.
