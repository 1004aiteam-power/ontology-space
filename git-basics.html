Git 사용법 · 구조와 로컬 명령GIT USAGE · MODEL AND LOCAL COMMANDS

🌿 스냅샷을 쌓는 도구:
세 영역과 일상 명령A tool that stacks snapshots:
three areas and everyday commands

Git 은 폴더의 스냅샷을 차곡차곡 쌓는 도구입니다. 파일이 작업 폴더에서 스테이지를 거쳐 저장소에 기록되는 길을, 브라우저 안의 작은 Git 터미널에서 명령을 직접 쳐 가며 따라갑니다. 결과는 오른쪽 그림에 바로 나타납니다.

Git is a tool that stacks snapshots of a folder. In a small Git terminal in your browser you follow, typing the commands yourself, how a file goes from the working tree through the stage into the repository. The result appears at once in the pictures on the right.

터미널은 이 페이지 안의 시뮬레이터입니다 (실제 컴퓨터에는 아무 영향이 없습니다). 명령 이름과 출력 문장은 진짜 Git 을 따르고, 해시 계산은 진짜와 같습니다. 동작은 tests/git.test.mjs로 확인합니다.

The terminal is a simulator inside this page (it affects nothing on your computer). Command names and output wording follow real Git, and the hash calculation is the real one. tests/git.test.mjs checks the behaviour.

LAB 1

터미널에서 직접: 세 영역을 오가는 파일In the terminal: a file travelling through three areas

Git 은 파일이 ① 작업 폴더 → ② 스테이지 → ③ 저장소 세 곳을 거쳐 기록됩니다. 오른쪽 표는 같은 파일이 세 곳에서 어떤 내용(해시)인지 보여 주고, 다르면 강조합니다. 아래 순서의 ▶ 버튼을 누르거나 터미널에 직접 쳐 보세요. 이 터미널은 진짜 Git 이 내는 문장을 그대로 흉내 냅니다.

Git records a file as it travels through ① working tree → ② stage → ③ repository. The table on the right shows what content (hash) the same file has in the three places and highlights differences. Press the ▶ buttons in order or type in the terminal yourself. The terminal reproduces real Git's wording.

도움말: helpHelp: help

세 영역 (파일별 내용 해시)Three areas (content hash per file)

커밋 그래프Commit graph

따라 해 보기 (위에서부터)Follow along (from the top)

  1. 파일을 만듭니다. ① 작업 폴더에만 있고, 오른쪽 표의 ① 칸에 내용의 해시가 생깁니다.Create a file. It exists only in the ① working tree; a content hash appears in column ① of the table on the right.
  2. "Untracked files": Git 은 아직 이 파일을 모릅니다."Untracked files": Git does not know this file yet.
  3. ② 스테이지에 올립니다. ② 칸에 ①과 같은 해시가 생깁니다 (같은 내용 = 같은 이름).Put it on the ② stage. Column ② gets the same hash as ① (same content = same name).
  4. ③ 저장소에 스냅샷을 남깁니다. 그래프에 점이 생기고 HEAD 가 거기를 가리킵니다.Record a snapshot in the ③ repository. A dot appears in the graph and HEAD points at it.
  5. 파일을 고칩니다. ① 칸의 해시만 바뀌어 주황색으로 강조됩니다.Edit the file. Only the hash in column ① changes and is highlighted in orange.
  6. 작업 폴더 ↔ 스테이지 차이. 아직 add 하지 않은 변경이 보입니다.Difference working tree ↔ stage: changes you have not added yet.
  7. 고친 내용을 스테이지로. ② 칸이 바뀌어 녹색으로 강조됩니다(저장소와 달라짐).Stage the edit. Column ② changes and is highlighted green (now different from the repository).
  8. 스테이지 ↔ 저장소(HEAD) 차이 = 지금 커밋하면 들어갈 내용.Stage ↔ repository (HEAD) difference = what a commit would contain now.
  9. 두 번째 스냅샷. 새 커밋의 부모는 첫 커밋입니다 (그래프의 선).A second snapshot. Its parent is the first commit (the line in the graph).
  10. 이력을 한 줄씩. 맨 앞이 가장 최근입니다.The history, one line each; the newest first.
  11. 실수로 파일을 망쳤다고 합시다.Suppose you ruined the file by accident.
  12. 마지막 커밋(스테이지) 상태로 되돌립니다. 커밋 안 한 변경은 이 방법으로 못 살립니다 — 신중하게!Restore it from the stage. Uncommitted changes cannot be recovered this way; be careful!
  13. HEAD 커밋 객체의 속뜻: 트리 · 부모 · 작성자 · 메시지. Git 의 모든 것은 이런 객체입니다.The insides of the HEAD commit object: tree, parent, author, message. Everything in Git is such objects.
LAB 2

해시: 내용이 곧 이름이다Hashes: the content is the name

Git 은 파일 내용 앞에 blob 길이\0을 붙여 SHA-1으로 해시를 구하고, 그것을 이름으로 저장합니다. 아래 칸에 글을 쓰면 git hash-object가 내놓는 것과 같은 값이 실시간으로 나옵니다. 한 글자만 바꿔 보세요.

Git prepends blob length\0 to the file content, takes the SHA-1 and stores it under that name. Type below and you get the same value git hash-object would print, live. Change a single character.

줄 끝의 줄바꿈도 내용입니다: echo "hello" > a.txt의 파일은 hello\n(6바이트)이라 해시가 ce01362…입니다 — 진짜 Git 과 같은 값입니다. 위 칸의 마지막에 줄바꿈 하나를 더해 보세요.

The newline at the end is content too: a file from echo "hello" > a.txt is hello\n (6 bytes), so its hash is ce01362…, the same value real Git gives. Add one trailing newline in the box above.

알아 둘 원리Principles worth knowing

① 차이가 아니라 스냅샷① Snapshots, not differences

Git 은 커밋마다 "그 순간 프로젝트 전체의 모습"을 저장합니다(바뀌지 않은 파일은 같은 객체를 다시 가리킬 뿐이라 공간은 아낌). 그래서 브랜치를 바꾸거나 과거로 가는 일이 빠르고, 차이(diff)는 두 스냅샷을 비교해 그때그때 계산하는 것입니다.

Git stores "the whole project as it looked at that moment" per commit (unchanged files just point at the same object, saving space). So switching branches or going to the past is fast, and a diff is computed on demand by comparing two snapshots.

② 스테이지는 왜 있나② Why a stage exists

곧바로 커밋하지 않고 스테이지를 거치는 이유는 커밋을 의미 있는 단위로 나누기 위해서입니다. 파일 열 개를 고쳤어도 "버그 수정"과 "문서 정리"를 따로 커밋할 수 있습니다(git add -p는 한 파일 안에서도 조각별로 고름). 스테이지는 "다음 커밋의 초안"입니다.

The stage sits between so you can split commits into meaningful units. After editing ten files you can still commit "bug fix" and "docs cleanup" separately (git add -p even picks hunks within one file). The stage is "a draft of the next commit".

③ 커밋 = 스냅샷 + 부모 + 메시지③ A commit = snapshot + parent + message

커밋 객체에는 파일 목록(트리), 부모 커밋의 해시, 작성자, 시각, 메시지가 들어 있습니다. 부모를 따라가면 이력이 되고, 부모가 둘이면 병합 커밋입니다. 위 LAB 의 git cat-file -p HEAD가 그 내용을 그대로 보여 줍니다.

A commit object holds the file list (tree), the parent commit's hash, author, time and message. Following parents gives history; two parents make a merge commit. git cat-file -p HEAD in the lab shows exactly that.

④ 해시는 내용의 지문④ A hash is the content's fingerprint

같은 내용은 어디서 만들든 같은 해시, 한 글자만 달라도 전혀 다른 해시입니다. 커밋 해시는 부모의 해시를 포함하므로 과거를 몰래 바꾸면 그 뒤 모든 해시가 달라져 변조가 드러납니다. 그래서 커밋을 고쳐 쓰면(--amend, rebase) 새 해시가 생기고, 이미 공유한 이력에서는 문제가 됩니다.

The same content gives the same hash anywhere, and one changed character gives a completely different one. A commit hash includes its parent's hash, so secretly altering the past changes every hash after it, exposing tampering. That is why rewriting a commit (--amend, rebase) yields a new hash, a problem for history already shared.

⑤ 브랜치와 HEAD 는 포인터⑤ Branches and HEAD are pointers

브랜치는 커밋 하나를 가리키는 이름표(파일 하나에 해시 40자)이고, HEAD 는 "지금 내가 있는 곳"을 가리킵니다. 그래서 브랜치를 만드는 비용은 거의 0이고, 커밋을 하면 현재 브랜치의 이름표가 새 커밋으로 한 칸 이동합니다. 그래프의 이름표가 그것입니다. 다음 페이지에서 자세히 다룹니다.

A branch is a label pointing at one commit (a file with a 40-character hash), and HEAD points at "where I am now". So making a branch costs almost nothing, and committing moves the current branch's label one step to the new commit. The labels in the graph are those. The next page covers it.

⑥ .git 폴더가 저장소의 전부⑥ The .git folder is the whole repository

프로젝트 폴더의 숨김 폴더 .git에 모든 이력 · 브랜치 · 설정이 들어 있고, 나머지 파일들은 "지금 꺼내 놓은 한 시점"일 뿐입니다. .git을 지우면 이력이 사라지고(되돌릴 수 없음), 폴더를 통째로 복사하면 저장소가 복제됩니다. 백업이 곧 GitHub 에 push 해 두는 이유입니다.

The hidden .git folder holds all history, branches and config, while the other files are just "one point in time checked out". Deleting .git erases history (irreversibly), and copying the folder whole duplicates the repo. That is why pushing to GitHub counts as a backup.

⑦ 좋은 커밋: 작게, 자주, 이유를 적어서⑦ Good commits: small, often, with the why

한 커밋은 한 가지 목적으로 작게 만들면 리뷰와 되돌리기(revert)가 쉬워집니다. 메시지 첫 줄은 50자 안팎의 요약(예: fix: 로그인 시 빈 비밀번호 거부), 필요하면 한 줄 비우고 왜 바꿨는지를 적습니다. "수정", "update", "asdf" 같은 메시지는 6개월 뒤의 나에게 도움이 되지 않습니다.

Keep a commit small with one purpose so review and revert stay easy. The first line is a summary of about 50 characters (e.g. fix: reject empty password at login); if needed, leave a blank line and explain why. Messages like "fix", "update" or "asdf" do not help you six months later.

⑧ 이 시뮬레이터가 단순화한 것⑧ What this simulator simplifies

진짜와 같은 것: 파일 내용의 해시(SHA-1), 명령 이름과 출력 문장, 스냅샷 · 부모 · 브랜치 포인터 구조. 단순화한 것: 트리를 폴더 중첩 없이 한 장 목록으로 두었고, 압축 · 팩 파일 · 훅 · 서브모듈 · 편집기가 없어 -m "메시지"가 필수이며, 커밋 해시는 시각이 달라 진짜 Git 과 같은 값이 아닙니다. 상태는 새로고침하면 사라집니다.

Real: file-content hashes (SHA-1), command names and output wording, the structure of snapshots, parents and branch pointers. Simplified: the tree is one flat list without nested folders; there is no compression, pack files, hooks, submodules or editor so -m "message" is required; commit hashes differ from real Git because the timestamps differ. State vanishes on reload.
