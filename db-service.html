🚪 DB 앞의 문지기:
서비스 계층(REST)A gatekeeper in front of the DB:
the service layer (REST)

브라우저 · 앱 · 외부 시스템은 DB 계정을 가질 수 없습니다. 그래서 중간에 서비스를 두고 DB는 그 서비스만 알게 합니다. 이 계단부터는 SQL이 아니라 HTTP 요청으로 데이터에 접근합니다. 그만큼 DB에서 멀어지고, 안전과 변화에 대한 내성을 얻습니다.

Browsers, apps and outside systems cannot hold a DB account. So a service sits in between, and only it knows the DB. From this rung on, data is reached not by SQL but by HTTP requests: further from the DB, but safer and more tolerant of change.

서비스는 이 페이지 안의 데모용 코드이고(실제 네트워크 없음) 같은 페이지의 작은 SQL 엔진을 씁니다. 상태 코드 · 권한 · 검증 규칙은 tests/db.test.mjs로 확인합니다. 메시지 형식은 HTTP 페이지의 설명과 같습니다.

The service is demo code inside this page (no real network) using the same page's small SQL engine. Status codes, permissions and validation rules are checked in tests/db.test.mjs. The message format is as explained on the HTTP page.

DB를 직접 열어 주지 않고, 앞에 서비스를 둔다Do not open the DB directly; put a service in front

앞 단계까지는 DB 계정을 쥔 코드가 SQL을 직접 썼습니다. 브라우저 · 모바일 앱 · 다른 회사 시스템에는 그 계정을 줄 수 없습니다. 그래서 서비스가 그 계정을 혼자 쥐고, 바깥에는 정해진 요청만 받는 문(API)을 엽니다. 누구인지 확인하고(인증), 해도 되는지 판단하고(권한), 값을 검사하고(검증), SQL은 서비스 안에서만 만들어집니다.

Up to the previous rung, code holding the DB account wrote SQL directly. That account cannot be given to a browser, a mobile app or another company's system. So a service holds the account alone and opens a door (the API) that accepts only defined requests to the outside. It checks who you are (authentication), whether you may (authorization) and the values (validation); SQL is made only inside the service.

REST와 RPC: 같은 일을 다르게 말하기REST and RPC: the same job said differently

  

    
REST (HTTP + JSON)
GET    /api/assets/T1
PATCH  /api/assets/T1   {"health": 80}
DELETE /api/assets/T1
"자원"(명사)과 HTTP 메서드(동사)로 표현. 브라우저 · curl로 바로 시험, 캐시와 도구가 풍부.
Expressed as "resources" (nouns) and HTTP methods (verbs). Testable straight from a browser or curl, with rich caching and tooling.

    
RPC (gRPC 예)
service Assets {
  rpc GetAsset (AssetId) returns (Asset);
  rpc SetHealth (HealthUpdate) returns (Asset);
}
"함수 호출"처럼 표현하고 이진(protobuf)으로 전송. 서비스 사이(내부) 호출에서 빠르고 계약이 엄격.
Expressed like "function calls" and sent in binary (protobuf). Fast and strictly contracted for service-to-service (internal) calls.

  






  
알아 둘 원리Principles worth knowing

  

    
① 인증과 권한은 서비스의 일① Authentication and authorization are the service's job

      
인증(누구인가: 토큰 · 로그인)과 권한(이 사람이 이것을 해도 되는가)은 서비스가 요청마다 확인합니다. 위 실험에서 같은 POST가 토큰에 따라 401(누군지 모름) · 403(누군지는 알지만 권한 없음) · 201로 갈립니다. DB에 직접 붙으면 이 구분을 DB 계정 단위(거칠게)로만 할 수 있습니다. 그리고 보여 주는 필드도 정합니다: 조회자에게는 설치 연도를 숨겼습니다.

      
Authentication (who: token, login) and authorization (may this person do this) are checked by the service on every request. In the lab above the same POST goes to 401 (unknown caller), 403 (known but not allowed) or 201 depending on the token. Connecting straight to the DB, this distinction exists only per DB account (coarsely). The service also decides which fields are shown: viewers do not see the installation year.

    
② 입력은 믿지 않는다 (검증)② Never trust input (validation)

      
바깥에서 온 값은 모두 의심합니다. 형식(id는 T9 꼴) · 범위(건전도 0~100) · 허용 값(종류는 4가지 중 하나)을 서비스가 먼저 검사해, 틀리면 422와 이유를 돌려줍니다. DB 제약이 마지막 방어선이지만, 서비스가 친절한 오류를 주는 첫 방어선입니다. 값은 늘 바인딩으로 DB에 넘기므로, 경로에 인젝션을 넣어도(마지막 프리셋) 그냥 "없는 id"입니다.

      
Distrust every value from outside. The service checks format (id shaped like T9), range (health 0–100) and allowed values (one of four types) first and returns 422 with reasons if wrong. DB constraints are the last line of defence; the service is the first, giving friendly errors. Values always go to the DB by binding, so an injection in the path (the last preset) is just a nonexistent id.

    
③ 자원 모델링과 CRUD③ Resource modelling and CRUD

      
REST는 DB 표와 1:1은 아니지만 닮은 "자원"을 주소로 노출합니다: GET /assets(목록) · GET /assets/T1(하나) · POST(만들기, 201과 Location) · PATCH(일부 수정) · DELETE(204). 중요한 점은 내부 표 구조를 그대로 내보내지 않아도 된다는 것입니다. 표를 쪼개거나 합쳐도 자원 모양을 유지하면 클라이언트는 영향을 받지 않습니다.

      
REST exposes "resources" that resemble but need not match 1:1 the DB tables: GET /assets (list), GET /assets/T1 (one), POST (create, 201 and Location), PATCH (partial update), DELETE (204). The key point: you need not expose the internal table layout as is. Split or merge tables while keeping the resource shape and clients are unaffected.

    
④ 계약과 버전④ Contracts and versions

      
API는 클라이언트와의 약속(계약)입니다. 필드를 지우거나 뜻을 바꾸면 이미 배포된 앱이 깨지므로, 호환되는 변경(필드 추가)은 그대로 하고 깨는 변경은 /v2/…처럼 새 버전으로 냅니다. 계약은 OpenAPI 문서로 적어 코드와 문서 · 테스트를 맞춥니다. DB 쪽은 자유롭게 고치되, 그 변화를 서비스가 흡수합니다.

      
An API is a promise (contract) with its clients. Deleting a field or changing its meaning breaks apps already shipped, so compatible changes (adding fields) go ahead while breaking ones ship as a new version such as /v2/…. The contract is written as an OpenAPI document to keep code, docs and tests aligned. The DB side may change freely, with the service absorbing it.

    
⑤ 목록은 쪼개서: 페이지 나누기⑤ Lists in pieces: pagination

      
"전부 주기"는 데이터가 자라면 서비스와 DB를 모두 무너뜨립니다. 위 서비스는 limit에 상한(100)을 둡니다. 큰 목록은 커서 방식(?after=T4&limit=50)이 OFFSET보다 안정적입니다(앞에서 행이 추가돼도 흔들리지 않고 DB도 건너뛰기를 하지 않음).

      
"Return everything" topples both service and DB as data grows. The service above caps limit (100). For big lists a cursor style (?after=T4&limit=50) is steadier than OFFSET (rows added earlier do not shift it, and the DB does not skip rows).

    
⑥ 재시도와 멱등성⑥ Retries and idempotency

      
네트워크는 응답을 잃을 수 있어 클라이언트는 같은 요청을 다시 보냅니다. HTTP 페이지에서 본 대로 GET · PUT · DELETE는 멱등이지만 POST는 두 번 보내면 두 개가 생깁니다. 위 서비스는 id가 이미 있으면 409로 막지만, 일반적으로는 요청에 멱등 키(Idempotency-Key)를 실어 서비스가 중복을 걸러 내게 합니다.

      
Networks can lose responses, so clients resend. As the HTTP page showed, GET, PUT and DELETE are idempotent but POST sent twice makes two. The service above blocks an existing id with 409, but in general a request carries an idempotency key (Idempotency-Key) so the service can filter duplicates.

    
⑦ 서비스를 두는 값⑦ The cost of a service

      
왕복이 한 번 늘고(클라이언트 → 서비스 → DB), 만들고 운영할 코드가 늘며, 클라이언트가 필요한 모양마다 엔드포인트를 만들게 됩니다(화면이 바뀔 때마다 서비스 수정). 그 대가로 DB 계정 비노출 · 권한 통제 · 변화 흡수 · 캐시 · 사용량 제한을 얻습니다. 마지막 항목의 "화면마다 엔드포인트" 문제를 푸는 시도가 GraphQL입니다.

      
One more hop (client → service → DB), more code to build and run, and an endpoint per shape clients need (the service changes whenever a screen does). In return you gain hidden DB credentials, permission control, absorbed change, caching and rate limiting. GraphQL is an attempt to solve that last "an endpoint per screen" problem.

    
⑧ 이 모형이 생략한 것⑧ What this model leaves out

      
토큰은 이름만 다른 고정 문자열이고, 실제 인증(JWT 서명 검증 · OAuth · 세션 만료)을 하지 않습니다. 속도 제한 · 로그 · 감사 기록 · CORS · TLS · 동시 수정 충돌(낙관적 잠금 · ETag)도 넣지 않았습니다.

      
The tokens are fixed strings with names; no real authentication (JWT signature checks, OAuth, session expiry) takes place. Rate limits, logs, audit trails, CORS, TLS and concurrent-edit conflicts (optimistic locking, ETag) are also left out.
