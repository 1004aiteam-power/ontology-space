브라우저, 음악, 컴파일러가 동시에 도는 것처럼 보이지만, CPU 코어 하나는 한 순간에 하나의 프로세스만 실행합니다. 누구를 언제 얼마나 돌릴지 정하는 커널의 부품이 스케줄러입니다. 같은 작업 묶음을 일곱 가지 스케줄러로 돌려 보며, 무엇을 얻고 무엇을 잃는지 확인합니다.

A browser, music and a compiler seem to run at once, but one CPU core runs only one process at any instant. The part of the kernel that decides who runs, when and for how long is the scheduler. Run the same set of jobs through seven schedulers and see what each one gains and gives up.

코어 하나, 정수 단위 시간으로 돌리는 학습용 모형입니다 (실제 커널의 측정값이 아님). 교과서 예제의 값(FCFS 평균 대기 17, SJF 3, RR 5.67, SRTF 6.5)과 계산 규칙은 tests/os.test.mjs로 확인합니다. CFS의 nice 가중치는 리눅스 커널의 표를 그대로 썼습니다.

A teaching model with one core and whole time units, not measurements of a real kernel. The textbook values (FCFS average wait 17, SJF 3, RR 5.67, SRTF 6.5) and the rules are checked in tests/os.test.mjs. The CFS nice weights are the Linux kernel's own table.

같은 작업, 일곱 가지 스케줄러The same jobs, seven schedulers

프로세스 하나는 CPU 버스트 → I/O 대기 → CPU 버스트 → …를 되풀이합니다. CPU를 짧게 쓰고 자주 I/O를 기다리면 대화형(편집기, 웹 서버), 길게 쓰면 계산 위주(컴파일, 영상 변환)입니다. 표의 숫자를 바꿔 직접 작업을 만들 수도 있습니다.

A process repeats CPU burst → I/O wait → CPU burst → …. Short CPU use with frequent I/O waits is interactive (an editor, a web server); long CPU use is CPU-bound (compiling, video encoding). You can change the numbers in the table to make your own jobs.

반환시간 = 끝난 시각 − 도착 시각, 대기 = 준비 줄에서 기다린 시간의 합, 응답 = CPU 버스트마다 준비된 뒤 처음 CPU를 얻기까지 걸린 시간(사용자가 "반응이 빠르다"고 느끼는 것).

Turnaround = finish − arrival, waiting = total time spent in the ready queue, response = for each CPU burst, the time from becoming ready to first getting the CPU (what users feel as "snappy").

해 볼 것: ① "호위 효과"에서 FCFS의 평균 대기와 SJF를 비교. ② "계산 둘 + 대화형 둘"에서 FCFS · SJF와 RR · MLFQ · CFS의 가장 긴 응답 차이. ③ RR의 할당량을 1로 낮추고 문맥 전환 비용을 3으로 올려 CPU 이용률이 떨어지는 것. ④ "우선순위와 기아"에서 ⑤의 P1이 끝까지 밀리는 것과 ⑥ MLFQ의 끌어올림을 0(끔)으로 했을 때. ⑤ "nice 값 차이"에서 ⑦ CFS 간트 차트의 P1 : P2 실행 비율이 약 3 : 1(가중치 1024 : 335)인 것.

Try: ① under "Convoy effect", compare FCFS's average waiting time with SJF. ② Under "Two crunchers + two interactive", compare the worst response of FCFS and SJF with RR, MLFQ and CFS. ③ Drop RR's quantum to 1 and raise the switch cost to 3, and watch CPU use fall. ④ Under "Priority and starvation", see P1 pushed to the very end by ⑤, and what MLFQ does with the boost set to 0 (off). ⑤ Under "Different nice values", see that ⑦ CFS runs P1 and P2 at about 3 : 1 (weights 1024 : 335).

알아 둘 원리Principles worth knowing

① 프로세스와 스레드① Processes and threads

프로세스는 실행 중인 프로그램 하나로, 자기만의 주소 공간(메모리), 열린 파일, 권한을 가집니다. 커널은 프로세스마다 PCB(프로세스 제어 블록: 상태, 레지스터 값, 우선순위, 메모리 정보)를 둡니다. 스레드는 한 프로세스 안의 실행 흐름으로, 메모리를 함께 쓰고 자기 스택과 레지스터만 따로 가집니다. 리눅스 스케줄러는 둘을 구별하지 않고 모두 "태스크"로 다룹니다.

A process is one running program with its own address space (memory), open files and permissions. The kernel keeps a PCB (process control block: state, register values, priority, memory info) for each. A thread is a flow of execution inside a process; threads share memory and have only their own stack and registers. The Linux scheduler does not tell them apart: both are "tasks".

② 다섯 가지 상태② Five states

프로세스는 생성 → 준비 → 실행 → 종료를 거치고, 실행 중에 I/O를 요청하면 대기로 갔다가 I/O가 끝나면 다시 준비로 돌아옵니다. 대기 중인 프로세스는 CPU를 주어도 할 일이 없으니 스케줄러는 준비 줄만 봅니다. 위 그림에서 시각을 옮겨 가며 화살표가 어떻게 켜지는지 보세요.

A process goes new → ready → running → done; if it requests I/O while running it moves to waiting, and back to ready when the I/O completes. A waiting process has nothing to do even if given the CPU, so the scheduler looks only at the ready queue. Step through time in the diagram above and watch the arrows light up.

③ 문맥 전환에서 일어나는 일③ What happens in a context switch

타이머 인터럽트나 시스템 호출로 커널에 들어오면, 지금 프로세스의 레지스터를 PCB에 저장하고, 다음 프로세스의 레지스터와 페이지 테이블을 불러옵니다. 저장 · 복원 자체는 수 마이크로초지만, 캐시와 TLB가 식어 버려 그 뒤로도 한동안 느려집니다. 같은 프로세스의 스레드끼리는 주소 공간이 같아 조금 쌉니다. 할당량을 너무 작게 하면 안 되는 이유입니다(위 ③ 실험).

On entering the kernel through a timer interrupt or a system call, it saves the current process's registers into its PCB and loads the next process's registers and page table. The save and restore take a few microseconds, but caches and the TLB go cold, so things stay slower for a while. Switching between threads of the same process is a little cheaper because the address space stays. That is why the quantum must not be too small (experiment ③ above).

④ 선점과 비선점④ Preemptive and non-preemptive

비선점(FCFS, SJF)은 프로세스가 스스로 CPU를 내놓을 때(I/O 요청, 종료)까지 기다립니다. 선점은 타이머 인터럽트로 언제든 빼앗을 수 있습니다. 무한 루프를 도는 프로그램 하나가 컴퓨터 전체를 멈추지 않게 하려면 선점이 필요하고, 오늘날 범용 OS는 모두 선점형입니다. 대신 데이터를 고치는 도중에 빼앗길 수 있어 동기화(잠금)가 필요해집니다.

Non-preemptive schedulers (FCFS, SJF) wait until a process gives up the CPU itself (I/O request, exit). Preemptive ones can take it away at any moment with a timer interrupt. Preemption is what stops one program stuck in an infinite loop from freezing the whole machine, and every general-purpose OS today is preemptive. In return a process can be interrupted mid-update, which is why synchronisation (locks) is needed.

⑤ 모든 지표를 다 잘할 수는 없다⑤ No scheduler wins on every measure

평균 반환시간은 SJF · SRTF가 가장 짧지만 긴 작업이 굶을 수 있습니다. 응답은 RR · MLFQ · CFS가 좋지만 문맥 전환이 늘어 처리량이 조금 줄어듭니다. 서버는 처리량을, 데스크톱 · 휴대폰은 응답을, 실시간 장비(보호계전기, 로봇)는 마감 시각을 절대 넘기지 않는 것을 가장 중시합니다. 그래서 OS마다, 그리고 같은 OS 안에서도 작업 종류마다 다른 정책을 씁니다.

SJF and SRTF give the shortest average turnaround but can starve long jobs. RR, MLFQ and CFS give good response times but switch more, costing a little throughput. Servers care most about throughput, desktops and phones about response, and real-time devices (protection relays, robots) about never missing a deadline. So each OS, and even each class of task within one OS, uses a different policy.

⑥ 코어가 여러 개일 때⑥ With several cores

실제 컴퓨터는 코어마다 준비 줄을 따로 두고, 한쪽이 바쁘면 다른 코어로 작업을 옮깁니다(부하 분산). 하지만 옮기면 캐시를 잃으므로 가능하면 같은 코어에 두려 합니다(친화성, affinity). 서버 구조에서 스레드 수를 코어 수 근처로 두는 이유는 동시 접속 처리 페이지에서 볼 수 있습니다.

Real machines keep a ready queue per core and move tasks to another core when one is overloaded (load balancing). Moving loses the cache, though, so the scheduler prefers to keep a task where it was (affinity). Why servers keep the thread count near the core count is shown on the Handling many connections page.

⑦ 이 모형이 생략한 것⑦ What this model leaves out

코어는 하나뿐이고, 시간은 정수 단위로만 흐릅니다. I/O 장치가 몇 개든 동시에 처리된다고 보았고, 실시간 스케줄링 클래스(리눅스의 SCHED_FIFO · SCHED_DEADLINE), 에이징, EEVDF의 마감 시각 계산, 인터럽트 처리 시간은 넣지 않았습니다. CFS는 목표 지연 · 최소 단위 · 깨어날 때의 보정만 단순화해 넣었습니다.

One core only, and time moves in whole units. Any number of I/O operations are assumed to run in parallel, and real-time scheduling classes (Linux SCHED_FIFO · SCHED_DEADLINE), aging, EEVDF's deadline computation and interrupt handling time are left out. CFS is reduced to a target latency, a minimum slice and a wake-up adjustment.
