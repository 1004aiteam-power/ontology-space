ONTOLOGY vs. OOD

온톨로지 vs. 객체지향 설계Ontology vs. object-oriented design

뿌리는 같습니다. 세상을 클래스와 개체, 상속과 관계로 나눕니다.
목적이 다릅니다. 객체지향은 프로그램을 움직이게, 온톨로지는 의미를 함께 쓰게 합니다.

Same roots: both split the world into classes and individuals, inheritance and relations.
Different goals: OOD makes a program run; an ontology makes meaning shareable.

객체지향 설계(OOD, Object-Oriented Design)에 익숙한 개발자라면 온톨로지는 금방 익숙해 보입니다. 그런데 바로 그 익숙함 때문에 자주 틀리는 곳이 있습니다. 이 페이지는 같은 ESS 하나를 파이썬 클래스와 OWL 온톨로지로 나란히 적어 보고, 어디까지 같고 어디서부터 다른지, 그리고 둘을 어떻게 함께 쓰는지 정리합니다. 예는 이 사이트의 VPP 가상 전력시장과 pycim에서 가져왔습니다.

If you know object-oriented design (OOD), ontologies look familiar at once — and that very familiarity is where people slip. This page writes the same battery as a Python class and as an OWL ontology, side by side, shows where they agree and where they part, and how to use them together. Examples come from this site's VPP virtual market and pycim.

실제로 전력 분야의 표준 IEC CIM은 처음부터 UML 클래스 다이어그램(객체지향 설계 도구)으로 만들어졌고, 그것을 RDF로 옮긴 것이 CGMES입니다. 이 사이트의 pycim은 반대로 CIM을 다시 파이썬 클래스로 옮긴 것입니다. 두 세계는 이렇게 서로 오갑니다.

In fact the power-sector standard IEC CIM was built from the start as a UML class diagram (an OOD tool), and CGMES is that model carried into RDF. This site's pycim goes the other way, turning CIM back into Python classes. The two worlds travel in both directions.

같은 ESS를 두 가지로 적어 보기The same battery, written two ways

OOD 파이썬 클래스Python classes

from dataclasses import dataclass
from typing import Optional

@dataclass
class Feeder:
    name: str

@dataclass
class DER:
    der_id: str
    capacity_kw: float
    feeder: Feeder              # 참조

@dataclass
class BatterySystem(DER):       # 상속
    energy_kwh: Optional[float] = None
    soc: float = 0.5            # 충전 상태

    def discharge(self, kw, hours):   # 행동
        e = min(kw * hours, self.soc * self.energy_kwh)
        self.soc -= e / self.energy_kwh
        return e

ess = BatterySystem("ESS_001", 500.0,
                    Feeder("광주 D/L 2"), energy_kwh=2000.0)
print(ess.discharge(500, 1), round(ess.soc, 2))   # 500 0.25

Ontology OWL (Turtle)OWL (Turtle)

# 스키마 (TBox): 클래스와 속성
vpp:DER a owl:Class .
vpp:BatterySystem a owl:Class ;
    rdfs:subClassOf vpp:DER, cim:BatteryUnit .   # 상속 (여러 개)

vpp:capacityKW a owl:DatatypeProperty ;
    rdfs:domain vpp:DER ; rdfs:range xsd:decimal .
vpp:energyKWh a owl:DatatypeProperty ;
    rdfs:domain vpp:BatterySystem .

# 개체 (ABox): 사실
vpp:ESS_001 a vpp:BatterySystem ;
    vpp:capacityKW 500.0 ;
    vpp:energyKWh 2000.0 ;
    cim:Equipment.EquipmentContainer vpp:FD_GWANGJU_2 .

The Python side was run with Python 3 (output 500 0.25). The right side is trimmed from vpp-schema.ttl and vpp-market.ttl.

겉보기에는 거의 같습니다. 하지만 아래 일곱 가지에서 두 세계는 다르게 생각합니다.

They look almost identical. But on the seven points below, the two worlds think differently.

일곱 가지 차이Seven differences

①

목적: 움직이는 프로그램 vs. 함께 쓰는 의미Purpose: a running program vs. shared meaning

객체지향의 클래스는 프로그램 안에서 일을 하기 위해 존재합니다. 데이터와 함께 메서드(행동)를 묶고, 바깥에서 함부로 못 건드리게 캡슐화합니다. 온톨로지에는 메서드도 캡슐화도 없습니다. 모든 사실이 공개된 문장(트리플)이고, 목적은 여러 시스템과 사람이 같은 뜻으로 데이터를 읽고 묻는 것입니다.

An OO class exists to do work inside a program: it bundles data with methods and encapsulates them. An ontology has neither methods nor encapsulation. Every fact is a public statement (triple), and the goal is that many systems and people read and query the data with the same meaning.

그래서 "ESS가 방전하면 충전 상태가 줄어든다"는 계산은 코드에, "ESS_001은 배터리이고 광주 D/L 2에 붙어 있다"는 사실은 온톨로지에 두는 것이 자연스럽습니다.

So the computation "discharging lowers the state of charge" belongs in code, and the fact "ESS_001 is a battery on Gwangju D/L 2" belongs in the ontology.

②

닫힌 세계 vs. 열린 세계Closed world vs. open world

프로그램과 데이터베이스는 닫힌 세계 가정(CWA)을 씁니다. 적혀 있지 않으면 없는 것입니다. 온톨로지(OWL)는 열린 세계 가정(OWA)을 씁니다. 적혀 있지 않으면 모르는 것입니다. 누군가 다른 파일에서 그 사실을 더할 수 있기 때문입니다.

Programs and databases use the closed-world assumption (CWA): if it is not written, it is false. OWL uses the open-world assumption (OWA): if it is not written, it is unknown — someone may add it in another file.

이 차이 때문에, "필수 값이 빠졌는지" 같은 검사는 OWL이 아니라 닫힌 세계로 읽는 별도 도구(SHACL, 또는 이 사이트의 Cypher 형상검증)로 합니다. 그래프 DB(Neo4j)에 올린 뒤 Cypher로 묻는 순간에는 다시 닫힌 세계가 된다는 점도 기억해 두면 좋습니다.

That is why checks such as "is a required value missing?" are done not with OWL but with closed-world tools (SHACL, or this site's Cypher shape checks). Note also that once the data sits in a graph DB (Neo4j) and you query it with Cypher, you are back in a closed world.

③

클래스 소속: 태어날 때 고정 vs. 여럿 · 나중에 추론Membership: fixed at birth vs. many, inferred later

객체는 만들어질 때 클래스 하나가 정해지고 바뀌지 않습니다. 여러 성격을 가지려면 다중 상속이나 인터페이스를 미리 설계해야 합니다. 온톨로지의 개체는 여러 클래스에 동시에 속할 수 있고, 조건을 만족하면 추론기가 분류해 줍니다.

An object gets one class when created, and it never changes; to wear several hats you must design multiple inheritance or interfaces up front. An individual can belong to several classes at once, and a reasoner can classify it when it meets a definition.

# "1,000kW 이상인 배터리"를 정의 → 조건을 만족하는 개체는 자동으로 LargeBattery
vpp:LargeBattery owl:equivalentClass [ a owl:Class ;
    owl:intersectionOf ( vpp:BatterySystem
      [ a owl:Restriction ; owl:onProperty vpp:capacityKW ;
        owl:someValuesFrom [ a rdfs:Datatype ; owl:onDatatype xsd:decimal ;
                             owl:withRestrictions ( [ xsd:minInclusive 1000 ] ) ] ] ) ] .

이 사이트의 그래프 DB에서 ESS 노드가 :BatterySystem:DER:BatteryUnit 라벨을 한꺼번에 가진 것도 같은 생각입니다. 파이썬이라면 class BatterySystem(DER, BatteryUnit)처럼 다중 상속을 설계해야 같은 효과가 납니다.

The ESS nodes in this site's graph DB carrying :BatterySystem:DER:BatteryUnit at once is the same idea. In Python you would need to design multiple inheritance — class BatterySystem(DER, BatteryUnit) — to get the same effect.

④

속성이 클래스 밖에서 독립적으로 존재Properties live on their own, outside classes

객체지향에서 필드는 클래스 안에 선언됩니다. DER.capacity_kw와 Feeder.capacity_kw는 이름만 같은 별개의 것입니다. 온톨로지에서 속성은 그 자체로 정의되는 1급 요소라서, 여러 클래스가 같은 속성을 공유하고 속성끼리 관계도 가집니다.

In OOD a field is declared inside a class; DER.capacity_kw and Feeder.capacity_kw merely share a name. In an ontology a property is a first-class thing defined by itself: many classes share it, and properties relate to each other.

  • rdfs:subPropertyOf: "정격 용량"은 "용량"의 한 종류
  • owl:inverseOf: VPP가 DER을 aggregates하면, DER은 VPP에 memberOf (한쪽만 적어도 됨)
  • owl:TransitiveProperty: 변전소 → 선로 → 구간으로 feeds가 이어지면 변전소가 구간에도 공급한다고 추론 (고장 영향 분석의 im:feeds와 같은 생각)
  • rdfs:subPropertyOf: "rated capacity" is a kind of "capacity"
  • owl:inverseOf: if a VPP aggregates a DER, the DER is memberOf the VPP (state just one side)
  • owl:TransitiveProperty: substation → feeder → section via feeds lets you infer the substation feeds the section (the idea behind im:feeds in failure impact)

객체지향에서는 이런 규칙을 매번 코드로 짜야 합니다(역방향 참조를 양쪽에 유지하기, 재귀로 하류 찾기).

In OOD each of these rules has to be coded by hand (keeping back-references in sync, recursing to find downstream).

⑤

이름: 프로그램 안 vs. 전 세계Names: inside one program vs. worldwide

객체의 정체성은 메모리 주소나 DB의 id입니다. 프로그램 밖으로 나가면 의미가 없고, 다른 시스템의 같은 설비와 이으려면 매핑 표가 필요합니다. 온톨로지의 개체는 전역 IRI를 가지므로, 다른 파일 · 다른 회사의 데이터가 같은 IRI를 쓰면 그대로 합쳐집니다. VPP 데이터가 디지털 트윈의 변전소 IRI를 가리키기만 했는데 두 그래프가 이어진 것이 그 예입니다.

An object's identity is a memory address or a DB id: meaningless outside the program, so linking to the same asset in another system needs a mapping table. An individual has a global IRI, so data from other files or companies that use the same IRI simply merges. The VPP data pointing at the digital twin's substation IRIs — and the two graphs joining — is exactly that.

또 하나 다른 점은 OWL에 "이름이 다르면 다른 것" 가정이 없다는 것입니다(UNA 없음). SCADA 코드와 EAM 코드가 같은 변압기라면 owl:sameAs로 같다고 말할 수 있습니다. pycim의 SCADA · EAM · GIS 코드 ↔ mRID 매핑 표가 객체지향 쪽에서 같은 문제를 푼 방식입니다.

Another difference: OWL has no "different names mean different things" assumption (no UNA). If a SCADA code and an EAM code name the same transformer, owl:sameAs says so. The SCADA/EAM/GIS ↔ mRID mapping table in pycim is how the OOD side solves the same problem.

⑥

스키마 변경: 코드 수정 · 이관 vs. 문장 추가Schema change: refactor and migrate vs. add statements

클래스에 필드를 하나 더하려면 코드를 고치고, 다시 배포하고, 저장된 데이터를 이관해야 합니다. 온톨로지는 스키마도 데이터와 똑같은 트리플이라 새 클래스 · 속성 · 상위 클래스를 문장으로 더하기만 하면 됩니다. 기존 데이터는 그대로 두고 새 뜻을 덧붙일 수 있습니다(예: 나중에 vpp:BatterySystem ⊑ ex:FlexibleResource를 한 줄 추가).

Adding a field to a class means editing code, redeploying and migrating stored data. In an ontology the schema is triples just like the data, so you only add statements — a new class, property or superclass — and leave existing data untouched (e.g. later add one line vpp:BatterySystem ⊑ ex:FlexibleResource).

그 대가로, 스키마가 너무 쉽게 바뀌므로 누가 · 왜 바꿨는지 기록하는 습관이 중요합니다. 이 사이트의 온톨로지 설계실이 설계 결정(D1, D2…)을 남기는 이유입니다.

The price: because the schema changes so easily, recording who changed what and why matters. That is why this site's Design Studio keeps design decisions (D1, D2…).

⑦

domain · range는 "검사"가 아니라 "추론" (가장 흔한 실수)domain and range infer — they do not check (the most common mistake)

객체지향의 타입 선언 feeder: Feeder는 검사입니다. 다른 타입을 넣으면 오류가 납니다(정적 타입 언어라면 컴파일 단계에서). 개발자는 rdfs:range도 그렇게 동작하리라 기대하지만, RDFS · OWL에서 range는 "그러니 이것은 그 클래스다"라고 추론합니다.

The OO declaration feeder: Feeder is a check: put in the wrong type and you get an error (at compile time in a static language). Developers expect rdfs:range to behave the same, but in RDFS/OWL a range infers "therefore this is of that class".

vpp:aggregates rdfs:range vpp:DER .
vpp:VPP02 vpp:aggregates vpp:FD_GWANGJU_2 .     # 실수로 배전선로를 넣음

# OOD라면:    타입 오류
# OWL이라면:  "FD_GWANGJU_2는 DER이다"라고 결론 (오류 아님!)

이 때문에 "잘못된 데이터를 막는 일"은 반드시 별도의 검증 규칙(SHACL, 형상검증 질의)으로 해야 합니다. 이 사이트의 테스트가 "모든 DER은 정확히 하나의 VPP와 하나의 선로를 가진다"를 Cypher로 따로 확인하는 것도 그래서입니다.

So "keeping bad data out" must be done with separate validation rules (SHACL, shape-check queries). That is why this site's tests check "every DER has exactly one VPP and one feeder" separately with Cypher.

둘을 함께 쓰는 법Using them together

둘은 경쟁 관계가 아닙니다. 실무에서는 온톨로지로 뜻을 정하고, 객체지향 코드로 계산합니다. 이 사이트에서도 그렇게 했습니다.

They are not rivals. In practice you fix the meaning with an ontology and compute with OO code — and so does this site.

① 온톨로지 → 클래스① Ontology → classes

Generate Python classes from a standard ontology (CIM) and compute with them — how pycim runs load flow and OpenDSS export.

계산 · 시뮬레이션 결과를 트리플로 내보내 다른 데이터와 합침. VPP 가상 시장, 배전공사 안전이 시뮬레이션 코드를 온톨로지로 옮긴 방식.

온톨로지를 클래스로 옮길 때의 요령Tips for mapping an ontology to classes

  • IRI를 필드로 남기기: 객체마다 mrid · iri 필드를 두어 프로그램 밖에서도 같은 개체로 찾을 수 있게 함 (pycim의 mRID)
  • 모르는 값은 Optional: 열린 세계에서 온 데이터는 언제든 비어 있을 수 있음
  • 다중 분류는 믹스인이나 태그로: 클래스 하나에 억지로 넣지 말고 roles 집합이나 믹스인 클래스로
  • 관계는 한쪽만 저장하고 역방향은 계산: owl:inverseOf처럼 양쪽을 따로 저장하면 어긋나기 쉬움
  • 행동은 코드에, 사실은 그래프에: 메서드를 온톨로지에 넣으려 하지 말 것
  • Keep the IRI as a field: give every object an mrid/iri so it can be found outside the program (pycim's mRID)
  • Unknown values are Optional: data from an open world can always be missing
  • Multiple classification via mixins or tags: don't force one class — use a roles set or mixins
  • Store a relation on one side, compute the inverse: storing both like owl:inverseOf drifts out of sync
  • Behaviour in code, facts in the graph: don't try to put methods into the ontology
💡 쉽게 말하면In plain words

객체지향 클래스는 한 프로그램의 설계도이고, 온톨로지는 여러 프로그램이 함께 보는 사전입니다. 설계도는 정확하게 움직이도록 엄격하고, 사전은 계속 새 뜻이 붙도록 열려 있습니다. 같은 단어(클래스 · 상속 · 관계)를 쓰지만, "적혀 있지 않은 것"과 "타입이 어긋난 것"을 대하는 태도가 정반대라는 것만 기억하면 대부분의 혼란을 피할 수 있습니다.

An OO class is one program's blueprint; an ontology is a dictionary many programs read together. The blueprint is strict so things run exactly; the dictionary stays open so new meaning can be added. They share words — class, inheritance, relation — but treat "what is not written" and "what has the wrong type" in opposite ways. Remember that and most confusion goes away.
