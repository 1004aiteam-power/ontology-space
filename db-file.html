데이터베이스 접근 · 직접 접근DATABASE ACCESS · DIRECT

📀 서버 없이 파일을 직접:
페이지 · 인덱스 · WALNo server, just the file:
pages, indexes and the WAL

데이터베이스에 가장 가까운 접근은 데이터 파일을 내 프로그램이 직접 여는 것입니다. 표가 파일 속에서 어떤 바이트로 놓이는지, 한 행을 찾는 데 페이지를 몇 개 읽는지, 쓰는 도중 전원이 나가면 무슨 일이 생기는지를 작은 저장 엔진으로 직접 봅니다.

The access closest to a database is your own program opening the data file. With a small storage engine you can see what bytes a table becomes in a file, how many pages it takes to find one row, and what happens if the power fails mid-write.

아래 엔진은 설명용 장난감입니다(페이지 128바이트, 마디당 키 3개). 레코드 인코딩 · 페이지 · B+트리 · WAL 규칙은 tests/db.test.mjs로 확인합니다. 실제 엔진은 가변 길이 · 삭제 · 노드 분할 · 체크포인트까지 다룹니다.

The engine below is a teaching toy (128-byte pages, 3 keys per node). The record encoding, pages, B+tree and WAL rules are checked in tests/db.test.mjs. Real engines also handle variable lengths, deletes, node splits and checkpoints.

LAB 1

표는 파일 속에서 이렇게 생겼다What a table looks like inside a file

설비 12행을 128바이트짜리 페이지에 차례로 채웠습니다(실제 DB는 보통 8KB 안팎). 페이지 앞쪽에는 머리(레코드 수 · 빈 공간 끝)와 슬롯 목록(각 레코드의 위치와 길이)이 있고, 레코드는 페이지 끝에서 앞으로 쌓입니다. 아래 표에서 행을 고르면 그 행의 바이트가 어디 있는지 표시됩니다.

The 12 asset rows are packed into 128-byte pages (real DBs use about 8 KB). The front of each page holds a header (record count, end of free space) and a slot list (where each record is and how long); records are stacked from the end toward the front. Pick a row below to see where its bytes live.

LAB 2

찾기: 전체 훑기 vs B+트리 인덱스Finding: full scan vs a B+tree index

id로 한 행을 찾아 봅니다. 인덱스가 없으면 모든 페이지를 읽어야 하고, B+트리가 있으면 루트에서 잎까지 마디 몇 개만 읽고 데이터 페이지 1개를 엽니다. 건전도처럼 인덱스가 없는 열로 찾으면 다시 전체 훑기입니다.

Find one row by id. Without an index every page must be read; with a B+tree you read a few nodes from root to leaf and then one data page. Searching an unindexed column such as health falls back to a full scan.

인덱스 없이: 전체 훑기No index: full scan

B+트리 인덱스 (마디당 키 3개)B+tree index (3 keys per node)

행이 많아지면As rows grow

페이지당 80행, 한 마디의 자식 200개로 가정한 계산입니다. 행이 10억이어도 인덱스는 마디 4~5개만 읽습니다. 전체 훑기는 행 수에 비례해 늘지만 인덱스는 로그로만 늘어납니다.

Calculated with 80 rows per page and 200 children per node. Even at a billion rows the index reads only about four or five nodes. A full scan grows with the row count; the index grows only logarithmically.

LAB 3

쓰는 도중 전원이 나가면: 쓰기 전 기록(WAL)Power loss mid-write: the write-ahead log (WAL)

설비 T2를 Sub-A 페이지에서 Sub-B 페이지로 옮기려면 페이지 두 개를 고쳐야 합니다. 둘 사이에서 전원이 나가면? WAL은 "이렇게 하겠다 + 확정"을 안전한 로그에 먼저 적고 나서 페이지를 고칩니다. 다시 켰을 때 로그에 확정이 있으면 끝까지 다시 해 주고(redo), 없으면 없던 일로 합니다.

Moving asset T2 from a Sub-A page to a Sub-B page means changing two pages. What if the power fails between them? A WAL writes "I will do this + commit" to a safe log first, then changes the pages. On restart, a commit in the log means finishing the job (redo); no commit means pretending it never happened.

알아 둘 원리Principles worth knowing

① 파일도 DB다: 가장 낮은 계단① A file is a database too: the lowest rung

가장 직접적인 접근은 데이터 파일을 내 프로그램이 직접 여는 것입니다. CSV · JSON을 읽는 것도, SQLite처럼 라이브러리 형태의 엔진으로 .db 파일 하나를 여는 것도 여기에 속합니다. 서버도 계정도 네트워크도 없고, 호출은 그냥 함수입니다. 설정 · 로컬 앱 · 테스트 · 모바일 앱(휴대폰의 연락처 · 사진 앱 대부분)이 이렇게 씁니다.

The most direct access is your own program opening the data file. Reading CSV or JSON counts, and so does opening a single .db file with a library-style engine such as SQLite. No server, no account, no network; a call is just a function. Settings, local apps, tests and mobile apps (most contact and photo apps) work this way.

② 페이지: 읽고 쓰는 최소 단위② Pages: the smallest unit read and written

디스크는 바이트가 아니라 블록 단위로 읽고 씁니다. 그래서 DB도 데이터를 같은 크기의 페이지로 나눠 두고, 한 줄을 읽으려 해도 그 줄이 든 페이지 전체를 메모리(버퍼 캐시)로 가져옵니다. 위 LAB 1의 슬롯 구조가 그 한 칸입니다. "몇 페이지를 읽었나"가 DB 성능의 기본 단위이고, 쿼리 계획(EXPLAIN)이 보여 주는 것도 대개 이것입니다.

Disks read and write in blocks, not bytes. So a DB splits data into equal-size pages and, to read one row, pulls the whole page holding it into memory (the buffer cache). The slot layout in Lab 1 is one such page. "How many pages did it read" is the basic unit of DB performance, and what a query plan (EXPLAIN) mostly shows.

③ 인덱스: 책의 찾아보기③ Index: the back-of-book index

인덱스는 키 → 레코드 위치를 정렬해 둔 별도의 구조이고, 가장 흔한 것이 B+트리입니다. 한 마디에 키를 수백 개 담아 트리가 아주 얕습니다(LAB 2). 대가가 있습니다: 쓸 때마다 인덱스도 고쳐야 해서 쓰기가 느려지고 공간을 더 쓰므로, 자주 찾는 열에만 만듭니다. 쓰기가 압도적으로 많은 DB는 LSM 트리(메모리에 모았다가 정렬된 파일로 합침)를 쓰기도 합니다.

An index is a separate sorted key → record location structure; the most common is the B+tree. Each node holds hundreds of keys, so the tree is very shallow (Lab 2). It has a cost: every write must update the index too, so writes slow down and space grows; build them only on columns you search often. Write-heavy DBs sometimes use an LSM tree (collect in memory, merge into sorted files).

④ WAL: 전원이 나가도 약속을 지킨다④ WAL: keeping the promise through power loss

"확정한 것은 남는다(지속성)"와 "전부 아니면 전무(원자성)"는 WAL이 지킵니다. 순서가 핵심입니다: 로그를 먼저 디스크에 확실히 쓴 뒤 확정 응답을 주고, 데이터 페이지는 나중에 천천히 씁니다. 로그는 순서대로 이어 쓰기만 하므로 빠릅니다. SQLite · PostgreSQL · MySQL이 모두 이 방식이고, 같은 로그를 다른 서버에 흘려 보내면 복제(replication)가 됩니다.

WAL upholds "what is committed stays (durability)" and "all or nothing (atomicity)". Order is the key: write the log to disk for certain first, then confirm, and write data pages later at leisure. The log is append-only, so it is fast. SQLite, PostgreSQL and MySQL all do this, and streaming the same log to another server gives replication.

⑤ 임베디드의 한계: 쓰는 쪽은 하나⑤ The embedded limit: one writer

파일을 여러 프로세스가 동시에 고치면 서로의 페이지를 덮어씁니다. SQLite는 이를 파일 잠금으로 막아 한 번에 한 쓰기만 허용합니다. 읽기는 여럿이 가능합니다. 그래서 서버 한 대 · 쓰기가 많지 않은 곳에는 훌륭하지만, 여러 서버가 같은 DB를 함께 쓰는 구조에는 맞지 않습니다. 이때 DB를 별도 서버로 떼어 내는 것이 다음 계단입니다.

When several processes edit one file at once they overwrite each other's pages. SQLite prevents this with file locks, allowing one write at a time (many reads are fine). It is excellent for one server or light writes, but unsuited to several servers sharing one DB. Splitting the DB out as its own server is the next rung.

⑥ 직접 파일을 열어도 되는 때, 안 되는 때⑥ When opening the file yourself is fine, and when it is not

괜찮은 때: 단일 사용자 앱, 분석용으로 내려받은 파일(Parquet · SQLite), 테스트, 엣지 기기. 피할 때: 다른 프로그램이 같은 파일을 쓰는데 엔진을 거치지 않고 바이트를 직접 읽고 쓰는 경우(형식을 모르면 깨뜨립니다), 네트워크 공유 폴더 위의 DB 파일(잠금이 믿을 수 없음). 규칙은 간단합니다: 파일 형식은 엔진만 만진다.

Fine: single-user apps, files downloaded for analysis (Parquet, SQLite), tests, edge devices. Avoid: reading and writing bytes directly without the engine while another program uses the same file (you will break a format you do not know), and DB files on a network share (locking is unreliable). The rule is simple: only the engine touches the file format.

import sqlite3                      # 파이썬에 들어 있는 임베디드 엔진 / the embedded engine in Python

con = sqlite3.connect("assets.db")  # 서버 접속이 아니라 "파일 열기" / opening a file, not connecting to a server
for row in con.execute("SELECT id, health FROM assets WHERE health >= ?", (90,)):
    print(row)
