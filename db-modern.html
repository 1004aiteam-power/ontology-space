Earlier rungs were roads by which human-written code reached the DB. Recently tools generate APIs automatically, serverless environments query over HTTP, and AI agents have appeared as a new kind of caller. The roads are new, but the questions stay the same: who holds the DB account, and where are permissions enforced.

실습은 이 페이지 안의 작은 SQL 엔진으로 실제 실행하지만, 자연어 → SQL 부분은 LLM이 아니라 규칙으로 흉내 낸 대역입니다. 변환 · 안전 점검 규칙은 tests/db.test.mjs로 확인합니다. 제품 설명은 정확하지 않을 수 있으니 공식 문서를 확인하세요.

The labs really run on the small SQL engine in this page, but the natural language → SQL part is a rule-based stand-in, not an LLM. tests/db.test.mjs checks the translation and safety rules. Product descriptions may be inaccurate; check the official documents.

LAB 1

표를 만들면 API가 생긴다: 자동 생성 APIMake a table and an API appears: auto-generated APIs

PostgREST · Supabase · Hasura 같은 도구는 DB의 표 구조를 읽어 REST(또는 GraphQL) API를 자동으로 만들어 줍니다. 서비스 코드를 짜지 않고, 주소의 type=eq.transformer 같은 조건이 SQL로 번역됩니다. 주소를 고쳐 보내 보세요.

Tools such as PostgREST, Supabase and Hasura read the DB's table structure and generate a REST (or GraphQL) API automatically. No service code is written; conditions in the address, like type=eq.transformer, are translated to SQL. Edit the address and send it.

LAB 2

  
AI 에이전트가 DB를 쓸 때: 초안 → 점검 → 실행When an AI agent uses the DB: draft → check → run

  
에이전트는 자연어 질문을 받아 SQL 초안을 만들고, 도구(MCP 등)를 통해 실행합니다. 초안은 틀리거나, 프롬프트 인젝션에 속아 위험할 수 있으므로 실행 전에 점검합니다: 문장 하나 · SELECT만 · 허용된 표만 · 행 수 상한. 질문을 골라 보세요. (초안을 만드는 부분은 LLM이 아니라 규칙으로 흉내 낸 대역입니다.)

  
An agent takes a natural-language question, writes a SQL draft and runs it through a tool (MCP and the like). A draft can be wrong, or dangerous if prompt injection fooled the agent, so it is checked before running: one statement, SELECT only, allow-listed tables, a row cap. Pick a question. (The draft step is a rule-based stand-in, not an LLM.)

알아 둘 원리Principles worth knowing

  

    
① 서비스 코드를 줄이는 방향① Toward writing less service code

      
앞 페이지의 REST 서비스는 CRUD 코드가 거의 같은 모양으로 반복됩니다. BaaS(Backend as a Service: Supabase · Firebase 등)와 자동 생성 API는 그 반복을 도구가 맡습니다. 표를 만들면 API · 인증 · 파일 저장 · 실시간 구독이 따라옵니다. 작은 팀이 빨리 만들기에 좋고, 업무 규칙이 복잡해지면 그 부분만 직접 만든 서비스(함수)로 보완합니다.

      
The REST service of the previous page repeats near-identical CRUD code. BaaS (Backend as a Service: Supabase, Firebase and the like) and auto-generated APIs hand that repetition to a tool. Make a table and the API, authentication, file storage and live subscriptions follow. Good for a small team building fast; when business rules grow complex, only that part is supplemented by your own service (function).

    
② 권한은 DB 안으로: 행 단위 보안(RLS)② Permissions move into the DB: row-level security (RLS)

      
브라우저가 API를 거쳐 DB에 거의 직접 닿으므로 "누가 어느 행을 보는가"를 DB가 직접 강제해야 합니다. PostgreSQL의 RLS는 표마다 USING (owner = current_user) 같은 정책을 걸어, 질의가 어떤 경로로 오든 보이는 행을 걸러 냅니다. 이는 앞 페이지의 "서비스가 권한을 확인한다"를 DB 쪽으로 옮긴 것입니다. 정책을 빠뜨린 표는 곧바로 노출되므로, 새 표는 기본으로 닫고 시작하세요.

      
Because the browser reaches the DB almost directly through the API, the DB itself must enforce "who sees which rows". PostgreSQL RLS attaches policies such as USING (owner = current_user) to each table, filtering visible rows however the query arrived. It is the previous page's "the service checks permissions" moved into the DB. A table without a policy is exposed at once, so start new tables closed by default.

    
③ 서버리스 DB와 HTTP로 묻기③ Serverless DBs and querying over HTTP

      
서버리스 환경(함수가 요청 때만 잠깐 떴다 사라짐)은 TCP 연결과 풀을 오래 유지하기 어렵고, 연결 수가 순식간에 폭증합니다. 그래서 HTTP · WebSocket으로 질의하는 드라이버(Neon · Turso/libSQL · Cloudflare D1 · AWS Aurora Data API 등)와 앞단 연결 중계가 나왔습니다. 호출은 여전히 SQL이지만 통로가 소켓 프로토콜에서 HTTP 요청으로 바뀐 것입니다. 연결을 맺는 대신 요청마다 묻고 끝내므로, 함수가 늘어도 DB 연결 수가 폭증하지 않습니다.

      
Serverless environments (functions that appear for a request and vanish) cannot keep TCP connections and pools alive, and connection counts spike instantly. Hence drivers that query over HTTP or WebSocket (Neon, Turso/libSQL, Cloudflare D1, AWS Aurora Data API and others) plus connection proxies in front. The call is still SQL, but the channel changed from a socket protocol to an HTTP request. Asking per request instead of holding a connection keeps connection counts from spiking as functions multiply.

    
④ 엣지와 복제본: 가까운 곳에서 읽기④ Edge and replicas: reading nearby

      
사용자가 전 세계에 있으면 DB가 한 곳에만 있을 때 먼 사용자는 왕복이 깁니다. 읽기 복제본을 여러 지역에 두거나 엣지에 캐시를 두어 읽기는 가까운 곳, 쓰기는 한 곳으로 처리합니다. 대가는 복제 지연으로 잠깐 낡은 값을 읽을 수 있다는 점입니다(자기가 방금 쓴 값은 쓰기 쪽에서 읽도록 라우팅하는 식으로 보완).

      
With users worldwide, one DB location means long round trips for distant users. Place read replicas in several regions or caches at the edge to read nearby and write in one place. The price is replication lag that can briefly serve stale values (mitigated by routing reads of something you just wrote to the write side).

    
⑤ 변경을 구독한다: CDC⑤ Subscribing to changes: CDC

      
"가져오기(요청-응답)" 대신 DB의 변경 기록(WAL)을 흘려 받는 방식입니다(WAL 실험의 그 로그). Debezium 같은 도구가 변경을 이벤트로 바꿔 메시지 큐 · 검색 엔진 · 캐시 · 분석 DB로 보냅니다. 실시간 화면 갱신, 다른 시스템과 동기화, 감사 기록에 쓰입니다. 접근의 방향이 "내가 묻는다"에서 "바뀌면 알려 준다"로 뒤집힌 셈입니다.

      
Instead of "fetching (request-response)" you receive the DB's change log (WAL) as a stream (the log from the WAL lab). Tools like Debezium turn changes into events sent to message queues, search engines, caches and analytics DBs, used for live screen updates, syncing other systems and audit trails. Access flips from "I ask" to "tell me when it changes".

    
⑥ AI 에이전트의 접근: 새 호출자⑥ AI agents: a new kind of caller

      
에이전트는 사람처럼 그때그때 묻고, 사람과 달리 빠르고 대량으로, 속을 수 있습니다(문서 안의 숨은 지시에 따라 행동하는 프롬프트 인젝션). 그래서 DB 계정을 주지 않고 좁은 도구(MCP 서버)를 주며, 도구 쪽에서 읽기 전용 · 허용 표 · 행 상한 · 감사 로그를 강제합니다(LAB 2). 에이전트가 쓰기를 해야 한다면 도구를 잘게 나눠(set_health(id, value)) 범위를 좁히고 사람 승인 단계를 둡니다.

      
An agent asks on the fly like a person but unlike a person is fast, high-volume and can be fooled (prompt injection: acting on hidden instructions inside a document). So do not give it a DB account; give it a narrow tool (an MCP server) that enforces read-only, allow-listed tables, a row cap and audit logs (Lab 2). If an agent must write, split tools finely (set_health(id, value)) to narrow the scope and add a human approval step.

    
⑦ 의미로 찾기: 벡터와 GraphRAG⑦ Finding by meaning: vectors and GraphRAG

      
문서를 질문과 의미가 가까운 순으로 찾는 벡터 검색(RAG)이 AI 응용의 기본 접근이 되었고, 관계를 따라가며 답을 모으는 GraphRAG가 그 위에 얹힙니다. 이 사이트의 AI × 온톨로지 시연이 LLM만 · 문서 검색 · GraphRAG를 비교하며, 자연어 질문이 Cypher로 바뀌어 그래프에서 답을 얻는 과정도 거기 있습니다. 앞의 지도에서 본 벡터 · 그래프 모양이 이렇게 접근의 새 통로가 됩니다.

      
Vector search (RAG), which finds documents closest in meaning to the question, has become the basic access path in AI applications, with GraphRAG, collecting answers by following relationships, layered on top. This site's AI × ontology demo compares LLM alone, document search and GraphRAG, including natural-language questions becoming Cypher to get answers from a graph. The vector and graph shapes of the map thus become new channels of access.

    
⑧ 이 모형이 생략한 것⑧ What this model leaves out

      
주소 번역은 PostgREST의 일부 문법(select · 필터 · order · limit · 한 단계 포함)만 흉내 냈고 RLS는 없습니다. 자연어 → SQL은 LLM이 아니라 키워드 규칙이며, 실제 에이전트는 스키마 설명을 읽고 훨씬 다양하게(그리고 틀리게) 씁니다. 점검 규칙도 한 예일 뿐 실제로는 열 단위 제한 · 비용 한도 · 감사까지 둡니다.

      
The address translation mimics only part of PostgREST's syntax (select, filters, order, limit, one level of embedding) and has no RLS. Natural language → SQL is keyword rules, not an LLM; a real agent reads schema descriptions and writes far more varied (and wrong) SQL. The check rules are only an example; real ones add column limits, cost caps and auditing.
