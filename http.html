HTTPThe text that travels over a socket:
HTTP

웹 브라우저와 서버가 주고받는 것은 사실 줄 단위로 적은 글자입니다. 첫 줄에 "무엇을 달라", 그 아래 몇 줄의 부가 정보(헤더), 빈 줄, 그리고 본문. 요청을 직접 만들어 보내고, 서버가 되돌린 응답을 줄 끝 문자까지 그대로 읽어 봅니다.

What a web browser and server exchange is really text written in lines: a first line saying "give me this", a few lines of extra information (headers), a blank line, then the body. Build a request yourself, send it, and read the server's reply exactly as it is, down to the line endings.

서버는 이 페이지 안의 데모용 가짜입니다 (실제 네트워크 없음). 메시지를 만들고 해석하는 규칙과 응답 코드는 tests/net.test.mjs로 확인합니다. 시간 비교는 대역폭 · 혼잡 제어 · 캐시를 뺀 단순 모형입니다.

The server is a demo fake inside this page (no real network). The rules for building and reading messages and the response codes are checked in tests/net.test.mjs. The timing comparison is a simple model without bandwidth, congestion control or caching.

알아 둘 원리Principles worth knowing

  

    
① 글자로 된 요청-응답① Text, request and response

      
HTTP/1.x는 사람이 읽을 수 있는 글자입니다: 시작 줄(GET / HTTP/1.1) + 헤더 + 빈 줄 + 본문. 서버는 요청에 응답하기만 하고, 먼저 말을 걸지 않습니다. 그리고 각 요청은 서로 독립이라 서버는 이전 요청을 기억하지 않습니다(stateless). 로그인 상태를 유지하려면 쿠키 같은 헤더에 신분표를 실어 매번 보냅니다.

      
HTTP/1.x is human-readable text: a start line (GET / HTTP/1.1), headers, a blank line and a body. The server only answers; it never speaks first. Each request is independent, so the server remembers nothing of earlier ones (stateless). To stay logged in, a token such as a cookie rides in a header on every request.

    
② 메서드: 하려는 일② Methods: the intended action

      
GET은 읽기만 하고, HEAD는 본문 없이 헤더만 받습니다. POST는 새 것을 만들거나 처리를 시키고, PUT은 통째로 바꾸며, DELETE는 지웁니다. GET · PUT · DELETE는 여러 번 보내도 결과가 같습니다(멱등). 그래서 응답이 늦어 다시 보내도 안전합니다. POST는 멱등이 아니어서 두 번 보내면 두 개가 생길 수 있습니다.

      
GET only reads and HEAD gets headers without a body. POST creates or triggers processing, PUT replaces wholesale and DELETE removes. GET, PUT and DELETE are idempotent: sending them several times has the same result, so a retry after a slow response is safe. POST is not, and two sends may create two things.

    
③ 상태 코드: 첫 숫자만 봐도③ Status codes: the first digit says a lot

      
2xx 성공, 3xx 다른 곳을 보라(301 영구 이동, 304 바뀐 것 없음), 4xx 요청한 쪽의 잘못(400 형식, 401 인증, 403 권한, 404 없음, 405 허용 안 된 메서드), 5xx 서버의 잘못(500 내부 오류, 503 일시 불능). 위 프리셋으로 하나씩 만나 보세요. 클라이언트는 4xx를 그대로 다시 보내도 소용없고, 5xx나 네트워크 오류는 잠시 뒤 재시도할 만하다는 식으로 대응이 달라집니다.

      
2xx success, 3xx look elsewhere (301 moved, 304 unchanged), 4xx the caller's fault (400 malformed, 401 authentication, 403 permission, 404 missing, 405 method not allowed), 5xx the server's fault (500 internal error, 503 unavailable). Meet them one by one with the presets above. Clients react differently: resending a 4xx as-is is pointless, while a 5xx or network error is worth retrying later.

    
④ 헤더가 하는 일④ What headers do

      
Host: 한 IP의 서버가 여러 사이트를 맡을 때 어느 사이트인지 가리킵니다(HTTP/1.1 필수). Content-Type · Content-Length: 본문이 무엇이고 몇 바이트인지, 곧 TCP 바이트 스트림에서 메시지의 경계를 정하는 규칙입니다. 길이를 모를 때는 Transfer-Encoding: chunked로 조각마다 길이를 적어 보냅니다. ETag · If-None-Match · Cache-Control: 캐시. 위 "조건부 요청"이 바로 304를 받는 경우입니다.

      
Host names the site when one IP serves many (required in HTTP/1.1). Content-Type and Content-Length say what the body is and how many bytes — the rule that sets message boundaries in a TCP byte stream. When the length is unknown, Transfer-Encoding: chunked writes a length before each chunk. ETag, If-None-Match, Cache-Control handle caching; the "Conditional" preset above is a 304.

    
⑤ 연결 재사용과 줄 서기 문제⑤ Reusing connections and the queue problem

      
HTTP/1.0은 요청마다 TCP 연결을 새로 열고 닫아, 자원 하나에도 handshake 왕복이 붙었습니다. HTTP/1.1은 keep-alive가 기본이라 연결을 이어 쓰지만, 한 연결에서는 앞 응답이 끝나야 다음 응답이 갈 수 있어(head-of-line blocking) 브라우저가 서버마다 연결을 6개쯤 병렬로 엽니다. 위 비교에서 "연결 수" 막대를 움직여 보세요.

      
HTTP/1.0 opened and closed a TCP connection per request, adding a handshake round trip even for one resource. HTTP/1.1 makes keep-alive the default and reuses connections, but on one connection the next response must wait for the previous one (head-of-line blocking), so browsers open about six in parallel per server. Move the "connections" slider in the comparison above.

    
⑥ HTTP/2와 HTTP/3⑥ HTTP/2 and HTTP/3

      
HTTP/2는 글자 대신 이진 프레임을 쓰고, 한 연결 안에서 여러 요청을 스트림으로 동시에 보내며(다중화), 헤더를 압축합니다. 그러나 밑의 TCP가 패킷 하나를 잃으면 모든 스트림이 같이 멈춥니다. HTTP/3는 TCP 대신 UDP 위의 QUIC을 써서 스트림별로 손실을 따로 복구하고, 연결 준비와 TLS 1.3을 한 번의 왕복으로 합치며, 접속한 적 있는 서버에는 0-RTT로 바로 요청합니다. 의미(메서드 · 상태 코드 · 헤더)는 세 버전이 같고 전달 방식만 바뀝니다.

      
HTTP/2 uses binary frames instead of text, sends many requests concurrently as streams on one connection (multiplexing) and compresses headers. But if the TCP underneath loses a packet, every stream stalls together. HTTP/3 runs over QUIC on UDP: it recovers loss per stream, merges connection setup and TLS 1.3 into one round trip, and may send 0-RTT to a server seen before. The meaning (methods, status codes, headers) is the same in all three; only the delivery changes.

    
⑦ HTTPS: 사이에 낀 TLS⑦ HTTPS: TLS in the middle

      
HTTPS는 HTTP 메시지를 바꾸지 않습니다. 소켓과 HTTP 사이에 TLS가 끼어 메시지를 암호화할 뿐입니다. 처음 연결할 때 TCP handshake 뒤에 TLS 협상(1.3은 1왕복, 1.2는 2왕복)이 더해지고, 서버 신원은 인증서로 확인합니다. 위 시간 비교에서 암호화 선택을 바꿔 보면 그 비용이 보입니다. 이 페이지가 보여 주는 글자는 암호화하기 전의 모습입니다.

      
HTTPS does not change the HTTP message. TLS sits between the socket and HTTP and merely encrypts it. A fresh connection adds a TLS negotiation after the TCP handshake (one round trip in 1.3, two in 1.2) and the server's identity is checked with a certificate. Change the encryption option in the timing comparison to see that cost. The text shown on this page is the message before encryption.

    
⑧ 이 모형이 생략한 것⑧ What this model leaves out

      
쿠키 · 압축(Content-Encoding) · 청크 전송 · 범위 요청 · 대용량 전송에서의 대역폭 · TCP 혼잡 제어 · 서버의 병렬 처리 · DNS 캐시는 넣지 않았습니다. 그래서 시간 비교의 절대값이 아니라 "왕복을 몇 번 기다리는가"라는 구조의 차이를 보세요. 실제 값은 Chrome 개발자 도구의 Network 탭에서 재 볼 수 있습니다.

      
Not included: cookies, compression (Content-Encoding), chunked transfer, range requests, bandwidth in large transfers, TCP congestion control, server concurrency and DNS caching. Read the timing comparison not as absolute values but as the structural difference in how many round trips you wait for. Real numbers can be measured in the Network tab of Chrome's developer tools.

  

  
전력·에너지 분야의 통신도 이 위에 있습니다. IEEE 2030.5(스마트 에너지 프로파일)는 HTTP(S)로 자원을 읽고 쓰는 REST 방식이고, OpenADR 3.0도 REST/JSON, OCPP-J(전기차 충전)는 HTTP로 시작해 연결을 WebSocket으로 바꿔 양방향 메시지를 주고받습니다. 목록은 통신 · 데이터 표준에 있습니다.

  
Energy-sector communication sits on this too. IEEE 2030.5 (Smart Energy Profile) is a REST style that reads and writes resources over HTTP(S), OpenADR 3.0 is REST/JSON as well, and OCPP-J (EV charging) starts with HTTP and upgrades the connection to a WebSocket for two-way messages. They are listed in Standards.
