Why did it go up by only one?

count++는 한 줄이지만 CPU에게는 읽기 → 더하기 → 쓰기 세 명령입니다. 그 사이에 스케줄러가 다른 스레드로 바꾸면(선점) 두 스레드가 같은 옛 값을 읽어 한쪽의 덧셈이 사라집니다. 이것이 경쟁 상태입니다. 잠금으로 막으면 이번엔 서로의 잠금을 기다리며 영원히 멈추는 교착상태가 생길 수 있습니다. 둘 다 직접 일으켜 봅니다.

count++ is one line, but to the CPU it is three instructions: read → add → write. If the scheduler switches threads in between (preemption), both threads read the same old value and one addition vanishes: a race condition. Guard it with locks and a new danger appears: deadlock, where threads wait for each other's locks forever. Cause both yourself.

명령은 x86 어셈블리를 흉내 냈지만 실제로 실행하지는 않는 학습용 모형입니다. "잠금 없음"에서 값이 사라지고 뮤텍스 · 원자적 명령에서는 사라지지 않는 것, 식사하는 철학자에서 순서 정하기 · 웨이터 방식이 교착상태를 만들지 않는 것을 tests/os.test.mjs가 확인합니다.

The instructions imitate x86 assembly but are not really executed: a teaching model. tests/os.test.mjs checks that updates are lost with no lock but never with a mutex or an atomic instruction, and that ordering and the waiter never deadlock in the dining philosophers.

    알아 둘 원리Principles worth knowing

    ① 임계 구역① Critical sections

    공유 데이터를 읽고 고치는 코드 구간을 임계 구역이라 합니다. 한 번에 한 스레드만 들어가야(상호 배제) 결과가 끼워 넣는 순서와 상관없이 같아집니다. 경쟁 상태는 대부분의 실행에서는 멀쩡하다가 아주 드물게 틀리기 때문에, 테스트로 찾기 어렵고 재현도 힘든 가장 악명 높은 버그입니다. 위 막대그래프에서 정답이 가장 흔하지 않다는 것도 눈여겨보세요.

    The stretch of code that reads and updates shared data is a critical section. Only one thread may be inside at a time (mutual exclusion) for the result to be the same whatever the interleaving. Race conditions are infamous because most runs are fine and only rare ones go wrong, so tests rarely catch them and they are hard to reproduce. Notice too that in the histogram above the correct answer is not even the most common.

    ② 뮤텍스는 어떻게 만드나② How a mutex is built

    잠금 변수를 "읽고, 비었으면 내 것으로 쓰기"도 두 단계라 그 자체가 경쟁입니다. 그래서 CPU는 끼어들 수 없는 명령을 따로 줍니다: x86의 lock cmpxchg · lock xadd, ARM의 LDREX/STREX. 잠금을 못 얻으면 계속 돌며 기다리는 스핀락(짧게 쥘 때, 커널 안)과, 커널에 부탁해 잠드는 방식(리눅스 futex)이 있습니다. 숫자 하나 더하기처럼 단순하면 잠금 없이 원자적 명령 하나로 끝냅니다.

    "Read the lock variable, and if free, write mine" is itself two steps and therefore a race. So CPUs provide instructions that cannot be interleaved: x86 lock cmpxchg and lock xadd, ARM LDREX/STREX. A thread that fails to get the lock can keep spinning (a spinlock, for short holds inside the kernel) or ask the kernel to put it to sleep (Linux futex). For something as simple as adding to a number, a single atomic instruction replaces the lock entirely.

    ③ 교착상태의 네 가지 조건③ The four conditions for deadlock

    Coffman(1971)이 정리한 네 조건이 모두 성립할 때만 교착상태가 생깁니다. ① 상호 배제: 포크는 한 사람만 쥔다. ② 점유 대기: 하나를 쥔 채 다른 것을 기다린다. ③ 비선점: 남의 포크를 빼앗을 수 없다. ④ 순환 대기: 기다림이 고리를 이룬다. 그러니 하나만 깨면 됩니다. "번호 작은 포크부터"는 ④를, "웨이터"는 동시에 앉는 사람을 줄여 ④가 닫히지 못하게 막습니다.

    Deadlock happens only when all four of Coffman's conditions (1971) hold: ① mutual exclusion: one holder per fork. ② hold and wait: holding one while waiting for another. ③ no preemption: nobody can take a fork away. ④ circular wait: the waiting forms a loop. Breaking any one is enough. "Lower-numbered fork first" breaks ④; "the waiter" limits who sits down so the loop can never close.

    ④ 실무의 규칙: 잠금 순서④ The practical rule: lock ordering

    대부분의 시스템은 "잠금에 번호를 매기고 항상 작은 번호부터 쥔다"는 규칙으로 교착상태를 막습니다. 리눅스 커널은 이 규칙을 실행 중에 검사하는 lockdep이라는 도구를 둡니다. 데이터베이스는 반대로 교착상태를 허용하고, 대기 그래프에서 순환을 찾으면 트랜잭션 하나를 취소합니다(PostgreSQL의 "deadlock detected" 오류). 위 그림에서 빨간 고리를 찾는 것과 같은 일입니다.

    Most systems avoid deadlock with one rule: "number the locks and always take lower numbers first". The Linux kernel even checks this at run time with a tool called lockdep. Databases take the opposite route: they allow deadlocks, find cycles in the wait-for graph, and abort one transaction (PostgreSQL's "deadlock detected" error), the same job as spotting the red loop above.

    ⑤ 잠금의 대가⑤ The price of locks

    잠금을 크게 잡으면 안전하지만 스레드들이 줄을 서서 코어가 여러 개여도 소용없어집니다(파이썬의 GIL이 극단적인 예). 잘게 쪼개면 빨라지지만 잠금이 많아져 순서 실수와 교착상태 위험이 커집니다. 그래서 공유를 줄이는 설계(스레드마다 자기 데이터, 메시지 전달, Rust의 소유권 검사)가 점점 인기를 얻고 있습니다. Rust 페이지의 "겁 없는 동시성"이 그 예입니다.

    One big lock is safe but makes threads queue up, so extra cores stop helping (Python's GIL is the extreme case). Fine-grained locks are faster but multiply the chances of ordering mistakes and deadlock. Designs that share less (per-thread data, message passing, Rust's ownership checks) are therefore increasingly popular; see "fearless concurrency" on the Rust page.

    ⑥ 이 모형이 생략한 것⑥ What this model leaves out

    코어가 여럿일 때의 캐시 일관성과 메모리 순서(재배치, 메모리 장벽), 조건 변수 · 세마포어 · 읽기쓰기 잠금, 우선순위 역전, 굶주림(공정성)은 넣지 않았습니다. 철학자는 정해진 확률로 배고파지고 정해진 시간 동안 먹습니다.

    Not included: cache coherence and memory ordering on multiple cores (reordering, memory barriers), condition variables, semaphores and reader-writer locks, priority inversion, and starvation (fairness). Philosophers get hungry with a fixed probability and eat for a fixed time.
