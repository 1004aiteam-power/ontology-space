① 복제하고 올리기① Clone and push

  1. GitHub 의 저장소를 통째로 복제합니다(이력 전부). 오른쪽 "GitHub" 그림이 원격, 왼쪽이 내 컴퓨터입니다.Copies the GitHub repo whole (all history). The "GitHub" graph on the right is the remote; the other is your computer.
  2. clone 은 새 폴더를 만들 뿐, 거기로 들어가지는 않습니다.clone only creates a folder; it does not enter it.
  3. 원격 이름 origin = 복제해 온 주소 (이름은 관례).The remote name origin = the address you cloned from (the name is a convention).
  4. 내 main 이 [origin/main]을 추적합니다. 그래서 git push/git pull에 주소를 안 적어도 됩니다.My main tracks [origin/main], so git push/git pull need no address.

Pull Request 로 일하는 하루A working day with Pull Requests

  1. git switch main && git pull — 최신 main 에서 시작
  2. git switch main && git pull — start from the latest main
  3. git switch -c feature/주제 — 내 브랜치 만들기, 작게 커밋
  4. git switch -c feature/topic — make my branch, commit in small steps
  5. git push -u origin feature/주제 — GitHub 에 올리기
  6. git push -u origin feature/topic — publish to GitHub
  7. GitHub 에서 Pull Request 열기: 무엇을 왜 바꿨는지 쓰고, 리뷰어를 지정합니다. 자동 검사(CI)가 돌아갑니다.
  8. Open a Pull Request on GitHub: say what and why, assign reviewers. Automated checks (CI) run.
  9. 리뷰 의견대로 같은 브랜치에 커밋을 더 push — PR 에 자동으로 반영됩니다.
  10. Push more commits to the same branch per the review; the PR updates automatically.
  11. 승인되면 머지: Merge commit(이력 그대로 + 병합 커밋) · Squash and merge(PR 전체를 커밋 하나로) · Rebase and merge(커밋들을 일렬로). 팀 규칙에 따릅니다.
  12. When approved, merge: Merge commit (history as is + a merge commit), Squash and merge (the whole PR as one commit) or Rebase and merge (commits in a line). Follow the team rule.
  13. 정리: GitHub 의 "Delete branch", 로컬은 git switch main && git pull && git branch -d feature/주제
  14. Tidy up: GitHub's "Delete branch"; locally git switch main && git pull && git branch -d feature/topic

남의 저장소에 기여하기: Fork 와 upstreamContributing to someone else's repo: fork and upstream

쓰기 권한이 없는 저장소는 Fork(내 계정으로 복사)해서 작업하고 PR 을 보냅니다. 원본은 관례적으로 upstream이라는 두 번째 원격으로 연결해 최신 상태를 따라갑니다.

For a repo you cannot write to, fork it (copy to your account), work there and send a PR. Link the original as a second remote named upstream by convention to keep up with it.

git clone https://github.com/me/grid.git          # 내 fork / my fork
git remote add upstream https://github.com/acme/grid.git
git fetch upstream
git switch main && git merge upstream/main          # 원본의 최신을 내 main 에 / bring upstream's latest into my main
git push origin main                                 # 내 fork 도 최신으로 / update my fork too

알아 둘 원리Principles worth knowing

① Git 과 GitHub 는 다르다① Git and GitHub are different things

Git은 내 컴퓨터에서 도는 버전 관리 프로그램이고, GitHub는 Git 저장소를 올려 두고 협업(Pull Request · Issue · 자동화)하게 해 주는 서비스입니다. GitLab · Bitbucket 도 같은 역할입니다. Git 저장소는 GitHub 없이도 완전하며, 원격은 그저 "또 하나의 복사본"입니다.

Git is version-control software running on your machine; GitHub is a service that hosts Git repos and adds collaboration (Pull Requests, Issues, automation). GitLab and Bitbucket do the same job. A Git repo is complete without GitHub; a remote is just "another copy".

② origin/main 은 사진이다② origin/main is a photograph

origin/main은 "마지막으로 GitHub 와 통신했을 때 main 이 가리키던 곳"을 적어 둔 내 컴퓨터 안의 기록입니다. 그래서 git status가 "up to date"라고 해도 GitHub 에 새 커밋이 있을 수 있고(위 ②단계), git fetch를 해야 사진이 갱신됩니다.

origin/main is a record inside your computer of "where main pointed when I last talked to GitHub". So even when git status says "up to date", GitHub may have new commits (step ② above); only git fetch refreshes the photograph.

③ fetch 는 안전하고 pull 은 합친다③ fetch is safe, pull joins

fetch는 내려받기만 하므로 언제 해도 안전하고, 받은 뒤 git log HEAD..origin/main(없는 커밋 보기)이나 git diff main origin/main으로 살펴볼 수 있습니다. pull은 거기에 merge(또는 rebase)까지 해 버립니다. 초보일수록 fetch → 확인 → merge 순서가 안전합니다.

fetch only downloads so it is always safe, and afterwards you can inspect with git log HEAD..origin/main (commits you lack) or git diff main origin/main. pull goes on to merge (or rebase). For beginners fetch → inspect → merge is safer.

④ push 는 앞으로만 간다④ push only moves forward

GitHub 는 원격 브랜치를 fast-forward 로만 움직이게 합니다. 내가 모르는 커밋이 원격에 있으면 push 가 rejected되는데(사례 보기), 이는 동료의 작업을 덮어쓰지 않도록 지켜 주는 장치입니다. 해결은 먼저 받아서 합치는 것이고, --force는 마지막 수단입니다.

GitHub lets a remote branch move only by fast-forward. If the remote has commits you lack, the push is rejected (see the case), a safeguard against overwriting teammates' work. The cure is to fetch and join first; --force is a last resort.

⑤ 추적(upstream) 설정⑤ Tracking (upstream)

브랜치가 어느 원격 브랜치와 짝인지 기억해 두는 설정입니다. git clone은 main 에 자동으로 해 주고, 새 브랜치는 git push -u origin 이름으로 처음 올릴 때 설정합니다. 이것이 있어야 git push/git pull만 쳐도 되고 git status가 "ahead/behind"를 알려 줍니다.

The setting remembering which remote branch a branch pairs with. git clone sets it for main; for new branches set it on the first git push -u origin name. With it plain git push/git pull work and git status reports "ahead/behind".

⑥ 머지 방식 세 가지의 이력⑥ The history of the three merge styles

Merge commit은 브랜치의 모든 커밋과 병합 커밋이 남아 무슨 일이 있었는지 보존합니다. Squash는 PR 하나가 main 에 커밋 하나로 남아 이력이 깔끔하지만 세부 이력은 사라집니다. Rebase and merge는 선형 이력이지만 해시가 바뀝니다. 한 저장소에서는 한 가지로 통일하는 편이 이력을 읽기 쉽습니다.

Merge commit keeps every commit of the branch plus a merge commit, preserving what happened. Squash leaves one commit per PR on main: tidy but the detail is gone. Rebase and merge gives linear history but changes hashes. Within one repo, pick one to keep history readable.

⑦ 올리면 안 되는 것⑦ What must not be pushed

비밀번호 · API 키 · 개인 키, 큰 바이너리(100MB 초과는 거절), 빌드 산출물, 개인 설정. .gitignore로 막고, 한 번 push 한 비밀은 폐기가 먼저입니다(사례 보기). 공개 저장소는 누구나 복제하므로 push 는 곧 공개입니다.

Passwords, API keys, private keys, big binaries (over 100 MB is refused), build outputs and personal settings. Block them with .gitignore, and for a secret already pushed revoking comes first (see the case). Anyone can clone a public repo, so pushing there is publishing.

⑧ 이 시뮬레이터가 생략한 것⑧ What this simulator leaves out

네트워크는 없고 "GitHub"는 이 페이지 안의 가짜 저장소입니다. Pull Request · 이슈 · Actions · 태그 push · 원격 브랜치 여러 개 동시 추적 · 부분 clone · LFS · 인증은 구현하지 않았고, 진짜 GitHub 의 오류 문장(거절 사유)을 흉내 내는 데 그쳤습니다.

There is no network, and "GitHub" is a fake repo inside this page. Pull Requests, issues, Actions, tag pushes, tracking several remote branches at once, partial clones, LFS and authentication are not implemented; only real GitHub's rejection wording is imitated.
