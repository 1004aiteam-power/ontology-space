소켓 페이지에서 서버는 accept()로 연결을 하나 받았습니다. 그런데 손님이 수천 명이라면? 그 연결을 누가, 무엇을 붙들고 처리하느냐가 서버 구조의 변천사입니다: 한 번에 하나씩 → 프로세스 → 스레드 → 스레드 풀 → 이벤트 루프 → async/코루틴. 같은 부하를 일곱 가지 방식으로 돌려 보며 왜 이렇게 바뀌어 왔는지 확인합니다.

On the sockets page the server took one connection with accept(). But what if thousands of clients show up? Who handles each connection, and what does it hold while waiting is the history of server design: one at a time → processes → threads → thread pools → event loops → async/coroutines. Run the same load through seven designs and see why things moved this way.

구조의 차이를 보이려는 학습용 모형입니다 (실제 서버의 벤치마크가 아님). 계산 규칙은 tests/net.test.mjs로 확인합니다. 메모리 · 생성 비용은 자릿수 감각을 위한 가정값이고, 연도와 제품 예는 대략적인 흐름입니다.

A teaching model to show structural differences, not a benchmark of real servers. The rules are checked in tests/net.test.mjs. Memory and creation costs are assumed values for a sense of scale, and the years and products give only a rough timeline.

알아 둘 원리Principles worth knowing

① C10K: 연결 1만 개 문제① C10K: ten thousand connections

1999년 무렵 "서버 한 대가 동시 연결 1만 개를 감당할 수 있는가"라는 물음이 "C10K 문제"로 불렸습니다. 연결마다 스레드·프로세스를 두는 방식으로는 메모리와 문맥 전환 때문에 어려웠고, 이것이 이벤트 기반 구조가 퍼지는 계기가 되었습니다. 지금은 하드웨어가 좋아져 연결 수십만~백만 개가 논의됩니다(C10M).

Around 1999 the question "can one server handle ten thousand simultaneous connections?" became known as the "C10K problem". A thread or process per connection struggled with memory and context switching, which pushed event-driven designs into wide use. With today's hardware, hundreds of thousands to a million connections are discussed (C10M).

② 스레드는 왜 비싼가② Why threads are costly

스레드마다 자기 스택이 있습니다(기본 1~8MB쯤을 가상 메모리로 예약하고, 쓴 만큼만 실제로 차지). 또 CPU가 스레드를 바꿀 때마다 문맥 전환(레지스터 저장·복원, 캐시가 식어 버림)이 일어납니다. 반면 이벤트 루프의 연결 하나는 수 KB의 객체이고, 코루틴 · goroutine은 수 KB의 작은 스택에서 시작합니다. 위 표의 "추정 메모리" 열이 그 자릿수 차이입니다.

Every thread has its own stack (about 1–8 MB reserved as virtual memory, with only the used part actually resident). And each time the CPU switches threads, a context switch occurs (saving and restoring registers, cooling the caches). A connection in an event loop is an object of a few KB, and a coroutine or goroutine starts with a small stack of a few KB. The "Est. memory" column above shows that order-of-magnitude gap.

③ select, poll, epoll: "누가 준비됐나"를 묻는 법③ select, poll, epoll: asking "who is ready"

소켓 1만 개 중 지금 읽을 데이터가 있는 것은 몇 개뿐입니다. select · poll은 호출할 때마다 감시 대상 전부를 커널에 넘겨 훑게 해서 연결 수에 비례해 느려집니다. 리눅스의 epoll(BSD · macOS는 kqueue)은 감시 목록을 커널에 한 번 등록해 두고, 준비된 것만 돌려받습니다. 이벤트 루프가 큰 수의 연결을 다룰 수 있는 핵심입니다.

Out of 10,000 sockets, only a few have data to read right now. select and poll hand the entire watch list to the kernel on every call, so they slow down in proportion to the connection count. Linux's epoll (kqueue on BSD and macOS) registers the watch list once and gets back only the ready ones. That is the key to event loops handling huge numbers of connections.

④ 이벤트 루프를 막지 마라④ Never block the event loop

루프 하나는 한 번에 한 가지 일만 합니다. 요청 안에서 CPU를 오래 쓰거나(큰 JSON 처리, 암호화, 이미지 변환) 멈추는 호출(블로킹 DB 드라이버, sleep)을 하면 그 시간 동안 다른 모든 연결이 멈춥니다. 위 "CPU 작업이 무거움"에서 ⑤가 ①과 같아지는 이유입니다. 그래서 무거운 일은 별도의 작업자 풀로 넘기거나(Node.js의 libuv 스레드 풀, run_in_executor), 코어마다 루프를 두는 ⑦ 구조를 씁니다.

One loop does one thing at a time. If a request burns CPU (big JSON, encryption, image conversion) or makes a blocking call (a blocking DB driver, sleep), every other connection stalls for that time — why ⑤ equals ① under "Heavy CPU work". Heavy work is therefore handed to a separate worker pool (Node.js's libuv thread pool, run_in_executor) or spread with one loop per core, as in ⑦.

⑤ CPU가 무거울 땐 "많이 동시에"가 답이 아니다⑤ For heavy CPU work, "more at once" is not the answer

"CPU 작업이 무거움"에서 ④(풀 8개)의 평균 지연이 ③(연결마다 스레드)보다 낮게 나옵니다. 코어가 4개뿐인데 24개를 한꺼번에 돌리면 모두가 조금씩만 나아가 전부 늦게 끝나기 때문입니다. CPU 중심의 일은 동시 실행 수를 코어 수 근처로 제한하는 편이 낫고, I/O 대기가 긴 일은 많이 동시에 걸어 두는 편이 낫습니다. 풀 크기 슬라이더로 직접 확인해 보세요.

Under "Heavy CPU work", ④ (8 workers) shows a lower average latency than ③ (a thread per connection). With only 4 cores, running 24 at once makes each advance only slowly so everything finishes late. CPU-bound work does better with concurrency capped near the core count, while work with long I/O waits does better with many in flight. Check it with the pool-size slider.

⑥ 요즘은 어떻게 고르나⑥ How people choose today

I/O 대기가 많고 연결이 많다(채팅, 웹소켓, API 게이트웨이) → 이벤트 루프 · async · 가상 스레드. CPU 계산이 무겁다 → 코어 수에 맞춘 워커(프로세스 · 스레드 풀). 격리와 안정성이 중요하다 → 프로세스(웹 브라우저 탭, PostgreSQL은 연결마다 프로세스를 두어, 연결이 많을 땐 앞에 연결 풀러를 둠). 실제 서버는 이것들을 섞습니다: nginx는 코어마다 이벤트 루프 워커를 두고, 무거운 일은 뒤의 애플리케이션 서버로 넘깁니다.

Many connections with long I/O waits (chat, WebSockets, API gateways) → event loop, async or virtual threads. Heavy computation → workers sized to the cores (processes or a thread pool). Isolation and stability matter → processes (browser tabs; PostgreSQL runs a process per connection and puts a connection pooler in front when there are many). Real servers mix them: nginx runs an event-loop worker per core and passes heavy work to the application server behind it.

⑦ 이 모형이 생략한 것⑦ What this model leaves out

문맥 전환 비용 자체, 캐시, 락 경쟁, 메모리 대역폭, 네트워크 대역폭, 커널의 연결 대기열(backlog), 운영체제 스케줄러의 실제 정책은 넣지 않았습니다. 메모리 · 생성 비용도 가정값입니다. 그래서 숫자 자체보다 "기다리는 동안 무엇을 붙들고 있나"와 "일꾼이 몇 개 도나"의 구조 차이를 보세요.

Not modelled: the cost of context switches themselves, caches, lock contention, memory and network bandwidth, the kernel's accept queue (backlog) and the real OS scheduler policy. Memory and creation costs are assumed. So read not the numbers but the structural difference in what is held while waiting and how many workers run.

전력·에너지 분야에서도 같은 고민이 나옵니다. VPP 플랫폼이나 전기차 충전 운영 시스템(OCPP의 CSMS)은 수만~수십만 대의 장치가 대부분 조용히 연결만 유지하다 가끔 메시지를 보내는 부하를 받습니다. I/O 대기가 압도적인 이 성격은 이벤트 기반 · async 구조와 잘 맞고, 연결마다 스레드를 두는 방식은 감당하기 어렵습니다. 장치와 이어지는 프로토콜은 통신 · 데이터 표준에 있습니다.

The energy sector faces the same question. A VPP platform or an EV-charging operations system (the CSMS in OCPP) takes a load of tens to hundreds of thousands of devices that mostly just keep a connection open and send a message now and then. That I/O-wait-dominated profile suits event-driven and async designs, while a thread per connection would struggle. The protocols toward the devices are in Standards.
