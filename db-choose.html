how to choose

파일을 직접 여는 것에서 AI 에이전트의 도구까지, DB에 닿는 길을 한 계단씩 올라 보았습니다. 마지막으로 누가 · 어떤 질문을 · 어떤 규모로 쓰는지에 따라 무엇이 맞는지 정리합니다. 요점은 하나입니다. 위로 갈수록 DB 계정이 안쪽에 머물고 변화에 강해지지만, 거치는 단계가 늘고 질문의 자유가 줄어듭니다.

From opening a file directly to an AI agent's tool, we climbed the roads to a DB one rung at a time. Finally, a summary of what fits depending on who uses it, with what questions, at what scale. The point is one: higher up, the DB account stays inside and the design copes better with change, but there are more hops and less freedom to ask.

점수와 이유는 assets/db/choose.js의 단순한 규칙입니다. 규칙이 의도대로 동작하는지(예: 브라우저에는 DB 계정을 주는 방식이 막힘)는 tests/db.test.mjs로 확인합니다.

Scores and reasons are simple rules in assets/db/choose.js. tests/db.test.mjs checks that they behave as intended (for example, approaches that hand a browser a DB account are blocked).

내 상황에는 어떤 접근이 맞을까Which access fits my situation

네 가지를 고르면, 일곱 가지 접근 방식이 점수와 이유와 함께 정렬됩니다. 정답표가 아니라 판단의 근거를 드러내는 규칙입니다. 같은 질문에서 하나만 바꿔 점수가 어떻게 움직이는지 보세요. 쓰면 안 되는 조합(예: 브라우저에 DB 계정)은 점수와 상관없이 맨 아래로 내려가며 이유가 붙습니다.

Choose four things and the seven approaches are ranked with scores and reasons. It is not an answer key but rules that expose the grounds for a judgement. Change just one answer and watch the scores move. Combinations you must not use (such as DB credentials in a browser) sink to the bottom regardless of score, with the reason attached.

한눈에 비교: 다섯 가지 기준Side by side: five criteria

각 항목은 1~5점이고 모두 높을수록 좋음입니다. 한 줄이 5점으로 가득 찬 방식은 없습니다. 한쪽을 얻으면 다른 쪽을 내주는 교환입니다.

Each item scores 1–5 and higher is always better. No approach fills every row with 5s: it is a trade of gaining one thing by giving up another.

  • 변화에 강함: DB 구조나 화면이 바뀌어도 덜 흔들림Resilience: less shaken when the DB structure or screens change
  • 보안 경계: DB 계정이 바깥에 닿지 않음Security boundary: DB credentials never reach outside
  • 속도: 거치는 단계(왕복)가 적음Speed: fewer hops (round trips)
  • 만들기 쉬움: 짜야 할 코드가 적음Ease: little code to write
  • 질문의 자유: 임의의 질문을 던질 수 있음Freedom: can ask arbitrary questions

고르는 순서: 네 개의 질문The order of choosing: four questions

  1. DB 계정을 가져도 되는 호출자인가? 내 서버 코드 · 분석가면 예, 브라우저 · 외부 시스템 · AI 에이전트면 아니오. 아니오라면 사이에 서비스(REST · GraphQL · 자동 생성 API · 점검된 도구)를 둡니다.
  2. Is the caller one that may hold a DB account? Your own server code or analysts: yes. A browser, an outside system or an AI agent: no. If no, put a service in between (REST, GraphQL, an auto-generated API or a checked tool).
  3. 필요한 질문이 정해져 있는가, 화면마다 다른가, 그때그때인가? 정해졌다면 REST 엔드포인트, 화면마다 다르면 GraphQL, 그때그때면 SQL(분석가) 또는 점검된 에이전트 도구.
  4. Are the questions fixed, different per screen, or ad hoc? Fixed: REST endpoints; per screen: GraphQL; ad hoc: SQL (analysts) or a checked agent tool.
  5. 빨리 만들기가 먼저인가, 오래 가는 구조가 먼저인가? 빨리라면 자동 생성 API · ORM, 오래 간다면 계약을 직접 설계한 서비스.
  6. Is building fast first, or a long-lived design first? Fast: auto-generated API or ORM; long-lived: a service whose contract you design yourself.
  7. 규모는? 작으면 가장 단순한 것(임베디드 · 자동 생성 API), 커지면 풀 · 캐시 · 질의 수 점검이 중요해집니다.
  8. How big? Small: the simplest thing (embedded, auto-generated API); as it grows, pools, caches and query counts matter.

이 메뉴의 한 줄 요약This menu in one line each

    흔한 실수와 현실Common mistakes and reality

    ① DB 계정을 클라이언트에 준다① Handing the DB account to a client

    가장 흔하고 가장 치명적인 실수입니다. 브라우저 코드나 모바일 앱에 들어간 비밀은 누구나 꺼내 볼 수 있습니다. 앱에 DB 주소와 비밀번호를 넣었다면 이미 공개된 것으로 봅니다. 이 문제가 서비스 계층이 존재하는 이유이고, 자동 생성 API를 쓸 때 행 단위 보안이 필수인 이유입니다.

    The commonest and deadliest mistake. A secret placed in browser code or a mobile app can be extracted by anyone. If you put the DB address and password in an app, treat it as already public. This is why the service layer exists and why row-level security is mandatory with auto-generated APIs.

    ② 한 계층만 고집한다② Insisting on a single layer

    현실의 시스템은 섞여 있습니다. 같은 프로젝트에서 업무 CRUD는 ORM, 무거운 보고서는 직접 SQL, 화면용 API는 REST나 GraphQL, 분석은 읽기 전용 계정의 SQL, 로컬 캐시는 임베디드 DB를 쓰는 것이 자연스럽습니다. 중요한 것은 계층을 섞는 것이 아니라 각 호출자가 어느 계단에 서 있는지 의식하는 것입니다.

    Real systems are mixed. In one project it is natural to use an ORM for business CRUD, raw SQL for heavy reports, REST or GraphQL for screen APIs, SQL from a read-only account for analysis and an embedded DB as a local cache. What matters is not avoiding mixing but being conscious of which rung each caller stands on.

    ③ 쓸데없이 높은 계단③ A needlessly high rung

    혼자 쓰는 스크립트에 REST 서비스와 GraphQL을 올리면 거치는 단계와 운영 부담만 늘어납니다. 호출자가 신뢰할 만하고 하나뿐이면 임베디드나 드라이버로 충분합니다. 반대로 호출자가 늘어날 조짐(앱 · 외부 연동)이 보이면 그때 서비스를 앞에 세우면 되고, 이를 쉽게 하려고 DB 접근 코드를 한곳에 모아 두는 것이 좋은 대비입니다.

    Putting a REST service and GraphQL on a script only you use adds hops and operating burden. When the caller is trustworthy and single, embedded or a driver suffices. When callers start to multiply (apps, outside integrations), put a service in front then; keeping DB access code in one place is good preparation for that.

    ④ 보이지 않는 질의④ Invisible queries

    계단이 높아질수록 실제로 DB에 간 SQL이 눈에 안 보입니다. ORM의 N+1, GraphQL 리졸버의 N+1, 자동 생성 API가 만든 비효율적인 조인 모두 같은 병입니다. 처방도 같습니다: 개발 중에 SQL 로그를 켜고 질의 수를 세며, 느린 질의는 실행 계획(EXPLAIN)으로 몇 페이지를 읽는지 봅니다.

    The higher the rung, the less you can see the SQL that actually reached the DB. An ORM's N+1, a GraphQL resolver's N+1 and an inefficient join from an auto-generated API are the same disease with the same cure: turn on SQL logs while developing, count queries, and check slow ones with an execution plan (EXPLAIN) to see how many pages they read.

    ⑤ 계단을 옮겨 갈 때⑤ When you move between rungs

    처음엔 자동 생성 API나 ORM으로 빨리 시작해 사용자가 늘면 직접 설계한 서비스로 옮기는 경로가 흔합니다. 이때 데이터 모양(표)과 외부에 약속한 모양(API)을 분리해 둘수록 옮기기 쉽습니다. 반대로 표 구조를 곧바로 API로 내보냈다면 표를 고칠 때마다 클라이언트가 깨집니다.

    A common path is to start fast with an auto-generated API or ORM and move to a hand-designed service as users grow. The more you keep the data shape (tables) and the promised shape (API) separate, the easier the move. If the table layout was exposed straight as the API, every table change breaks clients.

    ⑥ 측정하고 고른다⑥ Measure, then choose

    이 페이지의 점수는 생각을 정리하는 틀일 뿐입니다. 실제 선택은 팀의 숙련도 · 운영 환경 · 데이터 규모 · 보안 요구에 달려 있고, 병목은 짐작과 다른 곳에 있는 일이 많습니다. 작게 만들어 실제 질의 수와 지연을 재 본 뒤 정하세요.

    The scores on this page are only a frame for organising thought. The real choice depends on team skill, operating environment, data scale and security needs, and bottlenecks often lie elsewhere than guessed. Build small, measure real query counts and latency, then decide.

    ⑦ 전력·에너지 분야에서는⑦ In the power and energy field

    설비 · 고객 마스터는 관계형 + ORM/서비스, 계통의 연결 관계는 그래프(Cypher), 계량 · SCADA 측정값은 시계열 DB로 두는 경우가 많고, 현장 장치와의 통신(IEEE 2030.5 · OpenADR)은 데이터베이스가 아니라 HTTP API로 이루어집니다. 운영 시스템(OT)과 정보 시스템(IT) 사이에는 직접 DB 접속을 막는 경계를 두는 것이 안전의 기본입니다.

    Asset and customer masters often sit in relational + ORM/service, grid connectivity in a graph (Cypher), and metering and SCADA readings in a time-series DB; communication with field devices (IEEE 2030.5, OpenADR) runs over HTTP APIs, not databases. Between operational (OT) and information (IT) systems, a boundary that blocks direct DB connections is the safety baseline.

    ⑧ 이 도우미가 생략한 것⑧ What this helper leaves out

    점수와 이유는 이 사이트가 정한 단순한 규칙이고 가중치에 정답은 없습니다. 비용 · 조직 구조 · 규제 · 기존 자산 · 벤더 관계는 넣지 않았습니다. 규칙은 assets/db/choose.js에 그대로 적혀 있으니, 여러분의 상황에 맞게 고쳐 보세요.

    The scores and reasons are simple rules chosen by this site and the weights have no right answer. Cost, organisational structure, regulation, existing assets and vendor relationships are not included. The rules are written plainly in assets/db/choose.js, so adjust them to your own situation.
