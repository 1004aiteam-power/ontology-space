네트워크 스택 · 소켓NETWORK STACK · SOCKETS

🔌 프로그램이 네트워크를 쓰는 문:
소켓The door a program uses
to reach the network: sockets

프로그램은 TCP 헤더도 패킷도 직접 다루지 않습니다. 운영체제가 내어 주는 소켓(socket)이라는 번호표(fd)에 send()로 바이트를 넣고 recv()로 꺼낼 뿐입니다. 헤더 붙이기, 번호 매기기, 재전송은 그 뒤의 커널이 합니다. 서버와 클라이언트가 어떤 순서로 무엇을 호출하고, 그때마다 커널 안이 어떻게 바뀌는지 한 줄씩 따라갑니다.

A program never handles TCP headers or packets itself. It only send()s bytes into, and recv()s them out of, a numbered handle (fd) called a socket that the operating system gives it. Adding headers, numbering and retransmission happen in the kernel behind it. Follow, line by line, which calls a server and a client make, and how the kernel changes with each one.

실제 소켓이 아니라 커널의 동작을 흉내 낸 모형입니다 (같은 규칙은 tests/net.test.mjs로 확인). 예시 코드는 파이썬 표준 socket 모듈의 이름을 따랐고, 다른 언어(C · Java · Go …)도 호출 순서는 같습니다.

A model that mimics kernel behaviour, not real sockets (the rules are checked in tests/net.test.mjs). The example code uses the names of Python's standard socket module; the call order is the same in other languages (C, Java, Go …).

선 위로 오간 것What crossed the wire

    "기본" 시나리오에서 클라이언트가 send()를 두 번 한 뒤 서버의 recv()가 어떻게 읽는지, 위의 "recv() 크기"를 3~20쯤으로 줄여 보세요.

    In the "Basics" scenario, the client calls send() twice. Lower the "recv() size" to about 3–20 and watch how the server's recv() reads it.

    알아 둘 원리Principles worth knowing

    ① 소켓은 fd + 주소 한 쌍① A socket is an fd plus an address pair

    소켓은 파일처럼 번호(fd)로 다룹니다. 연결 하나는 (내 IP, 내 포트, 상대 IP, 상대 포트), 곧 5-tuple(여기에 프로토콜)로 구분됩니다. 서버가 8080 포트 하나로 수천 명을 받을 수 있는 것은, 클라이언트 쪽 IP나 포트가 달라 5-tuple이 모두 다르기 때문입니다. "클라이언트 둘" 시나리오로 확인해 보세요.

    A socket is handled by a number (fd), like a file. A connection is identified by (my IP, my port, peer IP, peer port) — the 5-tuple, with the protocol. A server can serve thousands on the single port 8080 because each client's IP or port differs, so every 5-tuple is different. See it in the "Two clients" scenario.

    ② 듣는 소켓과 연결 소켓은 다르다② The listening socket and connection sockets differ

    listen()하는 소켓은 연결을 받기만 하고 데이터는 주고받지 않습니다. accept()가 연결마다 새 소켓(새 fd)을 만들어 돌려주고, 데이터는 그것으로 주고받습니다. 위 표에서 LISTEN인 fd 3은 그대로 남고, 연결마다 ESTABLISHED인 fd가 하나씩 늘어나는 것을 보세요.

    The socket that listen()s only accepts connections; it never carries data. accept() creates a new socket (new fd) per connection, and data flows through that. In the table above, the LISTEN fd stays while one ESTABLISHED fd appears per connection.

    ③ 연결 대기열: accept() 전에 이미 연결돼 있다③ The accept queue: connected before accept()

    3-way handshake는 서버 프로그램이 accept()를 부르기 전에 커널이 끝냅니다. 완성된 연결은 대기열(backlog)에 쌓여 있다가 accept()가 하나씩 꺼내 갑니다. 대기열이 가득 차면 새 SYN은 무시되어 클라이언트가 시간 초과로 실패합니다. "자주 만나는 오류"에서 backlog를 1로 두고 확인할 수 있습니다. 앞 단계의 TCP 순서도가 바로 이 과정입니다.

    The kernel finishes the 3-way handshake before the server program calls accept(). Completed connections wait in the queue (backlog) and accept() takes them one by one. When the queue is full, new SYNs are ignored and the client fails by timeout. "Common errors" shows it with a backlog of 1. The TCP sequence diagram is exactly this process.

    ④ TCP는 바이트 스트림이다④ TCP is a byte stream

    send()를 두 번 한 것이 recv()에서 두 번으로 나오리라는 보장은 없습니다. 합쳐져서 한 번에 오기도 하고, 반으로 잘려 오기도 합니다. TCP에는 "메시지의 경계"가 없고 바이트의 흐름만 있기 때문입니다. 그래서 응용 프로토콜이 경계를 따로 정합니다: HTTP는 헤더의 끝(빈 줄)과 Content-Length로, 다른 프로토콜은 길이 접두사나 구분 문자로. recv() 크기를 줄여 보면 바로 보입니다.

    Two send() calls need not come out as two recv() calls. They may be merged, or split in half, because TCP has no message boundaries, only a flow of bytes. Application protocols therefore set their own boundaries: HTTP uses the blank line after the headers and Content-Length; others use length prefixes or delimiters. Shrink the recv() size and you see it at once.

    ⑤ send()가 돌아왔다고 상대가 받은 것은 아니다⑤ send() returning does not mean the peer received

    send()는 데이터를 커널의 송신 버퍼에 맡기면 돌아옵니다. 실제 전송, 번호 매기기, 재전송은 그 뒤에 커널이 합니다. 상대 프로그램이 읽었는지까지 알려면 응용 프로토콜의 응답(예: HTTP의 상태 줄)이 있어야 합니다. 상대가 먼저 닫았을 때 recv()가 0바이트(EOF)를 돌려주는 것, 닫힌 연결에 send()하면 오류(EPIPE)가 나는 것도 같은 맥락입니다.

    send() returns once the data is handed to the kernel's send buffer; the real transmission, numbering and retransmission come later. Knowing the peer program actually read it takes a reply in the application protocol (e.g. HTTP's status line). Likewise, recv() returns 0 bytes (EOF) when the peer closed first, and send() on a closed connection fails with EPIPE.

    ⑥ 멈추는 호출과 안 멈추는 호출⑥ Blocking and non-blocking

    accept()와 recv()는 기본적으로 데이터가 올 때까지 프로그램을 멈춥니다(blocking). 위 시나리오에서 ⏳가 그 모습입니다. 연결이 수천 개면 스레드를 그만큼 두는 대신, 여러 소켓을 한꺼번에 감시하다 준비된 것만 처리하는 select · epoll · 비동기 I/O(asyncio, Node.js, Netty)를 씁니다. 이 모형은 가장 단순한 blocking 방식만 다룹니다. 그 선택지들은 동시 접속 처리에서 비교합니다.

    accept() and recv() by default pause the program until data arrives (blocking) — the ⏳ above. With thousands of connections, instead of one thread each, servers watch many sockets at once and handle only the ready ones with select, epoll or async I/O (asyncio, Node.js, Netty). This model covers only the simplest, blocking style; the alternatives are compared in Handling many connections.

    HTTP 서버도 결국 이 호출 순서를 따르는 프로그램입니다: accept()한 소켓에서 recv()로 요청 글자를 읽고 send()로 응답 글자를 돌려줄 뿐입니다. 그 글자의 모양은 다음 페이지에서 봅니다. 전력 분야의 OCPP(전기차 충전)나 IEC 61850 MMS, DNP3도 같은 소켓 위에서 각자의 메시지 규칙을 얹은 것입니다.

    An HTTP server is, in the end, a program following this call order: it recv()s the request text from an accept()ed socket and send()s the response text back. The next page looks at the shape of that text. In power systems, OCPP (EV charging), IEC 61850 MMS and DNP3 are likewise their own message rules laid on these same sockets.
