🧱 SQL을 코드로 감싸기:
쿼리 빌더와 ORMWrapping SQL in code:
query builders and ORMs

SQL을 글자로 쓰는 일은 반복이 많고 실수하기 쉽습니다. 쿼리 빌더는 SQL을 코드로 조립하게 하고, ORM은 표의 행을 객체로 다루게 합니다. 편해진 만큼 어떤 SQL이 나가는지 안 보이는 대가가 따르고, 그 대표가 N+1 문제입니다.

Writing SQL as text is repetitive and error-prone. A query builder lets you assemble SQL in code, and an ORM lets you handle table rows as objects. The price of that comfort is not seeing which SQL goes out, and the classic case is the N+1 problem.

여기의 빌더 · 불러오기 코드는 설명용 최소 구현이고, 실행은 이 페이지 안의 작은 SQL 엔진이 합니다. 세 방식의 결과가 같다는 것과 질의 횟수는 tests/db.test.mjs로 확인합니다. 시간 계산은 왕복 횟수만 센 단순 모형입니다.

The builder and loading code here are minimal teaching implementations, run by the small SQL engine in this page. tests/db.test.mjs checks that the three styles give the same result and counts their queries. The timing is a simple model counting round trips only.

LAB 1

코드가 SQL이 되는 과정How code becomes SQL

조건을 고르면 쿼리 빌더 코드가 만들어지고, 그것이 SQL과 바인딩 값으로 바뀌어 실행됩니다. ORM은 이 위에 한 겹 더 얹어 "표 행"을 객체로 돌려줍니다. 어떤 표기든 결국 DB에는 아래 SQL이 갑니다.

Pick conditions and query-builder code is composed, then turned into SQL plus bound values and run. An ORM adds one more layer, returning "table rows" as objects. Whatever the notation, it is the SQL below that reaches the DB.

N+1 문제: 보이지 않는 질의The N+1 problem: invisible queries

  
"변전소 목록과 각 변전소의 설비를 함께 보여 줘". ORM에서는 for s in substations: s.assets 한 줄이지만, 기본 설정(지연 불러오기)에서는 변전소마다 질의가 한 번씩 나갑니다. 아래에서 세 방식이 실제로 보낸 SQL을 보고, 변전소가 늘면 어떻게 되는지 확인하세요.

  
"Show the substations, each with its assets." In an ORM it is one line, for s in substations: s.assets, but with the default (lazy loading) one query goes out per substation. See the SQL each of three styles really sent below, then watch what happens as substations multiply.

  

  

  

    
    
  

  






  
세 가지 스타일Three styles

  

    
쿼리 빌더Query builder
db.select("name")
  .from("assets")
  .where("health", ">=", 70)
SQL을 코드로 조립. 결과는 단순한 행. 가볍고 SQL이 잘 보임 (Knex · SQLAlchemy Core · jOOQ).
SQL composed in code; results are plain rows. Light, and the SQL stays visible (Knex, SQLAlchemy Core, jOOQ).

    
Active Record
a = Asset.find("T1")
a.health = 80
a.save()          # 객체가 스스로 저장
객체 하나가 표의 한 행이고 저장도 스스로 함. 쉽고 빠르지만 객체가 DB 구조에 묶임 (Rails · Django).
An object is one table row and saves itself. Easy and fast, but the object is tied to the DB structure (Rails, Django).

    
Data Mapper
a = session.get(Asset, "T1")
a.health = 80
session.commit()  # 매퍼가 저장
객체는 DB를 모르고 별도의 매퍼가 변환. 업무 객체가 깨끗하지만 설정이 많음 (Hibernate · SQLAlchemy ORM).
Objects know nothing about the DB; a separate mapper converts. Clean domain objects but more setup (Hibernate, SQLAlchemy ORM).

  






  
알아 둘 원리Principles worth knowing

  

    
① 왜 ORM이 생겼나① Why ORMs arose

      
앞 단계(드라이버)에서는 SQL 글자를 직접 쓰고, 결과의 열을 하나씩 꺼내 객체에 옮기는 반복 코드가 끝없이 생깁니다. ORM(Object-Relational Mapping)은 이 변환과, 방언 차이, 기본 CRUD를 맡습니다. 객체는 참조로 이어진 그물이고 관계형 표는 값으로 이어진 집합이라 서로 맞지 않는데(임피던스 불일치), ORM은 그 틈을 메웁니다. 같은 ESS를 클래스와 OWL로 쓰는 차이는 온톨로지 vs. 객체지향 설계에 있습니다.

      
At the previous rung (drivers) you write SQL text and endless repetitive code pulling columns out one by one into objects. An ORM (Object-Relational Mapping) takes over that conversion, dialect differences and basic CRUD. Objects are nets joined by references while relational tables are sets joined by values, and they do not fit (the impedance mismatch); the ORM bridges the gap. How one battery looks as classes and as OWL is in Ontology vs. OOD.

    
② 쿼리 빌더는 SQL 조립기② A query builder assembles SQL

      
빌더는 조건을 메서드로 받아 SQL 글자와 바인딩 값을 따로 만듭니다(LAB 1). 그래서 바인딩의 안전함이 기본으로 따라오고, 조건을 if문으로 붙였다 뗐다 하기 쉽습니다(검색 화면의 선택적 필터). 문자열 이어붙이기로 같은 일을 하다가 인젝션이 생기는 일을 구조적으로 막아 줍니다.

      
A builder takes conditions as methods and produces SQL text and bound values separately (Lab 1). So the safety of binding comes by default, and adding or dropping conditions with an if statement is easy (optional filters on a search screen). It structurally prevents the injection that string concatenation invites.

    
③ N+1과 불러오기 전략③ N+1 and loading strategies

      
관계를 쓰는 순간 질의하는 지연 불러오기는 편하지만, 목록 × 관계에서 질의가 N+1번 나갑니다. 고치는 길은 세 가지입니다: 미리 한 번에 묶어 IN으로(2번), JOIN으로 한 번에(1번 — 대신 부모 행이 자식 수만큼 반복되어 옵니다), 아니면 필요한 필드만 직접 SQL로. 개발 중에 질의 수를 세는 습관(로그 · 테스트에서 질의 수 상한)이 가장 확실한 방지책입니다.

      
Lazy loading, which queries the moment you use a relation, is convenient but issues N+1 queries for list × relation. Three fixes: gather up front and use IN (2 queries), JOIN in one go (1 query, though parent rows repeat once per child), or hand-written SQL for just the fields needed. The surest prevention is the habit of counting queries in development (logs, or a query-count cap in tests).

    
④ 작업 단위와 식별자 맵④ Unit of work and identity map

      
성숙한 ORM(데이터 매퍼 계열)은 한 세션 안에서 같은 행은 같은 객체로 돌려주고(식별자 맵), 바뀐 객체를 모아 두었다가 commit 때 필요한 UPDATE만 한꺼번에 보냅니다(작업 단위). 편리하지만, 언제 SQL이 나가는지 코드에서 보이지 않아 놀라는 일이 생깁니다. echo=True 같은 SQL 로그를 켜 두고 개발하세요.

      
Mature ORMs (data-mapper family) return the same row as the same object within a session (identity map) and collect changed objects, sending only the needed UPDATEs together at commit (unit of work). Convenient, but the code does not show when SQL goes out, which causes surprises. Develop with SQL logging on, such as echo=True.

    
⑤ 스키마 변경: 마이그레이션⑤ Schema changes: migrations

      
모델 코드를 고치면 DB 표도 바뀌어야 합니다. ORM 도구들은 변경을 순서 있는 마이그레이션 파일(열 추가, 인덱스 생성)로 남겨 개발 · 시험 · 운영 DB를 같은 상태로 맞춥니다. 운영에서는 큰 표의 열 추가가 오래 잠그지 않는지 따로 점검해야 합니다.

      
Changing model code means the DB tables must change too. ORM tooling records changes as ordered migration files (add a column, create an index) so development, test and production DBs reach the same state. In production, check separately that adding a column to a big table will not lock it for long.

    
⑥ 비상구: 직접 SQL⑥ The escape hatch: raw SQL

      
복잡한 집계 · 보고서 · 대량 처리 · 방언 전용 기능은 ORM으로 쓰면 오히려 읽기 어렵고 느립니다. 대부분의 ORM이 직접 SQL을 실행하는 문을 열어 둡니다(바인딩은 그대로 사용). 한 프로젝트에서 평범한 CRUD는 ORM, 무거운 분석은 SQL로 섞어 쓰는 것이 흔한 모습입니다.

      
Complex aggregates, reports, bulk processing and dialect-only features are harder to read and slower through an ORM. Most ORMs leave a door for running raw SQL (still with binding). Ordinary CRUD in the ORM and heavy analysis in SQL, mixed in one project, is common.

    
⑦ 언제 ORM이 짐이 되나⑦ When an ORM becomes a burden

      
데이터가 크고 질의가 복잡해 생성된 SQL을 늘 들여다봐야 할 때, 읽기 전용 분석 · 보고서 중심일 때, 팀이 SQL에 능숙하고 객체 모델이 얇을 때. 이때는 쿼리 빌더나 SQL 파일 + 얇은 매핑이 더 낫기도 합니다. 반대로 CRUD 위주의 업무 앱에서는 ORM이 생산성을 크게 올립니다.

      
When data is large and queries complex so that you must always inspect the generated SQL, when the work is read-only analysis and reports, or when the team is fluent in SQL and the object model is thin, a query builder or SQL files with a thin mapping may be better. In CRUD-heavy business apps, by contrast, an ORM raises productivity a lot.

    
⑧ 이 모형이 생략한 것⑧ What this model leaves out

      
여기서는 질의 횟수와 왕복 시간만 셌습니다. 실제로는 DB 안에서 걸리는 시간 · 캐시 · 연결 풀 대기 · 객체 생성 비용이 더해지며, JOIN은 부모 행이 반복되어 전송량이 늘 수 있습니다. 변경 추적 · 캐스케이드 삭제 · 낙관적 잠금은 다루지 않았습니다.

      
Only query counts and round-trip time are counted here. In reality time inside the DB, caches, pool waits and object-creation cost add up, and a JOIN repeats parent rows and can enlarge the transfer. Change tracking, cascading deletes and optimistic locking are not covered.
