🦀 Rust: 메모리 안전을 컴파일러가 지킨다Rust: memory safety kept by the compiler

Rust 는 C · C++ 만큼 빠르고 GC 도 없지만, 소유권과 빌림 규칙으로 메모리 오류와 데이터 경쟁을 컴파일 단계에서 막는 언어입니다. C 에서 실행 중에야 드러나던 버그가 Rust 에서는 컴파일 오류가 됩니다. 문법 입문은 건너뛰고 소유권 · 빌림 · 수명 · 트레이트 · 동시성처럼 중급의 문턱이 되는 개념을 컴파일해 본 코드로 설명합니다.

Rust is as fast as C and C++ and has no GC, yet its ownership and borrowing rules stop memory errors and data races at compile time. Bugs that C reveals only at run time become compile errors in Rust. Skipping syntax basics, this page explains the concepts that form the intermediate threshold — ownership, borrowing, lifetimes, traits and concurrency — with code that was actually compiled.

코드와 출력은 제작 환경(rustc 1.97, 2021 에디션, Linux 64비트)에서 실행한 결과입니다. 오류 문구는 컴파일러 버전에 따라 조금 다를 수 있습니다. 시연은 개념 설명용 모형입니다.

Code and output come from running rustc 1.97 (2021 edition) on 64-bit Linux in the authoring environment; error wording may vary slightly between compiler versions. The demo is a conceptual model.

    ① 소유권: 값마다 주인은 하나, 주인이 떠나면 drop① Ownership: one owner per value, dropped when the owner leaves
    

    모든 값에는 주인(owner) 변수가 딱 하나 있습니다. 주인이 범위를 벗어나면 값은 자동으로 drop(해제)됩니다. 대입이나 함수 인자로 넘기면 기본은 이동(move)이라서 주인이 바뀌고 원래 변수는 쓸 수 없습니다. 그래서 GC 없이도 누수 · 이중 해제 · 해제 후 사용이 생기지 않습니다. C++ 의 RAII 와 같은 생각을 언어가 강제하는 셈입니다. 아래의 Drop 구현은 해제 순간을 출력해 보여 줍니다.
    Every value has exactly one owner variable. When the owner goes out of scope the value is dropped (freed) automatically. Assigning or passing a value moves it by default: ownership changes and the old variable can no longer be used. So without a GC there are no leaks, double frees or uses after free. It is C++'s RAII, enforced by the language. The Drop implementation below prints the moment each value is freed.
    

    struct Res(&'static str);

impl Drop for Res {
    fn drop(&mut self) {
        println!("drop {}", self.0);

        println!("inner end");

    ② 빌림 규칙: 읽기 여럿 또는 쓰기 하나② The borrowing rule: many readers or one writer
    

    소유권을 넘기지 않고 값을 쓰려면 빌립니다(참조). &T 읽기 빌림은 동시에 여럿, &mut T 쓰기 빌림은 한 번에 하나만 가능하고 둘은 섞일 수 없습니다. 이 규칙 하나가 반복 중 컬렉션 변경, 재할당 뒤의 매달린 포인터, 스레드 간 데이터 경쟁을 컴파일 단계에서 막습니다. 빌림은 마지막으로 쓰인 곳까지만 살아 있으므로(NLL), 읽기 빌림을 다 쓴 뒤에는 쓰기 빌림을 할 수 있습니다.
    To use a value without taking ownership, you borrow it (a reference). Many &T shared borrows may exist at once, or exactly one &mut T mutable borrow, never both. This single rule stops mutating a collection while iterating it, dangling pointers after reallocation, and data races between threads, all at compile time. A borrow lives only until its last use (NLL), so once the shared borrows are done a mutable borrow is allowed.
    

    fn total(xs: &[i32]) -> i32 {
    xs.iter().sum()
}

fn double_all(xs: &mut Vec<i32>) {
    for x in xs.iter_mut() {
        *x *= 2;
    }
}

fn main() {
    let mut v = vec![1, 2, 3];
    let a = &v;
    let b = &v;                 // 읽기 빌림은 여럿 가능
    println!("{} {}", total(a), b.len());
    double_all(&mut v);         // a, b 를 더 쓰지 않으므로 이제 쓰기 빌림 가능
    println!("{:?}", v);
}

    ③ 수명('a): 참조가 얼마나 오래 유효한가③ Lifetimes ('a): how long a reference is valid
    

    참조를 돌려주는 함수는 결과가 어느 입력에서 빌려 온 것인지 컴파일러에 알려야 할 때가 있습니다. 'a 같은 수명 표기는 "결과는 두 입력 중 더 짧게 사는 쪽만큼 유효하다"는 관계를 적는 것이지 수명을 늘리는 것이 아닙니다. 대부분은 생략 규칙으로 쓰지 않아도 되고, 참조를 담는 구조체나 입력이 둘 이상일 때 필요합니다.
    A function returning a reference sometimes has to tell the compiler which input the result borrows from. A lifetime annotation like 'a states a relationship ("the result is valid as long as the shorter-lived input"); it does not extend anything. Elision rules make it unnecessary most of the time; you need it for structs holding references or when there are several inputs.
    

    fn longest<'a>(a: &'a str, b: &'a str) -> &'a str {

    ④ null 과 예외 대신 Option · Result 와 ?④ Option, Result and ? instead of null and exceptions
    

    Rust 에는 null 이 없습니다. 없을 수도 있는 값은 Option<T>(Some/None), 실패할 수 있는 결과는 Result<T, E>(Ok/Err)로 타입에 드러납니다. 처리하지 않으면 값을 꺼낼 수 없으니 "확인을 깜빡함"이 사라집니다. ? 연산자는 Err 면 그 자리에서 호출자에게 돌려주는 짧은 표기입니다. 복구할 수 없는 버그에만 panic!을 씁니다.
    Rust has no null. A value that may be absent is an Option<T> (Some/None); a result that may fail is a Result<T, E> (Ok/Err), visible in the type. You cannot get at the value without handling the other case, so "forgot to check" disappears. The ? operator returns an Err to the caller on the spot. panic! is only for unrecoverable bugs.
    

    use std::num::ParseIntError;

fn parse_kv(s: &str) -> Result<i32, ParseIntError> {
    let n: i32 = s.trim().parse()?;     // 실패하면 여기서 바로 Err 를 돌려줌
    Ok(n * 1000)
}

fn find(ids: &[&str], key: &str) -> Option<usize> {
    ids.iter().position(|x| *x == key)
}

fn main() {
    println!("{:?}", parse_kv(" 22 "));
    println!("{:?}", parse_kv("22kV"));
    let ids = ["T1", "B1", "C1"];
    match find(&ids, "B1") {
        Some(i) => println!("found at {i}"),
        None => println!("none"),
    }
    println!("{}", find(&ids, "X9").map_or(-1, |i| i as i32));
}

    ⑤ enum 과 match: 빠짐없는 경우 나누기⑤ enum and match: exhaustive case analysis
    

    Rust 의 enum은 변형마다 다른 데이터를 담을 수 있는 합 타입입니다. match는 모든 변형을 다루지 않으면 컴파일이 안 되므로, 나중에 변형을 하나 추가하면 고쳐야 할 곳을 컴파일러가 전부 알려 줍니다. 가드(if)와 구조 분해도 함께 씁니다. 상태 기계나 프로토콜 메시지를 표현하기 좋습니다.
    A Rust enum is a sum type whose variants can carry different data. A match that misses a variant does not compile, so when you add a variant later the compiler lists every place to fix. Guards (if) and destructuring work alongside. It suits state machines and protocol messages.
    

    #[derive(Debug)]
enum Breaker {
    Closed { load_a: f64 },

        Breaker::Tripped("overcurrent".into()),

    for b in &all {

    ⑥ 트레이트와 제네릭: 상속 대신 능력⑥ Traits and generics: capabilities instead of inheritance
    

    클래스 상속이 없고, 트레이트(trait)로 "이 타입은 이런 일을 할 수 있다"를 정의해 각 타입에 구현합니다(기본 구현도 가능). 제네릭 함수 fn f<T: Asset>는 타입마다 따로 컴파일되어(정적 디스패치, 비용 없음), Box<dyn Asset>은 실행 중 vtable 로 고르는 동적 디스패치입니다. 서로 다른 타입을 한 목록에 담을 때만 dyn을 씁니다.
    There is no class inheritance. A trait defines "this type can do this", and each type implements it (default methods are allowed). A generic function fn f<T: Asset> is compiled separately per type (static dispatch, no cost), while Box<dyn Asset> picks the method at run time through a vtable (dynamic dispatch). Use dyn only to put different types in one list.
    

    trait Asset {
    fn id(&self) -> String;
    fn risk(&self) -> f64;
    fn label(&self) -> String {                 // 기본 구현
        format!("{} (risk {:.2})", self.id(), self.risk())
    }
}

struct Transformer { name: String, age: u32 }
struct Cable { km: f64 }

impl Asset for Transformer {
    fn id(&self) -> String { self.name.clone() }
    fn risk(&self) -> f64 { self.age as f64 / 40.0 }
}

impl Asset for Cable {
    fn id(&self) -> String { format!("cable {}km", self.km) }
    fn risk(&self) -> f64 { 0.1 }
}

fn riskiest<T: Asset>(items: &[T]) -> Option<&T> {   // 정적 디스패치
    items.iter().max_by(|a, b| a.risk().total_cmp(&b.risk()))
}

fn main() {
    let ts = vec![
        Transformer { name: "T1".into(), age: 12 },
        Transformer { name: "T2".into(), age: 30 },
    ];
    println!("{}", riskiest(&ts).unwrap().label());
    let mixed: Vec<Box<dyn Asset>> = vec![       // 동적 디스패치
        Box::new(Cable { km: 2.5 }),
        Box::new(Transformer { name: "T3".into(), age: 20 }),
    ];
    for a in &mixed {
        println!("{}", a.label());
    }
}

    ⑦ 반복자와 클로저: 추상화의 비용이 0⑦ Iterators and closures: zero-cost abstraction
    

    iter().filter().map().collect() 같은 반복자 체인은 게으르게(lazy) 동작하고 컴파일러가 손으로 쓴 루프와 같은 기계어로 줄여 줍니다(zero-cost abstraction). 클로저는 주변 변수를 읽기 빌림(Fn) · 쓰기 빌림(FnMut) · 소유(FnOnce, move) 중 필요한 만큼만 붙잡습니다. 이 구분이 스레드로 넘길 때 중요해집니다.
    Iterator chains such as iter().filter().map().collect() are lazy and compile down to the same machine code as a hand-written loop (zero-cost abstraction). A closure captures surrounding variables only as much as it needs: shared borrow (Fn), mutable borrow (FnMut) or ownership (FnOnce, move). The distinction matters when handing a closure to a thread.
    

    fn main() {

    tick();
    tick();
    println!("{count}");
    let names: Vec<String> = (1..=3).map(|i| format!("T{i}")).collect();
    println!("{}", names.join(","));
}

    ⑧ 스마트 포인터: Box · Rc · RefCell⑧ Smart pointers: Box, Rc, RefCell
    

    Box<T>는 값을 힙에 두는 단일 소유자 포인터(재귀 타입에 필요), Rc<T>는 참조 횟수로 주인을 여럿 두는 포인터(스레드 간에는 Arc), RefCell<T>은 빌림 규칙을 컴파일 대신 실행 중에 검사해 공유 상태 안을 바꿀 수 있게 합니다(내부 가변성). 그래프처럼 소유 관계가 한 줄로 서지 않는 구조에 씁니다. Rc 순환은 누수가 되니 역방향은 Weak로 둡니다.
    Box<T> is a single-owner pointer that puts a value on the heap (needed for recursive types); Rc<T> allows several owners via a reference count (Arc across threads); RefCell<T> checks the borrowing rule at run time instead of compile time, so shared state can be mutated (interior mutability). Use them for structures such as graphs where ownership is not a single line. Rc cycles leak, so make back-links Weak.
    

    use std::cell::RefCell;
use std::rc::Rc;

#[derive(Debug)]
enum List {
    Node(i32, Box<List>),       // 재귀 타입은 크기를 알 수 없어 Box 로 힙에
    Nil,
}

fn sum(l: &List) -> i32 {
    match l {
        List::Node(v, next) => v + sum(next),
        List::Nil => 0,
    }
}

fn main() {
    let l = List::Node(1, Box::new(List::Node(2, Box::new(List::Nil))));
    println!("{:?} sum={}", l, sum(&l));

    let shared = Rc::new(RefCell::new(vec![10]));   // 주인 여럿 + 실행 중 빌림 검사
    let a = Rc::clone(&shared);
    let b = Rc::clone(&shared);
    a.borrow_mut().push(20);
    b.borrow_mut().push(30);
    println!("{:?} owners={}", shared.borrow(), Rc::strong_count(&shared));
    drop(a);
    println!("owners={}", Rc::strong_count(&shared));
}

    ⑨ 겁 없는 동시성: Send · Sync · Arc<Mutex>⑨ Fearless concurrency: Send, Sync, Arc<Mutex>
    

    스레드로 넘길 수 있는 타입은 Send, 여러 스레드가 함께 읽을 수 있는 타입은 Sync 라는 표시(트레이트)를 컴파일러가 자동으로 붙이고 검사합니다. 그래서 Rc를 스레드로 넘기거나 잠금 없이 공유 값을 바꾸는 코드는 컴파일되지 않고, 데이터 경쟁이 없다는 것이 보장됩니다(교착 상태 같은 논리 오류까지 막지는 않습니다). thread::scope는 지역 데이터를 빌려 쓰는 스레드를 안전하게 만듭니다. 비동기 I/O 는 async/.await + tokio 같은 런타임으로 합니다(동시 접속 처리 참고).
    The compiler automatically marks and checks types that may move to another thread (Send) and that several threads may read together (Sync). So handing an Rc to a thread, or mutating shared data without a lock, does not compile, and data races are ruled out (logic errors such as deadlocks are not). thread::scope lets threads safely borrow local data. Asynchronous I/O uses async/.await with a runtime such as tokio (see Handling many connections).
    

    use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let counter = Arc::new(Mutex::new(0));
    let mut handles = Vec::new();
    for _ in 0..4 {
        let c = Arc::clone(&counter);
        handles.push(thread::spawn(move || {
            for _ in 0..1000 {
                *c.lock().unwrap() += 1;
            }
        }));
    }
    for h in handles {
        h.join().unwrap();
    }
    println!("{}", *counter.lock().unwrap());

    let data = vec![1, 2, 3, 4, 5, 6];
    let (left, right) = data.split_at(3);
    let (a, b) = thread::scope(|s| {          // 범위 스레드: 지역 데이터를 빌려 씀
        let ha = s.spawn(|| left.iter().sum::<i32>());
        let hb = s.spawn(|| right.iter().sum::<i32>());
        (ha.join().unwrap(), hb.join().unwrap())
    });
    println!("{a} + {b} = {}", a + b);
}

    흔한 함정 5가지: 증상 → 원인 → 해결Five common pitfalls: symptom → cause → fix
    
  
    ⚠ 문자열에 s[0] 을 쓸 수 없다⚠ You cannot write s[0] on a string
    

    증상. C · Python 처럼 첫 글자를 꺼내려 했더니 컴파일 오류가 납니다.
    Symptom. Taking the first character as in C or Python is a compile error.
    

    let s = String::from("변압기");
let c = s[0];
// error[E0277]: the type `str` cannot be indexed by `{integer}`
    

    원인. String은 UTF-8 바이트입니다. 한글 한 글자는 3바이트라서 "0번째 바이트"는 글자가 아닙니다. 위치로 꺼내는 비용도 O(1) 이 아니라서 아예 막아 두었습니다.
    Cause. A String is UTF-8 bytes. A Hangul character is 3 bytes, so "byte 0" is not a character, and reaching a character by position is not O(1) anyway, so indexing is simply disallowed.

    ⚠ 정수 오버플로: 디버그는 panic, 릴리스는 조용히 감김⚠ Integer overflow: panics in debug, wraps silently in release
    

    증상. 개발 중에는 attempt to add with overflow 로 멈추던 코드가 릴리스 빌드에서는 엉뚱한 값을 냅니다.
    Symptom. Code that stopped with attempt to add with overflow during development gives a wrong value in a release build.
    

    let a: u8 = 250;

    ⚠ unwrap() 남발⚠ unwrap() everywhere
    

    증상. 입력이 조금만 이상해도 프로그램이 panicked at … called `Result::unwrap()` on an `Err` value 로 끝납니다.
    Symptom. The slightest odd input ends the program with panicked at … called `Result::unwrap()` on an `Err` value.
    

    let n: i32 = "22kV".parse().unwrap();
// panicked: called `Result::unwrap()` on an `Err` value: ParseIntError { kind: InvalidDigit }
    

    원인. unwrap은 "절대 실패하지 않는다"는 단언입니다. 외부 입력 · 파일 · 네트워크처럼 실패가 정상인 곳에 쓰면 예외를 잡지 않은 것과 같습니다.
    Cause. unwrap asserts "this never fails". Using it where failure is normal (external input, files, network) is like leaving an exception uncaught.
    

    해결. match · if let · unwrap_or · ?로 다루고, 정말 불가능한 경우에만 이유를 적어 expect("…")를 씁니다.
    Fix. Handle it with match, if let, unwrap_or or ?, and keep expect("…") with a reason for truly impossible cases.
    

    fn main() {
    let inputs = ["22", "22kV", "154"];
    for s in inputs {
        match s.parse::<i32>() {
            Ok(n) => println!("{s} -> {n}"),
            Err(e) => println!("{s} -> error: {e}"),
        }
    }
    let n: i32 = "x".parse().unwrap_or(0);
    println!("{n}");
}
    22 -> 22
22kV -> error: invalid digit found in string
154 -> 154
0
    
  
    
  
    ⚠ RefCell 은 실행 중에 panic 한다⚠ RefCell panics at run time
    

    증상. 컴파일은 되는데 실행하면 already borrowed: BorrowMutError 로 멈춥니다.
    Symptom. It compiles, but running it stops with already borrowed: BorrowMutError.
    

    let c = std::cell::RefCell::new(vec![1]);
let r = c.borrow();
c.borrow_mut().push(2);   // r 이 아직 살아 있음 → 실행 중 panic
println!("{}", r.len());
    

    원인. RefCell은 빌림 규칙을 없애는 것이 아니라 검사를 실행 시간으로 미룰 뿐입니다. 읽기 빌림(r)이 살아 있는 동안 쓰기 빌림을 요청했습니다.
    Cause. RefCell does not remove the borrowing rule; it only moves the check to run time. A mutable borrow was requested while the shared borrow r was still alive.
    

    해결. 빌림을 짧은 블록 안에 가두거나 필요한 값만 복사해 두고 반납합니다. 실패를 처리하고 싶으면 try_borrow_mut().
    Fix. Confine the borrow to a short block, or copy out what you need and release it. Use try_borrow_mut() to handle failure.
    

    use std::cell::RefCell;

fn main() {
    let c = RefCell::new(vec![1]);
    {
        let r = c.borrow();
        println!("len {}", r.len());
    }                               // r 이 여기서 반납됨
    c.borrow_mut().push(2);
    println!("{:?}", c.borrow());
    println!("{}", c.try_borrow_mut().is_ok());
}
    len 1
[1, 2]
true
    
  
    
  
    ⚠ 반복하면서 컬렉션 바꾸기⚠ Changing a collection while iterating it
    

    증상. 다른 언어에서 하던 대로 루프 안에서 push · remove 를 하면 컴파일 오류가 납니다.
    Symptom. Calling push or remove inside the loop, as in other languages, is a compile error.
    

    let mut v = vec![3, -1, 4];
for x in &v {
    if *x < 0 { v.push(0); }    // error[E0502]: cannot borrow `v` as mutable
}
    

    원인. for x in &v가 루프 내내 읽기 빌림을 쥐고 있습니다. 그 사이의 변경은 다른 언어에서는 ConcurrentModificationException이나 건너뛴 원소 같은 버그가 되는 바로 그 일입니다.
    Cause. for x in &v holds a shared borrow for the whole loop. Changing v meanwhile is exactly what becomes a ConcurrentModificationException or skipped elements in other languages.
    

    해결. 조건으로 지울 때는 retain, 추가할 것은 따로 모았다가 루프 뒤에 extend, 그 밖에는 인덱스 루프를 씁니다.
    Fix. Use retain to remove by condition, collect additions and extend after the loop, or fall back to an index loop.
    

    fn main() {
    let mut v = vec![3, -1, 4, -5, 9];
    v.retain(|&x| x >= 0);                  // 조건에 맞는 것만 남김
    println!("{:?}", v);
    let extra: Vec<i32> = v.iter().map(|x| x * 10).collect();
    v.extend(extra);                        // 다 읽고 나서 한 번에 추가
    println!("{:?}", v);
}
    [3, 4, 9]
[3, 4, 9, 30, 40, 90]
