🧩 프로토콜을 대신 말해 주는 것:
드라이버와 표준 APISpeaking the protocol for you:
drivers and standard APIs

실제 코드에서는 와이어 프로토콜의 바이트를 만들지 않고 드라이버를 씁니다. 코드는 SQL 글자를 쓰고, 값을 넘기고, 결과를 받습니다. 이 단순한 호출에서 가장 흔한 사고가 SQL 인젝션이고, 가장 중요한 습관이 바인딩과 트랜잭션입니다. 둘을 직접 일으켜 봅니다.

Real code does not build wire-protocol bytes; it uses a driver. The code writes SQL text, passes values and receives results. The commonest accident in that simple call is SQL injection, and the most important habits are binding and transactions. Trigger both yourself.

아래 SQL은 이 페이지 안의 작은 엔진이 실제로 해석 · 실행합니다(인젝션 입력도 진짜로 동작합니다). 가상 데이터이니 DROP을 눌러도 새로고침하면 돌아옵니다. 결과는 tests/db.test.mjs로 확인합니다.

The SQL below is really parsed and run by the small engine in this page (injection inputs genuinely work). It is fictional data, so a DROP is undone by reloading. tests/db.test.mjs checks the results.

드라이버는 번역기, 표준 API는 공통 손잡이A driver is a translator; a standard API is a common handle

앱 코드가 와이어 프로토콜의 바이트를 직접 만들지 않습니다. 드라이버가 그 일을 하고, 앱은 언어마다 정해진 표준 API(파이썬 DB-API, 자바 JDBC, 범용 ODBC)의 같은 함수만 부릅니다. DB를 바꿔도 앱의 호출은 거의 그대로이고 드라이버만 바뀝니다. 다만 SQL 문법(방언)의 차이는 표준 API가 감춰 주지 않습니다.

App code does not build wire-protocol bytes itself. A driver does, and the app just calls the same functions of the language's standard API (Python DB-API, Java JDBC, universal ODBC). Switch DBs and the app's calls stay nearly the same while the driver changes. The standard API does not hide differences in SQL dialects, though.

LAB 1

글자 이어붙이기 vs 바인딩: SQL 인젝션String concatenation vs binding: SQL injection

업무 규칙: "이름으로 설비를 찾되 건전도 60 이상만 보여 준다". 왼쪽은 입력을 SQL 글자에 이어붙이고, 오른쪽은 값을 따로 바인딩합니다. 같은 입력을 양쪽에 보냅니다. 입력 칸에 직접 써 봐도 됩니다.

Business rule: "look up an asset by name, but show only health 60 or more". The left side concatenates the input into the SQL text; the right side binds the value separately. The same input goes to both. You can type your own too.

트랜잭션 경계: 두 단계를 한 덩어리로Transaction boundary: two steps as one unit

  
설비 T2를 Sub-B로 옮기고(1) 이력 표에 기록하는(2) 두 단계가 있습니다. (이 DB에는 history 표가 없어서 2단계가 실패합니다.) 문장마다 바로 확정하는 자동 커밋이면 1단계만 남고, BEGIN … COMMIT으로 묶으면 실패 시 ROLLBACK으로 되돌아갑니다.

  
Two steps: move asset T2 to Sub-B (1), then record it in a history table (2). (This DB has no history table, so step 2 fails.) With autocommit, each statement is final immediately and only step 1 survives; wrapped in BEGIN … COMMIT a failure triggers ROLLBACK and everything is undone.

  

    
    
  

  






  
알아 둘 원리Principles worth knowing

  

    
① 표준 API가 정한 흐름① The flow a standard API sets

      
연결(connect) → 문장 준비 → 값 바인딩 → 실행(execute) → 결과 가져오기(fetch) → 확정(commit) → 닫기(close). 언어는 달라도 모양이 같습니다. ODBC(1992, 마이크로소프트 주도)는 언어를 가리지 않는 C 인터페이스이고, JDBC(1997)는 자바용, 파이썬은 DB-API 2.0(PEP 249)이 같은 일을 합니다. 요즘 서버리스 환경에서는 HTTP로 질의하는 드라이버도 나왔습니다(최근 흐름).

      
connect → prepare → bind values → execute → fetch → commit → close. Languages differ but the shape is the same. ODBC (1992, led by Microsoft) is a language-neutral C interface, JDBC (1997) is for Java, and Python's DB-API 2.0 (PEP 249) does the same job. In serverless settings there are now drivers that query over HTTP (Recent trends).

    
② 바인딩이 인젝션을 막는 이유② Why binding stops injection

      
(가)에서 입력의 따옴표는 SQL의 따옴표와 구분되지 않아, 입력이 명령의 일부가 됩니다. (나)에서는 SQL 틀과 값이 다른 칸으로 따로 갑니다. 와이어 페이지의 Parse와 Bind가 그것입니다. 서버는 틀을 먼저 해석해 구조를 확정한 뒤 값을 끼우므로, 값이 어떤 글자여도 데이터일 뿐입니다. 값을 직접 걸러 내는 방식(따옴표 지우기)은 빠뜨리기 쉬워 권하지 않습니다.

      
In (a) the quote in the input is indistinguishable from SQL's own quotes, so the input becomes part of the command. In (b) the SQL template and the values go in separate fields: Parse and Bind on the wire page. The server parses the template first and fixes its structure, then slots the values in, so whatever the characters, a value is only data. Filtering values by hand (stripping quotes) is easy to get wrong and not recommended.

    
③ 바인딩으로 안 되는 것③ What binding cannot do

      
값 자리에만 쓸 수 있습니다. 표 이름 · 열 이름 · 정렬 방향 같은 구조는 바인딩할 수 없으니, 사용자가 고르게 한다면 허용 목록(예: {"health","name"} 중 하나만)에서 골라 써야 합니다. 또 인젝션을 막아도 "이 사용자가 이 행을 봐도 되는가"는 별개의 문제라, 권한 확인은 서비스나 DB 쪽에서 해야 합니다.

      
It works only in value positions. Structure such as table names, column names and sort direction cannot be bound; if users choose them, pick from an allow-list (say, only {"health","name"}). And stopping injection does not answer whether this user may see this row; that check belongs in a service or the DB.

    
④ 커서와 가져오기④ Cursors and fetching

      
execute 뒤에 결과가 한꺼번에 메모리로 오는 것이 아닙니다. 드라이버는 커서로 행을 조금씩(fetchmany(100)) 가져올 수 있어, 수백만 행도 메모리를 터뜨리지 않고 훑습니다. 기본 설정이 "전부 한꺼번에"인 드라이버도 있으니, 큰 결과에는 서버 쪽 커서 옵션을 확인하세요.

      
The result does not necessarily arrive in memory at once after execute. A driver can pull rows bit by bit with a cursor (fetchmany(100)), scanning millions of rows without exhausting memory. Some drivers default to "all at once", so check the server-side cursor option for big results.

    
⑤ 트랜잭션과 자동 커밋⑤ Transactions and autocommit

      
여러 문장이 한 덩어리로 성공하거나 실패해야 할 때 트랜잭션으로 묶습니다(LAB 2). 드라이버마다 기본값이 달라(JDBC는 자동 커밋이 기본, 파이썬 DB-API는 보통 첫 문장에서 트랜잭션이 시작) 혼란이 잦습니다. 길게 열어 둔 트랜잭션은 다른 사람의 쓰기를 막으므로 짧게 열고 빨리 닫습니다. 두 사람이 동시에 같은 행을 고치는 문제는 격리 수준과 행 잠금이 다룹니다.

      
When several statements must succeed or fail as a unit, wrap them in a transaction (Lab 2). Drivers differ in defaults (JDBC autocommits by default; Python DB-API usually starts a transaction at the first statement), which causes confusion. A long-open transaction blocks others' writes, so open late, close early. Two people editing the same row at once is handled by isolation levels and row locks.

    
⑥ 접속 정보는 비밀이다⑥ Connection details are secrets

      
연결 문자열에는 주소 · 계정 · 비밀번호가 들어 있습니다. 코드나 저장소에 적지 말고 환경 변수 · 비밀 관리 서비스에 두며, 계정에는 필요한 권한만(읽기 전용 · 해당 표만) 줍니다. 앱 서버가 이 계정을 쥐고 있으니, 앱이 뚫리면 이 권한만큼 뚫립니다. 그래서 브라우저나 외부에는 이 계정을 절대 주지 않고, 사이에 서비스를 둡니다(다음 단계).

      
A connection string holds address, account and password. Do not put it in code or a repository; keep it in environment variables or a secrets service, and give the account only the privileges needed (read-only, just those tables). The app server holds this account, so a breach of the app is a breach of those privileges. Never hand it to a browser or outsider; put a service in between (next step).

    
⑦ 방언: 표준 API가 못 감추는 것⑦ Dialects: what a standard API cannot hide

      
값 자리표시자부터 ?(JDBC · SQLite) · %s(psycopg) · $1(PostgreSQL 자체) · :name(Oracle)로 다르고, LIMIT 3 / TOP 3 / FETCH FIRST 3 ROWS, 날짜 함수, 자동 증가 열의 표기가 DB마다 다릅니다. SQL을 직접 쓰는 이 계단에서는 DB를 바꾸는 비용이 크고, 이것이 다음 계단인 쿼리 빌더 · ORM이 나온 이유 중 하나입니다.

      
Even the placeholder differs: ? (JDBC, SQLite), %s (psycopg), $1 (PostgreSQL itself), :name (Oracle); LIMIT 3 / TOP 3 / FETCH FIRST 3 ROWS, date functions and auto-increment syntax vary by DB. Writing SQL by hand at this rung makes switching DBs costly, one reason the next rung, query builders and ORMs, arose.

    
⑧ 이 모형이 생략한 것⑧ What this model leaves out

      
여기의 SQL 엔진은 실제 DB와 달리 문장 구조를 한 번에 해석하므로 "틀 먼저, 값 나중" 서버 동작을 그대로 흉내 내지는 않고, 값이 글자로 해석되지 않는다는 결과만 보여 줍니다. 저장 프로시저 · 준비된 문장 캐시 · 배치 실행 · 격리 수준 · 데드락은 다루지 않았습니다.

      
Unlike a real DB, this SQL engine does not truly parse a template first and slot values in later; it only demonstrates the outcome that a value is never read as SQL text. Stored procedures, prepared-statement caches, batching, isolation levels and deadlocks are not covered.
