같은 데이터, 여러 모양There is more than one kind of database:
the same data, many shapes

"DB에 접근한다"는 말을 풀면 두 가지 질문이 나옵니다. 데이터를 어떤 모양으로 담았는가, 그리고 어떤 통로로 꺼내는가. 이 메뉴는 두 번째 질문을 파일을 직접 여는 방법에서 최근의 API · AI 에이전트까지 한 계단씩 올라가며 봅니다. 첫 페이지는 첫 번째 질문, 곧 "데이터베이스"라는 말의 범위를 넓게 잡습니다.

"Accessing a database" breaks into two questions: in what shape is the data kept, and through what channel do you get it out. This menu climbs the second question one rung at a time, from opening a file directly to today's APIs and AI agents. This first page takes the first question, widening what "database" can mean.

모든 실습은 이 사이트의 가상 데이터(변전소 3 · 설비 12)와, 브라우저 안에서 도는 작은 SQL 엔진으로 실제 계산합니다. 실제 DB 제품이 아니며 인덱스 · 제약 · 동시성은 없습니다. 맞는지는 tests/db.test.mjs로 확인합니다.

Every lab computes for real on this site's fictional data (3 substations, 12 assets) with a small SQL engine running in the browser. It is not a real DB product and has no indexes, constraints or concurrency. tests/db.test.mjs checks that it is right.

데이터베이스를 나누는 세 가지 축Three axes for telling databases apart

  
"데이터베이스"는 한 가지 물건이 아니라, 데이터를 오래, 믿을 수 있게, 다시 찾을 수 있게 보관하는 모든 방법을 가리킵니다. 이름이 낯선 제품을 만나면 아래 세 축으로 어디쯤인지 짚어 보세요.

  
"Database" is not one thing; it covers every way of keeping data durably, reliably and findably. When you meet an unfamiliar product, place it on these three axes.

  

    
① 데이터 모델: 어떤 모양으로 담나① Data model: what shape

      
관계형(표 + SQL), 문서(JSON 덩어리), 키-값(이름표로 꺼내기), 와이드 컬럼, 그래프(점과 선), 시계열(시간순 측정값), 벡터(의미가 비슷한 것 찾기). 위 실습이 이 축입니다. 한 제품이 여러 모델을 함께 지원하기도 합니다(PostgreSQL의 JSON · 확장).

      
Relational (tables + SQL), document (JSON blobs), key-value (fetch by name), wide-column, graph (nodes and edges), time-series (measurements in time order), vector (find things of similar meaning). The lab above is this axis. One product may support several (PostgreSQL with JSON and extensions).

    
② 저장 엔진: 안에서 어떻게 저장하나② Storage engine: how it stores inside

      
행 단위로 모으면(행 저장) 한 건을 읽고 쓰기에 좋고, 열 단위로 모으면(열 저장) 수억 건의 한 열을 합산하기에 좋습니다. 디스크 위의 B-트리는 읽기에, LSM 트리는 대량 쓰기에 유리하고, 메모리 DB는 빠른 대신 전원이 나갈 때를 따로 대비해야 합니다. 다음 글에서 페이지와 B-트리를 직접 봅니다.

      
Storing by row suits reading and writing single records; storing by column suits summing one column over hundreds of millions. A disk B-tree favours reads, an LSM tree favours heavy writes, and an in-memory DB is fast but must plan separately for power loss. The next page looks at pages and B-trees directly.

    
③ 배치: 어디서 돌아가나③ Deployment: where it runs

      
프로그램 안에 들어 있는 임베디드(SQLite), 따로 떠 있는 서버(PostgreSQL · MySQL), 여러 대에 나뉜 분산(Cassandra · CockroachDB), 운영을 맡겨 쓰는 관리형 클라우드(RDS · BigQuery). 접근 방법은 이 배치가 정합니다. 같은 프로세스 안이면 함수 호출이고, 서버면 소켓 위의 프로토콜입니다.

      
Embedded inside the program (SQLite), a separate server (PostgreSQL, MySQL), distributed across machines (Cassandra, CockroachDB), or a managed cloud service (RDS, BigQuery). Deployment decides how you reach it: inside the same process it is a function call, with a server it is a protocol over a socket.

    
ACID와 BASEACID and BASE

      
ACID는 트랜잭션의 약속입니다: 모두 반영되거나 하나도 안 되고(원자성), 규칙을 깨지 않으며(일관성), 동시에 해도 순서대로 한 것처럼 보이고(격리성), 확정한 것은 전원이 나가도 남습니다(지속성). 분산 환경에서 이를 일부 느슨하게 해 확장성을 얻는 쪽을 BASE(가용성 우선, 결과적 일관성)라 부릅니다. 어느 쪽이 옳다기보다 잔액 이체인가, 좋아요 수인가의 문제입니다.

      
ACID is the transaction promise: all or nothing (atomicity), rules stay intact (consistency), concurrent work looks as if done one after another (isolation), and what was committed survives power loss (durability). Loosening some of it in distributed settings to gain scale is called BASE (availability first, eventual consistency). Neither is "right": it depends on whether it is a money transfer or a like counter.

    
CAP: 네트워크가 갈라질 때CAP: when the network splits

      
여러 대에 나뉜 DB는 네트워크가 끊기면 일관성(모든 곳이 같은 값)과 가용성(계속 응답)을 둘 다 지킬 수 없습니다. 은행류는 응답을 늦추더라도 일관성을, 피드류는 조금 낡은 값을 주더라도 응답을 고릅니다. 한 대짜리 DB에서는 이 선택이 드러나지 않습니다.

      
When the network cuts a multi-machine DB in two, it cannot keep both consistency (everywhere sees the same value) and availability (always answers). Banking-style systems delay answers to stay consistent; feed-style systems serve slightly stale values to keep answering. A single-machine DB never faces this choice.

    
"파일"과 "DB"의 차이A "file" versus a "database"

      
CSV 파일도 데이터를 보관합니다. 그러나 두 사람이 동시에 고치면 깨지고, 한 줄을 찾으려면 전부 읽어야 하고, 쓰는 도중 전원이 나가면 반쯤 쓰인 채 남습니다. DB는 이 문제들(동시성 · 인덱스 · 복구)을 엔진이 대신 풀어 주는 것입니다. 그래서 "DB에 접근한다"는 말은 결국 그 엔진의 약속을 어떤 통로로 이용하는가입니다.

      
A CSV file also keeps data. But two people editing at once break it, finding one line means reading everything, and a power cut mid-write leaves it half-written. A DB is the engine solving these (concurrency, indexing, recovery) for you. So "accessing a database" means through which channel you use that engine's promises.

  






  
이 메뉴의 지도: 접근 사다리This menu's map: the access ladder

  
아래로 갈수록 DB에 가까운 직접 접근이고, 위로 갈수록 DB를 감춘 추상화입니다. 위로 올라갈수록 DB 계정이 바깥으로 새지 않아 안전해지고 바뀌는 데 강해지지만, 거치는 단계(왕복)가 늘고 질문의 자유는 줄어듭니다. 각 칸은 해당 페이지로 연결됩니다.

  
Lower rungs are direct access close to the DB; higher rungs are abstractions that hide it. Higher up, DB credentials stay inside and the design copes better with change, but there are more hops and less freedom to ask. Each rung links to its page.
