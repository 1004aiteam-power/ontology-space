🔌 소켓 위의 DB 말투:
와이어 프로토콜The DB's way of talking on a socket:
the wire protocol

DB를 서버로 떼어 내면 앱은 네트워크로 접속합니다. 그러면 TCP 소켓 위에 DB마다 정한 메시지 규칙이 흐릅니다. 보통은 드라이버가 대신 말해 주니 볼 일이 없지만, 한 번 바이트로 보아 두면 드라이버 · 풀 · 인젝션 방지가 왜 그렇게 생겼는지 이해가 쉬워집니다.

Once the DB becomes a server, the app reaches it over the network, and the message rules each DB defines flow over a TCP socket. A driver normally speaks them for you, but seeing them once as bytes makes it easier to understand why drivers, pools and injection defences look the way they do.

서버는 이 페이지 안의 데모용 가짜(브라우저 안의 작은 SQL 엔진)이지만, 메시지의 바이트 형식은 PostgreSQL 프로토콜 v3 그대로입니다. 형식 · 길이 · 왕복 검증은 tests/db.test.mjs가 합니다.

The server is a demo fake inside this page (a small SQL engine in the browser), but the byte format of the messages is PostgreSQL protocol v3 as is. tests/db.test.mjs checks formats, lengths and round trips.

LAB 1

소켓 위를 오가는 DB 메시지DB messages on a socket

DB 서버에 접속하면 소켓이 열리고, 그 바이트 스트림 위로 DB 전용 프로토콜이 흐릅니다. 아래는 PostgreSQL v3 프로토콜의 실제 메시지 형식으로 만든 바이트입니다. 질문을 바꿔 보내고, 메시지를 눌러 바이트가 어떤 뜻인지 보세요.

Connecting to a DB server opens a socket, and a DB-specific protocol flows over that byte stream. Below are bytes built in the real PostgreSQL v3 message format. Change the question, send it, and click a message to see what each byte means.

오간 메시지 (순서대로)Messages exchanged (in order)

    LAB 2

    커넥션 풀: 연결을 매번 새로 맺지 않기Connection pools: not reconnecting every time

    연결 하나를 맺으려면 TCP 3-way handshake, (TLS), 인증이 필요해 질의보다 오래 걸릴 때가 많습니다. 그래서 연결 몇 개를 미리 열어 두고 요청이 돌려 쓰는 것이 풀입니다. 요청이 연결 수보다 많이 몰리면 줄을 섭니다.

    Opening a connection needs a TCP 3-way handshake, (TLS) and authentication, which often takes longer than the query. A pool keeps a few connections open and lends them to requests; when requests outnumber connections, they queue.

    알아 둘 원리Principles worth knowing

    ① 길이를 앞에 적는 메시지① Length-prefixed messages

    모든 메시지는 [종류 1글자][길이 4바이트][내용]입니다. TCP는 바이트의 흐름일 뿐 메시지의 경계를 모르므로(소켓 페이지), 받는 쪽은 길이 칸을 읽고 그만큼을 잘라 한 메시지로 삼습니다. 위 LAB 1 아래 줄이 그것을 직접 해 보입니다. HTTP가 Content-Length로 하는 일을 DB는 모든 메시지에 합니다.

    Every message is [1-letter type][4-byte length][body]. TCP is just a stream of bytes with no idea of message boundaries (Sockets page), so the receiver reads the length and cuts that much as one message. The line under Lab 1 does exactly that. What HTTP does with Content-Length, a DB does on every message.

    ② 접속 단계: 시작 → 인증 → 준비② Connecting: startup → authentication → ready

    클라이언트가 StartupMessage(프로토콜 버전 · 사용자 · 데이터베이스 이름)를 보내면 서버가 인증을 요구합니다(여기서는 생략하고 AuthenticationOk만 보임. 실제로는 SCRAM-SHA-256 등 몇 번 더 오갑니다). 끝나면 서버 설정(ParameterStatus), 취소용 키(BackendKeyData)와 ReadyForQuery("질문하세요")가 옵니다. TLS를 쓰면 이 모든 것이 암호화됩니다.

    The client sends a StartupMessage (protocol version, user, database name) and the server asks for authentication (skipped here, only AuthenticationOk shown; in reality SCRAM-SHA-256 and others add several exchanges). Then come server settings (ParameterStatus), a cancel key (BackendKeyData) and ReadyForQuery ("go ahead"). With TLS, all of it is encrypted.

    ③ 결과는 "표 설명 + 행 + 완료"③ A result is "column info + rows + done"

    RowDescription이 열 이름과 타입을, 이어서 행마다 DataRow가, 마지막에 CommandComplete("SELECT 2")가 옵니다. 행은 하나씩 흘러오므로 큰 결과를 받는 쪽이 스트리밍으로 처리할 수 있습니다(드라이버의 커서). 값은 기본적으로 글자로 오고(여기서도 "90"은 글자 두 개), 받는 쪽이 타입에 맞게 바꿉니다. 오류는 ErrorResponse로 오며 SQLSTATE 코드(42P01 = 없는 표)가 붙습니다.

    RowDescription gives column names and types, then one DataRow per row, and finally CommandComplete ("SELECT 2"). Rows arrive one by one, so a receiver of a large result can stream it (a driver cursor). Values come as text by default (here "90" is two characters) and the receiver converts them to the right type. Errors arrive as ErrorResponse with a SQLSTATE code (42P01 = undefined table).

    ④ 간단한 질의 vs 확장 질의④ Simple query vs extended query

    Q는 SQL 글자 하나에 모든 것이 들어 있어 값도 글자 안에 섞입니다. 확장 질의는 Parse(SQL 틀, 값 자리는 $1) → Bind(값들을 따로) → Execute → Sync로 나뉩니다. 값은 SQL 글자와 다른 칸에 길이를 붙여 가므로 값이 SQL로 해석될 길이 없습니다. 다음 페이지의 "바인딩"이 안전한 이유가 이 구조이고, 같은 틀을 여러 번 쓰면 서버가 계획을 다시 세우지 않아도 됩니다.

    Q holds everything in one piece of SQL text, so values are mixed into it. The extended query splits into Parse (SQL template, $1 for values) → Bind (the values, separately) → Execute → Sync. Values travel in their own field with a length, so there is no way for a value to be read as SQL. This structure is why "binding" on the next page is safe, and reusing a template saves the server re-planning.

    ⑤ DB마다 다른 프로토콜⑤ Every DB has its own protocol

    MySQL은 자기 이진 프로토콜, Redis는 글자 기반 RESP(*2\r\n$3\r\nGET\r\n$8\r\nasset:T1\r\n, 사람이 읽을 수 있음), MongoDB는 BSON 기반 OP_MSG, Neo4j는 Bolt를 씁니다. 그래서 "DB 드라이버"는 DB마다 따로 있고, 프로토콜을 흉내 내는 호환 서버(예: PostgreSQL 호환 서비스)는 같은 드라이버를 그대로 쓸 수 있어서 갈아타기 쉽습니다.

    MySQL has its own binary protocol, Redis uses the text-based RESP (*2\r\n$3\r\nGET\r\n$8\r\nasset:T1\r\n, human-readable), MongoDB uses BSON-based OP_MSG, and Neo4j uses Bolt. So there is one driver per DB, and servers that imitate a protocol (e.g. PostgreSQL-compatible services) can use the same drivers, which makes switching easy.

    ⑥ 풀이 필요한 이유와 한계⑥ Why pools exist, and their limits

    서버는 연결 하나마다 프로세스나 메모리를 쓰므로 동시 연결 수에 상한이 있습니다(PostgreSQL 기본 100). 앱 서버가 수십 대이고 각자 연결을 수십 개 열면 금방 넘칩니다. 그래서 앱 안의 풀 외에 앞에 연결 중계기(PgBouncer 같은 것)를 두어 수천 개의 클라이언트를 수십 개의 서버 연결로 줄여 씁니다. 풀이 너무 커도 서버가 느려지니 작게 잡는 편이 낫습니다. 위 실험에서 풀 크기를 키워도 개선이 멈추는 지점을 찾아 보세요.

    A server spends a process or memory per connection, so there is a cap on concurrent connections (PostgreSQL defaults to 100). Dozens of app servers each opening dozens quickly overflows it. So besides the in-app pool, a connection proxy (like PgBouncer) squeezes thousands of clients into a few dozen server connections. An oversized pool also slows the server, so keep it small. In the lab above, look for where growing the pool stops helping.

    ⑦ 보안: 이 바이트를 누가 볼 수 있나⑦ Security: who can see these bytes

    프로토콜 자체는 암호화하지 않으므로 TLS를 켜야 합니다. 그리고 DB 포트(PostgreSQL 5432)를 인터넷에 직접 열어 두면 누구나 로그인을 시도할 수 있으니, DB는 사설망 안에 두고 앱 서버만 접속하게 하는 것이 기본입니다. 이것이 뒤의 서비스 계층이 필요한 이유의 출발점입니다.

    The protocol itself does not encrypt, so turn on TLS. And leaving the DB port (PostgreSQL 5432) open to the internet lets anyone try to log in, so the baseline is to keep the DB inside a private network with only app servers connecting. That is the starting point for why the service layer later is needed.

    ⑧ 이 모형이 생략한 것⑧ What this model leaves out

    인증 교환 · TLS 협상 · 이진 형식 · COPY(대량 입출력) · 알림(LISTEN/NOTIFY) · 취소 요청 · 파이프라인은 넣지 않았습니다. 풀 실험은 질의를 서버가 동시에 처리할 수 있다고 보고(실제로는 CPU · 디스크가 한계), 대기열은 먼저 온 순서로만 계산한 단순 모형입니다.

    Left out: the authentication exchange, TLS negotiation, binary formats, COPY (bulk I/O), LISTEN/NOTIFY, cancel requests and pipelining. The pool lab assumes the server can run those queries in parallel (in reality CPU and disk are limits) and queues strictly first-come, first-served, a simple model.
