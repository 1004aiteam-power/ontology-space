Git 사용법 · 장애 사례집GIT USAGE · TROUBLESHOOTING

🚑 사고는 난다, 대부분 되돌릴 수 있다:
장애 사례집Accidents happen, most can be undone:
troubleshooting cases

Git 을 쓰다 보면 반드시 만나는 장면들입니다: push 가 거절되고, 병합이 멈추고, 커밋이 사라진 것 같고, 비밀키를 올려 버립니다. 각 사례는 증상 → 원인 → 해결 → 예방 순서이고, 실제 Git · GitHub 의 오류 문장 그대로 터미널에서 직접 고쳐 보게 되어 있습니다.

Scenes you will certainly meet while using Git: a push is rejected, a merge stops, commits seem lost, a secret key gets pushed. Each case goes symptom → cause → fix → prevention, and you fix it yourself in a terminal that shows the real Git and GitHub error wording.

재현 상태와 성공 판정은 tests/git.test.mjs가 모든 사례마다 자동으로 확인합니다 (처음엔 미해결 → 정답을 치면 해결). 터미널은 이 페이지 안의 시뮬레이터라 실제 컴퓨터에는 영향이 없습니다.

For every case tests/git.test.mjs automatically checks the staged problem and the success test (unsolved at first → solved after the answer). The terminal is a simulator in this page and affects nothing on your computer.

되돌리기 결정표Undo decision table

사고가 났을 때 가장 먼저 물을 것은 "이미 push 해서 남이 받아 갔는가?"입니다. 아직 내 컴퓨터에만 있다면 이력을 다시 써도 되지만(✗가 해당), 공유했다면 revert 처럼 앞으로 나아가는 방법만 안전합니다(✓).

The first question in an accident is "was it already pushed and pulled by others?" If it exists only on your machine you may rewrite history (the ✗ rows); once shared, only forward-moving methods like revert are safe (✓).

사례를 고르면 문제가 이미 일어난 상태의 터미널이 열리고 증상을 보여 줍니다. 터미널에서 직접 명령을 쳐 해결해 보세요. 해결되면 ✓ 표시가 뜨고, 막히면 힌트 → 정답 순서로 볼 수 있습니다. (점선 버튼은 환경 문제라 터미널 없이 설명만 있는 사례입니다.) 사례 링크: #case=push-rejected 처럼 주소 끝에 붙일 수 있습니다.

Pick a case and a terminal opens with the problem already happening, showing the symptom. Fix it by typing commands yourself. A ✓ appears once solved; if stuck, see hints, then the answer. (Dashed buttons are environment problems explained without a terminal.) Cases are linkable: append something like #case=push-rejected to the address.

사고를 만났을 때의 원칙Principles for when things go wrong

① 멈추고, 메시지를 끝까지 읽는다① Stop and read the message to the end

Git 의 오류 문장은 길지만 해결책이 적혀 있는 경우가 많습니다. hint:로 시작하는 줄, use "git restore --staged <file>..." 같은 안내가 그것입니다. 당황해서 아무 명령이나 연달아 치면 상황이 더 나빠집니다 — 특히 --force · --hard가 붙은 명령.

Git's error text is long but often contains the fix: the lines starting with hint: and guidance like use "git restore --staged <file>...". Panicking and firing commands makes things worse, especially anything with --force or --hard.

② 먼저 현재 위치를 파악한다② First learn where you are

git status(무슨 상태인가) → git log --oneline --all(이력이 어떻게 생겼나) → git reflog(내가 무슨 짓을 했나). 이 세 줄이면 대부분의 사고가 설명됩니다. 터미널 프롬프트에 브랜치와 MERGING/rebase 상태를 표시해 두면 더 빨리 알아챕니다.

git status (what state) → git log --oneline --all (what the history looks like) → git reflog (what I did). These three lines explain most accidents. Showing the branch and MERGING/rebase state in your prompt spots them sooner.

③ 위험한 작업 전에는 표시를 남긴다③ Leave a marker before risky work

git branch backup 한 줄이면 지금 상태에 이름표가 붙어 어떤 실수를 해도 돌아올 수 있습니다(브랜치가 붙잡고 있는 커밋은 reflog 보다 오래 남음). 큰 rebase · reset · filter-repo 전에 습관으로 만드세요. 일을 마치면 git branch -D backup.

One line, git branch backup, puts a label on the current state so you can return after any mistake (commits held by a branch outlast the reflog). Make it a habit before big rebase, reset or filter-repo. Afterwards git branch -D backup.

④ 공유한 이력은 건드리지 않는다④ Do not touch shared history

이미 push 해서 남이 받은 커밋은 reset · amend · rebase · push --force로 바꾸지 마세요. 되돌릴 때는 revert. 부득이 강제 push 가 필요하면 --force 대신 --force-with-lease(내가 마지막으로 본 상태일 때만 덮어씀)를 쓰고, 팀에 먼저 알리세요.

Do not change commits already pushed and pulled by others with reset, amend, rebase or push --force; undo with revert. If a force push is unavoidable, use --force-with-lease (overwrites only if the remote is as you last saw it) instead of --force, and tell the team first.

⑤ 복구되는 것과 안 되는 것⑤ What can and cannot be recovered

복구됨: 커밋한 적 있는 것(reflog 에 기록, 기본 약 30~90일), stash 한 것, 삭제한 브랜치의 커밋. 복구 안 됨: 한 번도 add/commit/stash 하지 않은 작업 폴더의 변경(restore · reset --hard · clean -f로 버린 것), 다른 사람의 reflog, 이미 퍼진 비밀. 그래서 자주 커밋하고 임시 커밋(wip)도 두려워하지 마세요.

Recoverable: anything ever committed (recorded in the reflog, by default roughly 30–90 days), stashed work and commits of a deleted branch. Not recoverable: working-tree changes never added, committed or stashed (discarded by restore, reset --hard or clean -f), other people's reflogs, and secrets already spread. So commit often, and do not fear temporary (wip) commits.

⑥ 팀 차원의 예방⑥ Prevention at the team level

브랜치 보호(main 직접 push 금지 · PR 필수 · CI 통과), Secret scanning · Push protection(키 push 차단), pre-commit 훅(포맷 · 비밀 검사), .gitignore · .gitattributes 템플릿, 커밋 · 브랜치 이름 규칙, 정기적인 git pull. 사고의 대부분은 사람의 실수이므로 실수가 일어나도 피해가 작게 만드는 장치가 가장 효과적입니다.

Branch protection (no direct pushes to main, PR required, CI must pass), secret scanning and push protection (blocks pushed keys), pre-commit hooks (format and secret checks), .gitignore and .gitattributes templates, commit and branch naming rules, and regular git pull. Most accidents are human error, so devices that keep damage small when mistakes happen work best.

⑦ 도움을 청할 때⑦ When asking for help

다음을 붙여 주면 남이 빨리 도와줄 수 있습니다: git status, git log --oneline --graph --all -n 15, git remote -v, git branch -vv, 그리고 정확한 오류 문장 전체. 비밀(토큰 · 키)이 섞이지 않았는지 보고 보내세요. 도움을 받기 전에 git branch backup도 잊지 마세요.

Paste these and others can help quickly: git status, git log --oneline --graph --all -n 15, git remote -v, git branch -vv and the exact full error text. Check no secrets (tokens, keys) are mixed in. And do not forget git branch backup before getting help.

⑧ 이 사례집이 생략한 것⑧ What these cases leave out

실제 사고는 파일이 더 많고, 편집기로 충돌을 풀며, 원격은 GitHub 설정(브랜치 보호 · 권한 · 훅)에 따라 다르게 반응합니다. 여기서는 핵심 원리가 드러나는 최소 상태로 줄였고, 서브모듈 · LFS · 훅 · 대용량 저장소의 성능 문제, rebase -i, bisect 는 다루지 않았습니다. 해결 명령이 여러 가지인 사례는 한 가지 정답만 보여 줍니다(다른 방법도 인정됩니다).

Real accidents involve more files, conflicts resolved in an editor, and remotes that react differently to GitHub settings (branch protection, permissions, hooks). Here each case is reduced to the minimum state that reveals the principle; submodules, LFS, hooks, performance problems of huge repos, rebase -i and bisect are not covered. Where several commands work, only one answer is shown (others also count).
