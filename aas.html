ASSET ADMINISTRATION SHELL

자산관리셸(AAS)과 온톨로지The Asset Administration Shell and ontologies

AAS는 자산 한 대의 정보를 담아 주고받는 표준 그릇이고,
온톨로지는 그 안에 담긴 말의 뜻을 정하고 서로 잇는 사전입니다.

The AAS is a standard container for exchanging what is known about one asset.
An ontology is the dictionary that fixes the meaning of what is inside and links it.

자산관리셸(AAS, Asset Administration Shell)은 독일 인더스트리 4.0에서 나온 디지털 트윈의 표준 형식입니다. 이 페이지는 AAS가 무엇이고 어떻게 생겼는지, 온톨로지와 무엇이 같고 다른지를 정리하고, 이 사이트 자산관리 온톨로지의 주변압기 한 대를 실제 AAS 데이터셋(JSON · RDF)으로 만들어 두 가지를 이어 봅니다.

The Asset Administration Shell (AAS) is the standard format for a digital twin that came out of Germany's Industrie 4.0. This page explains what an AAS is and how it is built, where it agrees with and differs from an ontology, and then turns one main transformer from this site's asset-management ontology into a real AAS dataset (JSON and RDF) and joins the two.

⚠ 가상 데이터 · 개인 학습 정리Fictional data · personal study notes

데이터셋의 변전소 · 제작사 · 형식 · 진단값은 모두 지어낸 것입니다. AAS의 구조와 식별자는 IDTA 공개 사양(메타모델 V3.0)과 공개 템플릿에서 확인해 옮겼지만, 설명에는 만든 이의 해석이 섞여 있으니 실제 적용에는 원문을 확인하세요.

The substation, manufacturer, type and diagnostic values in the dataset are all invented. The AAS structure and identifiers were checked against the public IDTA specification (metamodel V3.0) and public templates, but the explanations include the author's own reading — check the sources before relying on them.

AAS란 무엇인가What an AAS is

공장의 모터, 변전소의 변압기, 소프트웨어 한 벌처럼 조직에 가치가 있는 것을 자산(Asset)이라 부릅니다. 자산마다 명판 · 기술 사양 · 도면 · 시험 성적서 · 정비 이력이 따라다니는데, 제작사마다 형식이 달라 받는 쪽에서 매번 다시 입력해야 했습니다. AAS는 이 정보를 누가 만들어도 같은 구조로 담도록 정한 것입니다. 자산과 그 관리셸을 한 쌍으로 묶은 것을 인더스트리 4.0에서는 I4.0 컴포넌트라고 부릅니다.

Anything of value to an organisation — a motor in a plant, a transformer in a substation, a piece of software — is an asset. Each one drags along a nameplate, technical data, drawings, test reports and a maintenance history, in a different format per manufacturer, so the receiver re-types it every time. The AAS fixes one structure regardless of who produced it. Industrie 4.0 calls the pair of an asset and its shell an I4.0 component.

주고받는 세 가지 방식Three ways to exchange it

유형 1 · 파일Type 1 · file

JSON · XML · RDF로 적거나, 문서와 도면까지 한 파일로 묶은 .aasx 꾸러미로 넘깁니다. 납품할 때 설비와 함께 건네는 방식.

Written as JSON, XML or RDF, or bundled with documents and drawings into one .aasx package — handed over together with the equipment.

유형 2 · 서버(API)Type 2 · server (API)

셸이 서버에 살아 있고, 표준 REST API로 서브모델과 값을 읽고 씁니다. 운전 중인 설비의 현재 값을 볼 때.

The shell lives on a server; a standard REST API reads and writes submodels and values — for the live state of equipment in service.

유형 3 · 능동형Type 3 · proactive

셸끼리 스스로 말을 걸고 협상합니다. 아직 연구 · 시범 단계에 가깝습니다.

Shells talk and negotiate with each other on their own initiative. Still closer to research and pilots.

AAS가 하는 큰 역할What the AAS is really for

AAS를 "설비를 기술하는 용어의 통일"로 이해하기 쉽지만, 용어 통일은 절반이고 그나마 AAS가 직접 하는 일도 아닙니다. 뜻을 정하는 것은 IEC CDD · ECLASS 같은 사전과 온톨로지이고, AAS는 semanticId로 그 사전을 가리킬 뿐입니다. AAS 고유의 역할은 설비 정보를 담는 그릇과 꺼내는 창구의 통일입니다. 어떤 설비든 같은 구조(셸 → 서브모델 → 요소)로 담고, 같은 API로 꺼내고, 같은 파일(.aasx)로 넘깁니다.

It is tempting to read the AAS as "unifying the vocabulary that describes equipment", but vocabulary is only half of it — and not the half the AAS itself does. Meaning is fixed by dictionaries such as IEC CDD and ECLASS and by ontologies; the AAS merely points at them with semanticId. What the AAS itself unifies is the container the information sits in and the door it comes out of: any equipment in the same structure (shell → submodel → element), through the same API, in the same file (.aasx).

둘 중 하나만 있으면 상호운용이 되지 않습니다. 그릇의 통일에서 따라 나오는 실질적인 효과는 세 가지입니다.

Either one alone does not give interoperability. Three practical effects follow from unifying the container.

①

회사 경계를 넘는 인수인계Handover across company boundaries

제작사가 납품할 때 명판 · 사양 · 시험 성적서 · 도면을 셸로 넘기면, 운영자는 자산 대장에 다시 입력하지 않고 그대로 읽어 들입니다. 제작사가 100곳이어도 받는 쪽은 연동을 한 번만 만들면 됩니다. 전력 분야에서는 이것이 가장 현실적인 가치라고 봅니다.

When a manufacturer delivers the nameplate, technical data, test reports and drawings as a shell, the operator loads them instead of re-typing them into the asset register. With a hundred manufacturers the receiver still builds one integration. For the power sector this looks like the most realistic value.

②

설비 한 대의 생애 기록The life record of one unit

셸은 실물을 따라다니며 제작 → 설치 → 운전 → 정비 → 폐기의 이력을 한곳에 쌓습니다. 계통 모델(CIM)은 "자리"를 다루기 때문에 실물 한 대의 이력은 비어 있는데, 그 자리를 AAS가 채웁니다.

The shell travels with the physical unit and accumulates its history in one place: manufacture → installation → operation → maintenance → disposal. The network model (CIM) deals in positions, so the history of the physical unit is a gap there — the gap the AAS fills.

③

규제 대응의 틀A frame for regulation

IDTA는 탄소발자국(IDTA 02023)과 디지털 배터리 여권(IDTA 02035)을 서브모델 템플릿으로 내놓았습니다. 제품 정보를 정해진 형식으로 공개하라는 요구가 늘수록, 같은 그릇을 쓰는 쪽이 대응하기 쉽습니다. 어디까지 의무가 될지는 제도마다 다르니 해당 규정을 확인해야 합니다.

IDTA publishes submodel templates for the carbon footprint (IDTA 02023) and the digital battery passport (IDTA 02035). As demands to disclose product information in a fixed format grow, whoever already uses the common container responds more easily. How far any of this becomes mandatory depends on the regulation in question, so check the rule that applies.

💡 쉽게 말하면In plain words

AAS는 "무엇을 어느 칸에 담아 어떻게 건넬지"를 통일하고, 사전과 온톨로지는 "그 칸에 적힌 말이 무슨 뜻인지"를 통일합니다. 택배로 치면 AAS는 규격 상자와 송장 양식이고, 온톨로지는 품목 이름을 풀이한 사전입니다.

The AAS unifies "what goes in which slot and how it is handed over"; dictionaries and ontologies unify "what the words in the slot mean". In parcel terms, the AAS is the standard box and waybill form; the ontology is the dictionary of what the item names mean.

온톨로지와의 관계How it relates to ontologies

둘 다 "기계가 읽는 정보 모델"이라 자주 섞여 불리지만 푸는 문제가 다릅니다. AAS는 자산 한 대의 정보를 어떤 칸에 담아 건넬지를 정하고, 온톨로지는 그 칸의 말이 무엇을 뜻하고 다른 것과 어떻게 이어지는지를 정합니다.

Both are "machine-readable information models", so they are often lumped together, but they solve different problems. The AAS decides which slots carry one asset's information when it is handed over; an ontology decides what the words in those slots mean and how they connect to everything else.

💡 쉽게 말하면In plain words

AAS는 설비마다 붙는 표준 서류철입니다. 어느 칸에 무엇을 넣는지가 정해져 있어 누구나 꺼내 볼 수 있습니다. 온톨로지는 서류철들에 적힌 낱말을 풀이하고 서로 이어 주는 사전이자 지도입니다. 서류철의 칸마다 "이 칸의 뜻은 사전의 이 낱말"이라고 적어 두는 것이 semanticId입니다.

An AAS is a standard file folder attached to each piece of equipment: the slots are fixed, so anyone can find things. An ontology is the dictionary and map that explains the words in those folders and connects them. A semanticId is the note on each slot saying "this slot means that word in the dictionary".

같은 사실 한 줄, 세 가지 모양One fact, three shapes

"이 변압기의 건전도 지수는 53이다"를 AAS(JSON), AAS의 RDF 직렬화, 온톨로지로 각각 적으면 이렇습니다.

"This transformer's health index is 53", written as AAS JSON, as the AAS RDF serialisation, and as an ontology statement.

AAS · JSON

{ "idShort": "HealthIndex",
  "semanticId": { "type": "ExternalReference",
    "keys": [ { "type": "GlobalReference",
      "value": "https://…/asset#healthIndex" } ] },
  "valueType": "xs:decimal",
  "value": "53",
  "modelType": "Property" }

AAS · RDF

[ rdf:type aas:Property ;
  <…/Referable/idShort> "HealthIndex" ;
  <…/HasSemantics/semanticId> [
    rdf:type aas:Reference ;
    <…/Reference/keys> [ rdf:type aas:Key ;
      <…/Key/value> "https://…/asset#healthIndex" ] ] ;
  <…/Property/valueType> <…/DataTypeDefXsd/Decimal> ;
  <…/Property/value> "53" ]

온톨로지Ontology

pam:AS_TR_0007 pam:healthIndex 53.0 .

주어가 자산 자신이고, 술어가 곧 뜻입니다.

The subject is the asset itself and the predicate is the meaning.

가운데 칸이 중요합니다. AAS를 RDF로 적는다고 온톨로지가 되지는 않습니다. AAS RDF는 "idShort가 HealthIndex이고 값이 문자열 53인 Property가 있다"는 서류철의 모양을 그래프로 옮긴 것이지, "이 변압기의 건전도는 53"이라는 사실을 직접 말하지 않습니다. 뜻을 가리키는 semanticId도, 값도, 다른 서브모델을 가리키는 참조도 모두 문자열이라, 그대로는 다른 그래프와 선이 이어지지 않습니다.

The middle column matters. Writing an AAS in RDF does not make it an ontology. AAS RDF transcribes the shape of the folder — "there is a Property whose idShort is HealthIndex and whose value is the string 53" — rather than stating "this transformer's health index is 53". The semanticId, the value and the references to other submodels are all strings, so nothing links to another graph as it stands.

둘을 잇는 세 가지 방법Three ways to connect the two

①

자산 식별자를 온톨로지의 개체 IRI로Use the ontology individual's IRI as the asset id

globalAssetId에 온톨로지에서 이 자산을 가리키는 IRI를 그대로 씁니다. 셸과 온톨로지가 같은 물건을 말하고 있음을 알 수 있는 가장 단순한 고리입니다. 업무 시스템의 번호는 specificAssetIds에 둡니다.

Put the IRI that names this asset in the ontology straight into globalAssetId. It is the simplest hook that shows the shell and the ontology are talking about the same thing. Ids from business systems go in specificAssetIds.

"assetInformation": { "assetKind": "Instance",
  "globalAssetId": "https://1004aiteam-power.github.io/ontology-space/asset#AS_TR_0007",
  "specificAssetIds": [ { "name": "eamNumber", "value": "EQ-TR-2015-0007" } ] }
②

semanticId를 온톨로지의 용어 IRI로Point semanticIds at ontology terms

표준 사전(IEC CDD · ECLASS)에 있는 항목은 그 식별자를 쓰고, 사전에 없는 분야 고유 항목은 온톨로지의 속성 · 클래스 IRI를 semanticId로 씁니다. 여기서는 건전도 · 위험도는 자산관리 온톨로지(pam:), 정격 용량 · 전압은 IEC CIM(cim:)을 가리킵니다. 셸에 함께 싣는 ConceptDescription에는 isCaseOf로 같은 IRI를 적어, 받는 쪽이 정의와 단위를 바로 볼 수 있게 했습니다.

Items that exist in a standard dictionary (IEC CDD, ECLASS) use that identifier; domain-specific items use an ontology property or class IRI. Here health and risk point at the asset-management ontology (pam:) and rated power and voltage at IEC CIM (cim:). The ConceptDescriptions shipped with the shell carry the same IRI in isCaseOf, so a receiver sees the definition and unit at once.

③

AAS를 RDF로 옮기고 다리를 놓아 한 그래프로Serialise to RDF and bridge into one graph

AAS RDF를 온톨로지와 같은 그래프에 불러온 다음, 문자열로 적힌 참조 가운데 온톨로지에 실제로 있는 개체를 가리키는 것만 골라 진짜 연결로 적어 줍니다. 아래 데이터셋에서는 연결 15개(aas-links.ttl)가 그 다리입니다. 그러면 셸에서 출발해 온톨로지에만 있는 고장 모드 · 작업지시 · 설치 이력까지 한 번에 물을 수 있습니다.

Load the AAS RDF into the same graph as the ontology, then turn the string references that point at individuals actually present in the ontology into real links. In the dataset below 15 links (aas-links.ttl) form that bridge. A query can then start at the shell and reach failure modes, work orders and deployment history that exist only in the ontology.

<…/aas/shell/AS-TR-0007> aasl:describes pam:AS_TR_0007 ;          # globalAssetId
    aasl:hasSubmodel <…/aas/sm/AS-TR-0007/ConditionAndRisk> , … .   # submodels
<…/ConditionAndRisk#FunctionalLocation> aasl:refersTo ex:TR_1 .   # ReferenceElement

전력 분야에서: CIM과 AASIn the power sector: CIM and the AAS

이 사이트가 다루는 IEC CIM은 계통 관점의 모델입니다. "주변압기 #1"이라는 자리(기능 위치)가 어디에 연결되어 있는지를 다룹니다. AAS는 제품 관점입니다. 그 자리에 놓인 실물 한 대가 누가 만든 어떤 형식이고 어떤 이력을 가졌는지를 제작사에서 운영자에게 넘깁니다. 자산관리 온톨로지가 기능 위치와 물리 자산을 나눠 둔 덕분에 둘이 자연스럽게 이어집니다. 셸은 물리 자산(pam:Asset)에 붙고, 자산은 pam:installedAt으로 CIM의 설비를 가리킵니다. 변압기를 교체하면 셸은 새것으로 바뀌지만 자리와 계통 모델은 그대로입니다.

IEC CIM, which this site is built around, is the system view: where the position "main transformer #1" is connected. The AAS is the product view: who made the physical unit sitting in that position, what type it is and what has happened to it — handed from manufacturer to operator. Because the asset-management ontology separates functional locations from physical assets, the two meet cleanly: the shell attaches to the physical asset (pam:Asset) and the asset points at the CIM equipment through pam:installedAt. Replace the transformer and the shell changes, while the position and the network model stay.

데이터셋: 주변압기 #1 본체의 자산관리셸Dataset: the shell of main transformer #1

가상 A변전소 주변압기 #1 본체(AS-TR-0007) 한 대를 AAS 메타모델 V3.0의 JSON으로 적은 것입니다. 값은 새로 만들지 않고 자산관리 온톨로지의 원본 CSV와 계산값에서 가져왔고, 공개된 AAS JSON 스키마로 검사했습니다. 왼쪽에서 항목을 고르면 오른쪽에 그 항목의 뜻과 원본 JSON이 나옵니다.

One unit — main transformer #1 of virtual substation A (AS-TR-0007) — written as AAS metamodel V3.0 JSON. No value is new: everything comes from the asset-management ontology's source CSV files and computed values, and the result was validated against the public AAS JSON schema. 한 그래프로 합쳐 묻기 (Cypher)Asking across one graph (Cypher)

aas-mtr1.ttl(AAS RDF), aas-links.ttl(다리), asset-ontology.ttl(자산관리 온톨로지)을 Neo4j에 불러올 때와 같은 방식(클래스 → 라벨, 값 → 속성, 연결 → 관계)으로 한 그래프에 합쳐, 빌드할 때 아래 질문을 실행한 결과입니다. Q1 · Q2는 AAS만으로 답하고, Q3 · Q4는 다리를 건너 온톨로지에만 있는 지식을 가져오며, Q5는 두 곳에 적힌 같은 값이 어긋나지 않았는지 확인합니다.

aas-mtr1.ttl (AAS RDF), aas-links.ttl (the bridge) and asset-ontology.ttl are merged into one graph the way Neo4j would load them (classes → labels, values → properties, links → relationships), and these questions are run at build time. Q1 and Q2 are answered by the AAS alone, Q3 and Q4 cross the bridge to knowledge that exists only in the ontology, and Q5 checks that values written in both places have not drifted apart.

설계 결정Design decisions

D1

값은 한 곳에서 만들고 AAS는 내보내는 창구로One source of truth; the AAS is an export

건전도 · 위험도는 자산관리 온톨로지 빌드가 계산하고, AAS는 그 결과를 읽어 적기만 합니다. 같은 값을 두 곳에서 따로 관리하면 반드시 어긋나므로, 어긋났는지 확인하는 질문(Q5)을 함께 두었습니다.

Health and risk are computed by the asset-ontology build; the AAS only writes down the result. Keeping one value in two places always drifts, so a question that detects drift (Q5) ships with it.

D2

표준 사전에 있으면 그것을, 없으면 온톨로지를Standard dictionary first, ontology where there is none

명판은 IDTA 템플릿의 IEC CDD 식별자를 그대로 써서 다른 회사의 도구도 읽을 수 있게 했습니다. 건전도처럼 표준 사전에 없는 항목만 온톨로지 IRI를 semanticId로 썼습니다. 온톨로지 IRI만 쓰면 이 사이트 밖에서는 아무도 뜻을 모릅니다.

The nameplate uses the IEC CDD identifiers of the IDTA template unchanged, so other vendors' tools can read it. Only items absent from standard dictionaries, such as the health index, use ontology IRIs. With ontology IRIs alone, nobody outside this site would know what anything means.

D3

지식은 셸에 복사하지 않는다Knowledge is not copied into the shell

고장 모드 · 점검 주기 · 작업지시 · 정전 영향은 셸에 넣지 않았습니다. 자산 한 대의 것이 아니라 여러 자산과 계통에 걸친 지식이기 때문입니다. 셸에는 그 자산의 사실만 두고, 나머지는 다리를 건너 온톨로지에서 묻습니다.

Failure modes, inspection cycles, work orders and outage impact are not in the shell: they are knowledge spanning many assets and the network, not facts about one unit. The shell holds the unit's own facts; the rest is asked across the bridge.

D4

다리는 따로 둔 파일로The bridge is a separate file

AAS RDF는 사양의 대응 규칙 그대로 두고, 연결은 aas-links.ttl에 따로 적었습니다. 표준 형식의 파일을 고치지 않아도 되고, 가리키는 IRI가 온톨로지에 없으면 빌드가 실패해 끊어진 참조를 바로 알 수 있습니다.

The AAS RDF stays exactly as the specification's mapping produces it; links live in aas-links.ttl. The standard-format file is never touched, and the build fails if a referenced IRI is missing from the ontology, so broken references surface immediately.
