☕ Java: 계약을 지키는 객체들Java: objects that honour contracts

Java 는 JVM 위에서 수십 년째 현역인 대규모 시스템의 언어입니다. 메모리는 GC 가 맡아 주지만 객체의 동일성 · equals/hashCode 계약 · 컬렉션 선택 · 동시성을 모르면 느리거나 틀린 코드를 씁니다. 문법 입문은 건너뛰고 중급의 문턱 개념을 실제로 컴파일해 본 코드로 설명하고, HashMap 속을 직접 들여다보는 시연을 더했습니다.

Java is the language of large systems that have been in service for decades on the JVM. The GC handles memory, but without object identity, the equals/hashCode contract, collection choice and concurrency you write slow or wrong code. Skipping syntax basics, this page explains the intermediate-threshold concepts with code that was really compiled, plus a demo that looks inside a HashMap.

코드와 출력은 제작 환경(OpenJDK 21, Linux 64비트)에서 실행한 결과입니다. 버전이 다르면 일부 출력이 다를 수 있습니다. 시연의 HashMap 모형은 테스트가 실제 JVM 과 대조합니다.

Code and output come from running OpenJDK 21 on 64-bit Linux in the authoring environment; other versions may differ in some output. The demo's HashMap model is checked against a real JVM by a test.

    핵심 개념 10가지Ten core concepts

    문법 입문은 건너뛰고, 면접과 실무에서 갈리는 개념만 모았습니다: 실행 모델 → 객체와 동일성 → 컬렉션의 계약 → 제네릭 → 함수형 → 예외 · 동시성 · 메모리 → 현대 문법.

    Skipping syntax basics, these are the concepts that separate people in interviews and on the job: the execution model → objects and identity → collection contracts → generics → functional style → exceptions, concurrency, memory → modern syntax.

    ① JVM: 바이트코드 · 클래스 로딩 · JIT① The JVM: bytecode, class loading, JIT

    javac는 소스를 기계어가 아닌 바이트코드로 번역하고, JVM 이 클래스를 필요할 때 로딩해 실행합니다. 처음엔 해석하다가 자주 실행되는 메서드(핫스팟)를 JIT 가 최적화된 기계어로 바꾸므로 시작은 느리고 오래 돌수록 빨라집니다(워밍업). 그래서 짧은 벤치마크는 믿기 어렵고, 성능 측정은 JMH 같은 도구로 합니다. javap -c로 바이트코드를 볼 수 있습니다.

    javac translates source not to machine code but to bytecode, and the JVM loads classes when needed and runs them. It interprets at first, then the JIT turns frequently run methods (hot spots) into optimised machine code, so it starts slowly and speeds up the longer it runs (warm-up). That is why short benchmarks are unreliable and performance is measured with tools like JMH. javap -c shows the bytecode.

    }

    ② 기본형 · 참조형 · == 와 equals② Primitives, references, and == vs equals

    int · double · boolean 같은 기본형은 값, 나머지(객체)는 참조입니다. 변수에 객체를 대입하거나 메서드에 넘기는 것은 참조 값을 복사(pass-by-value)하므로 메서드 안에서 객체의 내용은 바꿀 수 있어도 호출자의 변수가 가리키는 대상은 못 바꿉니다. ==는 기본형은 값, 참조는 같은 객체인가이고, 내용 비교는 equals입니다. Integer 같은 박싱 타입은 -128~127 만 캐시해서 ==가 가끔만 true 가 됩니다.

    Primitives like int, double, boolean are values; everything else (objects) is a reference. Assigning or passing an object copies the reference value (pass-by-value), so a method can change an object's contents but not which object the caller's variable points at. == compares values for primitives and identity for references; content comparison is equals. Boxed types like Integer cache only -128 to 127, so == is true only sometimes.

    import java.util.*;

public class Main {
    static void change(List<Integer> list, int n) {
        list.add(99);          // 객체 내용은 바꿀 수 있다
        list = new ArrayList<>(); // 지역 변수만 바뀜 (호출자는 모름)
        n = 0;                 // 기본형은 값 복사
    }

    public static void main(String[] args) {
        List<Integer> xs = new ArrayList<>(List.of(1, 2));
        int n = 5;
        change(xs, n);
        System.out.println(xs + " " + n);

        String a = "grid", b = new String("grid");
        System.out.println((a == b) + " " + a.equals(b));
        Integer i1 = 127, i2 = 127, j1 = 1000, j2 = 1000;
        System.out.println((i1 == i2) + " " + (j1 == j2) + " " + j1.equals(j2));
    }
}

    ③ equals · hashCode 계약과 HashMap③ The equals/hashCode contract and HashMap

    HashMap · HashSet은 hashCode 로 버킷을 고르고, 그 안에서 equals 로 같은 키를 찾습니다. 그래서 계약이 있습니다: equals 가 같으면 hashCode 도 같아야 합니다(반대는 아니어도 됨). equals 만 재정의하면 같은 값의 두 객체가 다른 버킷에 들어가 contains가 false 가 됩니다. 키는 불변으로 두세요. 위 시연이 좋은 · 나쁜 · 가변 키 세 경우를 보여 줍니다. 값 클래스는 record(16+)를 쓰면 equals · hashCode · toString 이 자동으로 맞게 만들어집니다.

    HashMap and HashSet choose a bucket with hashCode, then find the same key inside it with equals. Hence the contract: equal objects must have equal hashCodes (not necessarily the reverse). Overriding only equals puts two equal objects in different buckets so contains says false. Keep keys immutable. The demo above shows good, bad and mutable keys. For value classes use a record (16+) and equals, hashCode and toString are generated correctly.

    import java.util.*;

public class Main {
    static class Bad {                         // equals 만 재정의
        final int id;
        Bad(int id) { this.id = id; }
        @Override public boolean equals(Object o) { return o instanceof Bad b && b.id == id; }
    }
    record Good(int id) {}                      // equals · hashCode 자동

    public static void main(String[] args) {
        Set<Bad> bad = new HashSet<>(List.of(new Bad(1)));
        Set<Good> good = new HashSet<>(List.of(new Good(1)));
        System.out.println(bad.contains(new Bad(1)) + " " + good.contains(new Good(1)));
        System.out.println(new Good(1) + " " + new Good(1).equals(new Good(1)));
    }
}

    ④ 제네릭과 타입 소거④ Generics and type erasure

    제네릭은 컴파일 때 타입 오류를 잡아 주지만, 실행 시에는 List<String>과 List<Integer>가 같은 클래스(List)입니다(타입 소거). 그래서 new T() · T[] · instanceof List<String>가 안 되고, 기본형은 제네릭 인자로 못 써서 List<Integer>처럼 박싱됩니다. 와일드카드는 PECS(Producer extends, Consumer super)로 기억하세요: 읽기만 하면 ? extends T, 쓰기만 하면 ? super T.

    Generics catch type errors at compile time, but at run time List<String> and List<Integer> are the same class (List) (type erasure). So new T(), T[] and instanceof List<String> are not allowed, and primitives cannot be generic arguments so List<Integer> boxes. Remember wildcards as PECS (Producer extends, Consumer super): ? extends T to only read, ? super T to only write.

    import java.util.*;

public class Main {
    static double sum(List<? extends Number> xs) {        // 읽기 전용 → extends
        double s = 0;
        for (Number n : xs) s += n.doubleValue();
        return s;
    }
    static void fill(List<? super Integer> out) {          // 쓰기 전용 → super
        out.add(1); out.add(2);
    }

    public static void main(String[] args) {
        System.out.println(new ArrayList<String>().getClass() == new ArrayList<Integer>().getClass());
        List<Number> nums = new ArrayList<>();
        fill(nums);
        System.out.println(sum(nums) + " " + sum(List.of(1.5, 2.5)));
    }
}

    ⑤ 컬렉션: 무엇을 고를까⑤ Collections: which to choose

    List는 순서 · 중복 허용(ArrayList가 기본, LinkedList 는 드묾), Set은 중복 없음, Map은 키 → 값. HashMap/HashSet은 순서 보장 없이 가장 빠르고, LinkedHashMap은 넣은 순서, TreeMap은 키 정렬 순서(O(log n))입니다. List.of · Map.of는 수정 불가 컬렉션이라 안전한 값 전달에 좋습니다. 변수 타입은 구현이 아닌 인터페이스(List)로 선언합니다.

    List keeps order and allows duplicates (ArrayList is the default; LinkedList is rare), Set has no duplicates, Map maps key → value. HashMap/HashSet are fastest with no ordering, LinkedHashMap keeps insertion order and TreeMap sorted key order (O(log n)). List.of and Map.of build unmodifiable collections, good for passing values safely. Declare variables by interface (List), not implementation.

    import java.util.*;

public class Main {
    public static void main(String[] args) {
        String[] ids = {"T3", "B1", "T1", "C2"};
        Map<String, Integer> hash = new HashMap<>(), linked = new LinkedHashMap<>(), tree = new TreeMap<>();
        for (String id : ids) { hash.put(id, id.length()); linked.put(id, id.length()); tree.put(id, id.length()); }
        System.out.println(linked.keySet());   // 넣은 순서
        System.out.println(tree.keySet());     // 정렬 순서
        System.out.println(hash.size());       // HashMap 은 순서를 약속하지 않음
        List<Integer> fixed = List.of(1, 2, 3);
        try { fixed.add(4); } catch (UnsupportedOperationException e) { System.out.println("immutable"); }
    }
}

    ⑥ 람다 · 스트림 · Optional⑥ Lambdas, streams and Optional

    람다는 메서드가 하나인 인터페이스(함수형 인터페이스)를 간단히 쓰는 문법이고, 스트림은 컬렉션을 선언적으로 처리합니다: filter → map → collect. 스트림은 최종 연산이 불릴 때까지 아무것도 실행하지 않는(지연) 파이프라인이고 한 번만 쓸 수 있습니다. Optional은 "값이 없을 수 있음"을 타입으로 드러내는 반환 타입용이며(필드 · 매개변수에는 쓰지 않음), groupingBy 같은 Collectors로 집계합니다. 스트림 안에서 바깥 변수를 바꾸지 마세요(부수 효과).

    A lambda is concise syntax for an interface with a single method (a functional interface), and streams process collections declaratively: filter → map → collect. A stream is a lazy pipeline that runs nothing until a terminal operation is called, and can be used only once. Optional is a return type that exposes "maybe no value" in the type (not for fields or parameters), and Collectors such as groupingBy aggregate. Do not mutate outer variables inside a stream (side effects).

    import java.util.*;
import java.util.stream.*;

public class Main {
    record Asset(String id, String type, int health) {}

    public static void main(String[] args) {
        List<Asset> assets = List.of(new Asset("T1", "transformer", 82), new Asset("B1", "breaker", 91),
                                     new Asset("B2", "breaker", 58), new Asset("T2", "transformer", 64));
        System.out.println(assets.stream().filter(a -> a.health() >= 70).map(Asset::id).collect(Collectors.toList()));
        Map<String, Double> avg = assets.stream().collect(Collectors.groupingBy(Asset::type, TreeMap::new, Collectors.averagingInt(Asset::health)));
        System.out.println(avg);
        Optional<Asset> worst = assets.stream().min(Comparator.comparingInt(Asset::health));
        System.out.println(worst.map(Asset::id).orElse("none"));
    }
}

    ⑦ 예외: checked · unchecked · try-with-resources⑦ Exceptions: checked, unchecked, try-with-resources

    RuntimeException(unchecked)은 프로그래머 오류(NullPointerException · IllegalArgumentException)에, checked 예외(IOException 등)는 "호출자가 복구할 수 있는 외부 실패"에 쓰며 컴파일러가 처리(catch/throws)를 강제합니다. 자원은 try-with-resources(AutoCloseable)로 열어 예외가 나도 선언의 역순으로 닫히게 합니다. 예외를 삼키지 말고(빈 catch), 원인을 연쇄(new X("…", cause))해 스택 트레이스를 보존하세요.

    RuntimeException (unchecked) is for programmer errors (NullPointerException, IllegalArgumentException); checked exceptions (IOException etc.) are for "external failures the caller can recover from", and the compiler forces handling (catch/throws). Open resources with try-with-resources (AutoCloseable) so they close in reverse order of declaration even on exceptions. Do not swallow exceptions (empty catch); chain the cause (new X("…", cause)) to keep the stack trace.

    public class Main {
    static class Res implements AutoCloseable {
        final String name;
        Res(String n) { name = n; System.out.println("open " + n); }
        @Override public void close() { System.out.println("close " + name); }
    }

    static void run() throws Exception {
        try (Res a = new Res("A"); Res b = new Res("B")) {
            System.out.println("work");
            throw new IllegalStateException("boom");
        }
    }

    public static void main(String[] args) {
        try {
            run();
        } catch (Exception e) {
            RuntimeException wrapped = new RuntimeException("run failed", e);   // 원인 연쇄
            System.out.println(wrapped.getMessage() + " <- " + wrapped.getCause().getMessage());
        }
    }
}

    ⑧ 동시성: 스레드 풀 · 원자 변수 · 가상 스레드⑧ Concurrency: thread pools, atomics, virtual threads

    스레드를 직접 만들기보다 ExecutorService(스레드 풀)에 작업을 제출하고 Future로 결과를 받습니다. 여러 스레드가 공유 변수를 고치면 경쟁 상태로 결과가 틀리므로 synchronized · Lock · AtomicInteger · ConcurrentHashMap으로 보호합니다(volatile은 "보이기"만 보장하고 원자성은 아님). Java 21 의 가상 스레드는 JVM 이 관리하는 가벼운 스레드라 I/O 로 대기하는 작업을 수십만 개 만들어도 되고, 블로킹 코드를 그대로 쓰면서 asyncio 같은 효과를 얻습니다.

    Rather than create threads directly, submit work to an ExecutorService (thread pool) and receive results through Future. When several threads modify shared variables a race condition corrupts results, so protect them with synchronized, Lock, AtomicInteger or ConcurrentHashMap (volatile only guarantees visibility, not atomicity). Java 21's virtual threads are lightweight JVM-managed threads, so you can create hundreds of thousands of I/O-waiting tasks and keep blocking-style code while getting an asyncio-like effect.

    import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicInteger;

public class Main {
    public static void main(String[] args) throws Exception {
        AtomicInteger counter = new AtomicInteger();
        try (ExecutorService pool = Executors.newFixedThreadPool(4)) {     // 21: try-with-resources 로 종료까지 기다림
            List<Future<Integer>> fs = new ArrayList<>();
            for (int t = 0; t < 4; t++) {
                int id = t;
                fs.add(pool.submit(() -> {
                    for (int i = 0; i < 1000; i++) counter.incrementAndGet();   // 원자적 증가
                    return id * id;
                }));
            }
            for (Future<Integer> f : fs) System.out.print(f.get() + " ");
        }
        System.out.println("| " + counter.get());
    }
}

    ⑨ 메모리와 GC: 누수는 "남아 있는 참조"⑨ Memory and GC: a leak is a "retained reference"

    GC 는 어디서도 도달할 수 없는 객체만 회수합니다. 그래서 Java 의 메모리 누수는 "해제를 잊음"이 아니라 더는 안 쓰는데 참조가 남아 있는 것(예: 비워지지 않는 static 맵 캐시 · 등록만 하고 해제하지 않는 리스너 · ThreadLocal)입니다. 힙은 젊은 세대(대부분의 객체가 금방 죽음)와 늙은 세대로 나뉘고 젊은 세대 GC(minor)는 빠르며 늙은 세대 GC(major/full)는 길어질 수 있어, 객체를 오래 잡아 두지 않는 것이 성능의 핵심입니다. 상황 파악은 -Xlog:gc · jcmd · jmap · VisualVM / JFR 로 합니다.

    The GC reclaims only objects reachable from nowhere. So a Java memory leak is not "forgot to free" but a reference kept to something no longer used (a static map cache never emptied, listeners registered and never removed, ThreadLocal). The heap splits into a young generation (most objects die soon) and an old generation; young (minor) GCs are fast while old (major/full) GCs can be long, so not holding objects long is key to performance. Investigate with -Xlog:gc, jcmd, jmap, VisualVM or JFR.

    Combining records (data classes), sealed interfaces (only permitted implementations) and switch pattern matching (21) expresses algebraic data types concisely and safely: the compiler checks that the switch is exhaustive and fails to compile when a new case appears. Also var, text blocks ("""), Stream.toList() and enhanced instanceof (o instanceof Foo f) cut verbosity. New projects typically use an LTS release (17, 21).

    public class Main {

        System.out.println(area(new Circle(2)) + " " + area(new Rect(2, 3)));
        var text = """
            grid
              sub-A
            """;                                     // 텍스트 블록
        System.out.print(text);
    }

    흔한 함정 6가지: 증상 → 원인 → 해결Six common pitfalls: symptom → cause → fix

    ⚠ 문자열 · 박싱 타입을 == 로 비교⚠ Comparing strings and boxed values with ==

    증상. 같은 값인데 ==가 때로는 true, 때로는 false 입니다.

    Symptom. Equal values, yet == is true sometimes and false other times.

    public class Main {
    public static void main(String[] args) {
        String a = "grid", b = new String("grid");
        System.out.println((a == b) + " " + a.equals(b));
        Integer x = 127, y = 127, p = 1000, q = 1000;
        System.out.println((x == y) + " " + (p == q));
    }
}
    false true
true false

    원인. ==는 같은 객체인가를 봅니다. 리터럴은 풀에서 공유되고 new String은 별개 객체이며, Integer 는 -128~127 만 캐시됩니다.

    Cause. == asks same object? Literals are shared in a pool, new String is a separate object and Integer caches only -128 to 127.

    해결. 객체 비교는 equals(또는 Objects.equals, null 안전)로. ==는 기본형과 열거형 · null 확인에만.

    Fix. Compare objects with equals (or Objects.equals, null-safe). Use == only for primitives, enums and null checks.

    ⚠ equals 만 재정의하고 hashCode 는 그대로⚠ Overriding equals but not hashCode

    증상. HashSet.contains가 분명히 넣은 값을 못 찾습니다.

    Symptom. HashSet.contains cannot find a value you clearly added.

    원인. 객체의 기본 hashCode 는 주소 기반이라 값이 같아도 다른 버킷으로 갑니다. (위 ③의 첫 줄 false)

    Cause. The default hashCode is identity-based, so equal values go to different buckets (the first line of ③ above, false).

    해결. 둘을 함께 재정의하거나, 값 클래스는 record로 만듭니다. IDE 의 "equals/hashCode 생성"이나 Objects.hash(...)를 쓰세요.

    Fix. Override both together, or make value classes records. Use the IDE's "generate equals/hashCode" or Objects.hash(...).

    ⚠ 순회 중에 컬렉션 수정⚠ Modifying a collection while iterating

    증상. ConcurrentModificationException이 납니다.

    Symptom. ConcurrentModificationException is thrown.

    import java.util.*;

public class Main {
    public static void main(String[] args) {
        List<Integer> xs = new ArrayList<>(List.of(1, 2, 3, 4));
        try {
            for (Integer x : xs) if (x % 2 == 0) xs.remove(x);
        } catch (ConcurrentModificationException e) {
            System.out.println("CME");
        }
    }
}
    CME

    원인. for-each 는 내부 반복자를 쓰는데 그 밖에서 구조를 바꾸면 반복자가 감지해 예외를 던집니다(fail-fast).

    Cause. for-each uses an internal iterator that, on structural changes made elsewhere, detects them and throws (fail-fast).

    해결. removeIf · 반복자의 remove(), 또는 걸러낸 새 컬렉션을 만듭니다.

    Fix. Use removeIf, the iterator's remove(), or build a new filtered collection.

    import java.util.*;

public class Main {
    public static void main(String[] args) {
        List<Integer> xs = new ArrayList<>(List.of(1, 2, 3, 4));
        xs.removeIf(x -> x % 2 == 0);          // 안전한 일괄 삭제
        System.out.println(xs);
    }
}
    [1, 3]

    ⚠ 정수 오버플로는 조용히 일어난다⚠ Integer overflow is silent

    증상. 큰 수를 더했더니 음수가 나옵니다 (예외 없음).

    Symptom. Adding big numbers gives a negative result (no exception).

    public class Main {
    public static void main(String[] args) {
        int big = Integer.MAX_VALUE;
        System.out.println(big + 1);
        try { Math.addExact(big, 1); } catch (ArithmeticException e) { System.out.println(e.getMessage()); }
        long safe = (long) big + 1;                 // 더 넓은 타입으로 먼저
        System.out.println(safe);
    }
}
    -2147483648
integer overflow
2147483648

    원인. int는 32비트라 범위를 넘으면 2 의 보수로 돌아갑니다. Java 는 오버플로를 검사하지 않습니다.

    Cause. int is 32-bit and past the range it wraps around in two's complement. Java does not check overflow.

    해결. 크기가 걱정되면 long · BigInteger, 또는 Math.addExact(오버플로 시 예외)를 씁니다. 금액은 BigDecimal / 정수 단위.

    Fix. If size is a worry use long, BigInteger or Math.addExact (throws on overflow). Money belongs in BigDecimal or integer units.

    ⚠ null 과 자동 언박싱⚠ null and auto-unboxing

    증상. NullPointerException인데 줄에 변수 하나뿐입니다.

    Symptom. A NullPointerException on a line with just a variable.

    import java.util.*;

public class Main {
    public static void main(String[] args) {
        Map<String, Integer> health = new HashMap<>();
        try {
            int h = health.get("T9");               // 키가 없으면 null → 언박싱 NPE
        } catch (NullPointerException e) {
            System.out.println("NPE");
        }
        int ok = health.getOrDefault("T9", -1);     // 기본값 제공
        System.out.println(ok);
    }
}
    NPE
-1

    원인. Integer(박싱) 값이 null일 때 int로 대입하면 숨은 .intValue() 호출에서 NPE 가 납니다. map.get(key)가 null 을 돌려주는 경우가 흔합니다.

    Cause. Assigning a null Integer to an int triggers an NPE in the hidden .intValue() call. map.get(key) returning null is the common source.

    해결. getOrDefault · Optional · Objects.requireNonNullElse로 null 을 일찍 다루고, 박싱 타입이 정말 필요한지 검토하세요.

    Fix. Handle null early with getOrDefault, Optional or Objects.requireNonNullElse, and check whether you really need the boxed type.

    ⚠ 실수형으로 돈 계산 · BigDecimal 의 함정⚠ Money with floating point; BigDecimal traps

    증상. 0.1 + 0.2가 0.3 이 아닙니다. new BigDecimal(0.1)도 이상한 긴 수가 됩니다.

    Symptom. 0.1 + 0.2 is not 0.3, and new BigDecimal(0.1) is a strange long number.

    import java.math.BigDecimal;

public class Main {
    public static void main(String[] args) {
        System.out.println(0.1 + 0.2);
        System.out.println(new BigDecimal(0.1));
        System.out.println(new BigDecimal("0.1").add(new BigDecimal("0.2")));   // 문자열로 만들면 정확
        System.out.println(BigDecimal.valueOf(0.1));
    }
}
    0.30000000000000004
0.1000000000000000055511151231257827021181583404541015625
0.3
0.1

    원인. 이진 부동소수점은 0.1 을 정확히 못 담고, BigDecimal(double)은 그 부정확한 double 의 정확한 값을 가져옵니다.

    Cause. Binary floating point cannot hold 0.1 exactly, and BigDecimal(double) takes the exact value of that inexact double.

    해결. BigDecimal은 문자열 생성자나 valueOf로 만들고, 비교는 compareTo(equals는 자릿수까지 비교). 가능하면 정수(원 · 센트)로 다룹니다.

    Fix. Build BigDecimal from a string or valueOf, compare with compareTo (equals also compares scale). Prefer integer units (won, cents) where possible.
